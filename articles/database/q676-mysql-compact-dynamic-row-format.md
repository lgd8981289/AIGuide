# MySQL 的 COMPACT 和 DYNAMIC 行格式有什么区别？长字段为什么会放到溢出页？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/database/q676-mysql-compact-dynamic-row-format/) · [题库目录](../../README.md)

下面是一段模拟面试对话。

🧑‍💻 **面试官：** InnoDB 一页放不下一行时，长字段怎么办？

🙋‍♂️ **我：** 部分数据可以放到溢出页，记录里保留引用。

🧑‍💻 **面试官：** COMPACT 和 DYNAMIC 留在记录里的内容一样吗？

🙋‍♂️ **我：** 不一样，外部存储时保留的前缀策略有区别。

🧑‍💻 **面试官：** 那 DYNAMIC 下，每个 TEXT 都一定单独放到页外吗？行大小限制又是不是“整页那么大”？

> 看清“完整字段、页内部分、页外部分”三者的关系，别把类型名直接当成存储位置。

## 面试速答（60 秒版）

InnoDB 行格式决定记录怎样组织，以及长字段在页内、页外怎样分配。本文以 MySQL 8.4 为范围。

COMPACT 对需要页外存储的长变长字段，会在聚簇索引记录中保留前 768 字节及页外引用，其余部分放到溢出页。DYNAMIC 则可以把长字段完整放到页外，页内保留 20 字节引用，减少长前缀占用。

但 DYNAMIC 不是所有变长字段都无条件页外存储。是否移出要看整行、页大小和字段长度等条件，较短数据仍可以留在页内。

还要分清 MySQL 的行大小限制与 InnoDB 页内记录限制。改行格式只能改变一部分存储安排，不能让所有超宽表设计自然变合理，也不能保证读长字段永远更快。

## 知识点详解：记录里留的是值，还是找到值的线索？

### 聚簇索引叶子页，不只是主键列表

InnoDB 的聚簇索引记录承载行数据。页面除了记录本身，还有页面管理等开销，所以不能把默认 16KB 页面全部当成某一行可用空间。

如果行里出现很长的变长数据，把完整内容都挤在当前页里，会影响其他记录的存放。页外存储让记录保留找到数据的线索，把较大的部分放到其他页面。[MySQL 8.4 行格式文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-row-format.html)说明了对应组织方式。

这不意味着页外存储没有代价。查询真的需要那些内容时，仍要沿引用取得后面的数据。

### COMPACT 为什么还要留下长前缀？

对于需要外部存储的变长字段，COMPACT 在记录里保留 768 字节前缀，再加页外引用。

如果有多个较长字段，这些前缀本身就会占去不少页内空间。即使剩余大部分已经移到外部，当前记录仍可能很宽。

所以不要把 COMPACT 简化成“超过 768 字节就全部搬走”。留下什么，正是它和 DYNAMIC 的重要区别。触发页外的条件也不能只根据某个字段声明长度判断。

![页外存储时，页内留下什么？](https://note.lgdsunday.club/img/Q676/02-mysql-compact-dynamic-row-format.webp)

### DYNAMIC 让页内记录更紧凑，但不是强制搬空

在符合页外存储条件时，DYNAMIC 可以把长字段整个移出去，页内只保存 20 字节引用，不再强制留下同样的 768 字节前缀。

| 观察位置        | COMPACT 的长字段页外情况 | DYNAMIC 的长字段页外情况 |
| ----------- | ---------------- | ---------------- |
| 页内          | 前缀＋引用            | 可以只留引用           |
| 页外          | 剩余部分             | 可以保存完整字段值        |
| 是否所有变长字段都移出 | 否                | 否                |

把表理解成“发生页外存储时的差别”，就不会误读成两个格式对所有字段的固定摆放图。

它还与字符集、实际值大小和页内空间有关。CHAR 也不该只按名字认定永远不参与变长处理，某些较长定长字段会按相应变长方式编码。

### 两种限制，不是同一个数字

MySQL 有逻辑层面的最大行大小约束，InnoDB 又有与页面及记录组织相关的本地限制。外部存储的数据在这些限制中的计算方式也不相同。[InnoDB 限制文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-limits.html)应与行格式说明一起看。

因此，遇到 row size too large，要先看具体报错、列定义、字符集、实际行格式和页面设置。不要看到有人把某个字段改成 TEXT 就通过，便把它当作所有表的统一修复。

![紧凑记录，与读取路径一起看](https://note.lgdsunday.club/img/Q676/03-mysql-compact-dynamic-row-format.webp)

### 改格式之前，先看查询需要什么

如果大多数请求只读几个短字段，减少页内长前缀可能有利于页面利用。但请求每次都 SELECT \* 并读取大字段，又可能付出更多页外访问。

验证时记录行格式、数据分布、页与索引空间，以及目标查询的 I/O 和延迟。变更可能涉及表重建和资源开销，应先在副本或测试环境评估。本文没有执行生产 ALTER，也没有虚构两种格式的跑分。

## 面试官继续追问

### DYNAMIC 的名字，是说每一行可以任意改变格式吗？

不是。它是指定的行格式名称，仍按相应记录规则组织。不要把“动态”理解成没有限制、每次写入随便选择存储机制。

### 页外字段不能建索引吗？

不能这样推断。索引的键长度、前缀与字符集限制，需要按列类型、行格式和 MySQL 版本继续检查。数据本体在哪，和索引允许怎样建立，是相关但不同的问题。

## 面试速记卡

> - 行格式：影响记录组织和长字段页内、页外安排。
> - COMPACT：页外长字段仍保留 768 字节前缀及引用。
> - DYNAMIC：符合条件时可完整页外，只留 20 字节引用。
> - 条件：类型名和声明长度不能单独决定实际存储位置。
> - 判断：行限制、页内限制和真实读取成本分别核对。
