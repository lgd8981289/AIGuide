# Go 的 := 和 = 有什么区别？变量遮蔽为什么会让 err 判断失效？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/go/q715-go-short-declaration-variable-shadowing/) · [题库目录](../../README.md)

以下是一段用于讲解的模拟面试对话。

🧑‍💻 **面试官：** Go 里面 `:=` 和 `=` 有什么区别？

🙋‍♂️ **我：** 一个声明变量，一个给已有变量赋值。

🧑‍💻 **面试官：** 那 `file, err := open()`，err 已经存在时为什么有时能编译，有时会遮蔽？

🙋‍♂️ **我：** 只要左边有一个新变量就可以。

🧑‍💻 **面试官：** 这里的“已经存在”，是同一个代码块，还是外层代码块？如果看错，会不会把失败结果返回成 nil？

> 判断 `:=` 之前，先画出代码块的边界。同一个名字是否对应同一份变量，取决于声明所在的作用域。

## 面试速答（60 秒版）

`=` 给已经存在的变量赋值；`:=` 是短变量声明，只能在函数内部使用。它可以在同一个代码块里复用已有变量，但左边至少要有一个新的非空白变量，而且复用的变量类型要符合声明规则。

如果同名变量只存在于外层代码块，那么内层的 `:=` 通常会创建新变量，这就是变量遮蔽。内层修改 err，不代表外层 err 也跟着改变。

比如函数外层有一个 err，if 初始化语句又写 `value, err := load()`，if 里面用的是新 err。离开 if 后检查外层 err，可能仍然是 nil。

所以处理错误时，优先在拿到错误的位置直接返回或处理。如果需要更新外层状态，明确使用赋值，不要只凭变量名相同就认为它们是同一个变量。

## 知识点详解：两个 err，为什么看起来像同一个？

### 先看一个不会报编译错误的反例

```go
package main

import (
    "errors"
    "fmt"
)

func broken() error {
    var err error
    if _, err := load(); err != nil {
        fmt.Println("inner:", err)
    }
    return err
}
func load() (int, error) { return 0, errors.New("load failed") }

func main() { fmt.Println("returned:", broken()) }
```

程序会打印内部错误，但最后返回 nil。它不是错误丢失在某个库里，也不是 if 判断失效。if 初始化语句创建了一个新的 err，这个变量的范围包括后面的条件和分支。

函数开头声明的外层 err 从来没有被赋过错误，所以最后 `return err` 仍然返回它的零值。

修复也不需要复杂技巧。既然这次加载失败就该结束，直接在 if 分支里 `return err` 即可。如果业务确实要求先记录再往后执行，就应明确决定是否给外层变量赋值，以及后续还能不能继续。

### 同一代码块里的复用，又是另一种情况

假设同一层先写 `value, err := load()`，后面写 `other, err := load()`。other 是新变量，err 在同一代码块里已经声明过，因此这次可以复用 err。

如果这次左边全是当前块里已经存在的变量，就不能再靠 `:=` 声明一遍，通常会遇到“没有新变量”的编译错误，此时应该使用 `=`。

但只要再加一层花括号，或者进入 if、for 的新作用域，同名变量的判断就可能变了。[Go 短变量声明规范](https://go.dev/ref/spec#Short_variable_declarations)规定的是代码块内的重新声明，不是沿着整个函数搜索同名变量。

### 命名返回值也不能靠名字相同来保证正确

函数如果声明 `(err error)`，这个 err 是结果变量。内层可以出现同名声明，但这不会自动把错误写回结果变量。某些被遮蔽位置的裸 return 会被编译器拒绝，不能据此认为所有遮蔽错误都能被编译器发现。

更好读的写法通常是显式返回本次错误，或者给临时错误起一个能区分阶段的名字。不要为了每个调用都写成统一样子，就把真正的数据流藏起来。

本题使用 Go 的词法作用域规则，只有 Go 代码；TS/Python 的声明与绑定方式不同，不做表面翻译。

## 面试官继续追问

### 在 if 里面用 `:=` 都不安全吗？

不是。把短期变量限制在 if 里通常很好读。问题出在代码期待修改外层变量，却实际创建了内层变量。只要错误就在这个分支处理清楚，局部作用域反而可以减少误用。

### 是否可以把所有 `:=` 都改成 `=`？

这样只是把声明搬到别处，还可能扩大变量作用域。应该让变量尽量靠近使用位置，并明确哪些是新变量、哪些需要更新已有状态。统一替换符号，解决不了返回路径设计错误。

### 怎么验证这类问题？

给 load 安排一个必然失败的测试，断言调用方最后收到的错误不为 nil。再检查日志记录和返回值是不是来自同一条错误路径。静态分析可以辅助找遮蔽，但错误传播的业务预期仍要由测试验证。

## 面试速记卡

> - `=`：更新已有变量。
> - `:=`：短变量声明，同块复用时至少有一个新的非空白变量。
> - 遮蔽：外层同名变量，不等于当前块已经声明的变量。
> - 错误处理：日志打印失败，不代表错误已经向调用方传播。
> - 验证：用失败用例检查真实返回值，而不只看分支有没有执行。
