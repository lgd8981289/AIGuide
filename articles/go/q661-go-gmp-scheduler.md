# Go 的 GMP 调度模型是什么？G、M、P 如何配合运行 goroutine？

下面是一段模拟面试对话。

🧑‍💻 **面试官：** goroutine 为什么不是来一个就创建一条系统线程？

🙋‍♂️ **我：** Go 有 GMP 调度，把很多 goroutine 分配给少量线程运行。

🧑‍💻 **面试官：** G 是 goroutine，M 是线程，那 P 是 CPU 核心吗？

🙋‍♂️ **我：** P 是运行 Go 代码需要的执行资源，不是物理核心本身。

🧑‍💻 **面试官：** 如果一个 G 阻塞了，M 和 P 都必须跟着一直等吗？

> 把任务、系统线程和执行资格分开，再看不同阻塞方式会留下谁。

## 面试速答（60 秒版）

G 表示 goroutine，保存执行所需的栈和调度状态；M 表示操作系统线程；P 表示执行 Go 代码需要的运行时资源，数量受 GOMAXPROCS 控制，不能直接等同于 CPU 核数。

运行时把可运行的 G 分配给持有 P 的 M 执行。大量 G 可以排队和切换，不要求一一对应系统线程。P 有本地运行队列，调度还会涉及全局队列、工作窃取和网络轮询等机制。

阻塞要分类。channel 等待可以挂起 G，让 M 继续运行其他任务；某些阻塞系统调用则可能占住 M，但 P 可以被交给其他 M。具体过程由运行时实现决定。

所以 goroutine 能降低并发任务的组织成本，却不会让线程、内存或下游连接变成无限资源。并发很多时，仍要控制任务数量和外部系统容量。

## 知识点详解：一个 goroutine 得到 CPU 之前，要经过什么？

### G 是任务的执行记录

假设程序启动一批 goroutine，分别等待网络响应。它们不可能在单个核心上同一时刻全部执行。

运行时需要记住每个任务执行到哪里、栈在哪里、现在能不能继续。这些就是理解 G 的入口。一个 G 暂时等待，不代表必须为它保留一条一直闲着的系统线程。

不过，goroutine 也不是没有成本。它有栈和运行时记录，业务代码还可能持有大量对象。无边界地创建，仍然可能耗尽内存。[Go Runtime HACKING](https://go.dev/src/runtime/HACKING)解释了 G、M、P 的实现职责。

### M 真正由操作系统调度

CPU 最终执行的是操作系统线程上的指令。Go 运行时决定让哪个 G 在某个 M 上执行，操作系统再决定这个线程何时获得 CPU。

因此，不能把“Go 自己调度 goroutine”说成它绕开了操作系统调度。它在系统线程之上，又管理了一层更轻的任务切换。

同样，M 的数量不必与 P 一样。可能有线程正在执行阻塞调用，或者承担其他运行时工作。把两者始终画成固定的一一对应，会漏掉阻塞和重新绑定的过程。

### P 不负责变出新的 CPU

P 可以理解成运行 Go 代码所需的一组调度和运行时资源。某个 M 要执行普通 Go 代码，通常需要持有 P。

GOMAXPROCS 限制的是同时执行用户层 Go 代码所用的 P 数量，不是整个进程允许拥有多少线程，也不是 goroutine 总数。[runtime.GOMAXPROCS 文档](https://pkg.go.dev/runtime#GOMAXPROCS)还说明了默认值与运行环境的关系，不应简单记成“永远等于机器物理核数”。

假设只有两个 P，创建一万个 G，不会因此获得一万个同时执行 Go 计算的资格。对于 CPU 密集任务，增加 G 可能只是增加排队和切换。

![G 等待，不一定需要 M 陪等](https://note.lgdsunday.club/img/Q661/02-go-gmp-scheduler.webp)

### 阻塞时，分别看 G、M 和 P

| 情况              | 先看哪个对象停下来  | 需要避免的误解            |
| --------------- | ---------- | ------------------ |
| channel 等待条件未满足 | G 可以被挂起    | 不一定占住一条系统线程陪等      |
| 可由网络轮询处理的 I/O   | G 等待就绪     | 不是每个连接一个 M         |
| 阻塞系统调用          | M 可能被占用    | P 可以重新交给其他 M       |
| 长时间 CPU 计算      | G 持续消耗执行机会 | goroutine 多不等于计算更快 |

这里是机制主线，不承诺每条代码都走同一条底层路径。运行时版本、系统调用形态和 cgo 等情况，都需要具体分析。

![goroutine 多，不会扩大下游容量](https://note.lgdsunday.club/img/Q661/03-go-gmp-scheduler.webp)

### 怎样确认问题出在调度，而不是下游？

先区分 CPU 忙、G 在等待，还是大量线程被阻塞。可以结合 runtime trace、goroutine 栈和 CPU/阻塞剖析检查。

例如，所有任务都等数据库连接，就算再调大 GOMAXPROCS，也不会增加数据库连接池容量。反而可能让更多任务一起挤进队列。先找等待点，再决定调参数还是改并发入口。

## 面试官继续追问

### 工作窃取能保证任务绝不饥饿吗？

不要把某个调度策略当成应用层的确定性公平承诺。运行队列、抢占和系统负载都会影响何时执行；业务需要时限、优先级或配额，应自己定义可验证的调度规则。

### 为什么没有 TS、Python 的同名实现？

GMP 是 Go 运行时实现，JS 事件循环和 Python 协程不能直接当成它的 API 对照。跨语言比较可以帮助理解等待方式，但不能据此伪造相同的线程调度过程。

## 面试速记卡

> - G：goroutine 的执行状态和栈，不是系统线程。
> - M：由操作系统调度的线程。
> - P：执行 Go 代码需要的运行时资源，数量由 GOMAXPROCS 管理。
> - 阻塞：先区分挂起 G、占住 M，以及 P 是否能重新交接。
> - 工程判断：goroutine 不是无限资源，下游容量仍需要单独限制。
