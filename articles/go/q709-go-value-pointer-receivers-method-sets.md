# Go 值接收者和指针接收者有什么区别？方法集如何决定接口实现？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/go/q709-go-value-pointer-receivers-method-sets/) · [题库目录](../../README.md)

以下是一段用于讲解的模拟面试对话。

🧑‍💻 **面试官：** Go 的值接收者和指针接收者，主要区别是什么？

🙋‍♂️ **我：** 值接收者拿到一份副本，指针接收者可以修改原对象。

🧑‍💻 **面试官：** 那一个变量能调用指针方法，就说明它实现了相应接口吗？

🙋‍♂️ **我：** 应该可以吧，方法都能调用。

🧑‍💻 **面试官：** 为什么 `c.Inc()` 能编译，把 `c` 赋给要求 `Inc()` 的接口却不行？

> 这道题要分清两件事：编译器可以替一次方法调用取地址，但不会因此把 `T` 的方法集变成 `*T` 的方法集。

## 面试速答（60 秒版）

Go 调用方法时，值接收者拿到的是接收者值的副本；指针接收者拿到的是指针的副本，因此可以通过它修改原对象。需要修改状态、避免复制较大的结构体，或者类型内部带有不能随意复制的锁时，通常使用指针接收者。

同时还要看方法集。对于通常定义的非指针、非接口类型 `T`，`T` 的方法集只包含值接收者方法，`*T` 的方法集同时包含值接收者和指针接收者方法。接口赋值就是按这个规则检查的。

如果变量 `c` 可以取地址，写 `c.Inc()` 时，编译器可以按 `(&c).Inc()` 处理。但这只是调用上的便利，并不代表 `c` 的类型已经实现了包含 `Inc` 的接口。需要这个接口时，应传 `&c`。

## 知识点详解：能调用方法，为什么还不能赋给接口？

### 先沿着一个计数器看接收者

假设我们写一个计数器，既要增加数值，也要读取当前结果。

```go
package main

import "fmt"

type Counter struct { N int }
func (c Counter) Value() int { return c.N }
func (c *Counter) Inc() { c.N++ }

type Incrementer interface { Inc() }
var _ Incrementer = (*Counter)(nil)

func main() {
    c := Counter{}
    c.Inc()
    var task Incrementer = &c
    task.Inc()
    fmt.Println(c.Value()) // 2
}
```

这里的 `Inc` 通过指针访问同一个 Counter，所以两次调用都修改 `c.N`。如果改成值接收者，`c.N++` 增加的就只是本次调用拿到的副本。

不过，“副本”不等于深拷贝。结构体里面如果放着 slice、map 或指针，复制结构体以后，内部仍可能引用相同的数据。值接收者也可能通过这些引用修改共享内容，所以不能把它理解成自动只读。

![值复制，不等于数据全复制](https://note.lgdsunday.club/img/Q709/02-go-value-pointer-receivers-method-sets.webp)

### 方法集负责回答类型能满足什么接口

对上面的 Counter，关系很清楚。

| 类型         | 方法集               | 实现 Incrementer？ |
| ---------- | ----------------- | --------------- |
| `Counter`  | `Value()`         | 否               |
| `*Counter` | `Value()`、`Inc()` | 是               |

因此，把示例改成 `var task Incrementer = c` 会出现编译错误。我们需要保存到接口里的那个值，其类型本身满足接口约定，不能依赖某次调用现场是否恰好可以取地址。

`var _ Incrementer = (*Counter)(nil)` 是编译期检查，表示让编译器确认 `*Counter` 实现了接口。它并没有真的运行 `Inc`。nil 指针调用方法是否安全，要另外看方法有没有解引用接收者，这又是一个问题了。

[Go 规范的方法集与调用规则](https://go.dev/ref/spec#Method_sets)对这两个层面分别作了规定。

### 自动取地址也有条件

示例里的 `c` 是一个可取地址的变量，所以可以省略 `&`。但 map 元素不能取地址，假如 `items` 是 `map[string]Counter`，`items["a"].Inc()` 就不能依赖同样的简写。

如果确实要修改这个元素，可以先取出副本，修改后放回；也可以让 map 保存 `*Counter`，不过随后就要考虑这些指针是否被多个 goroutine 共享。改了存储类型，并不会顺便得到并发安全。

这也是为什么选择接收者时，不宜只看方法内部有没有赋值。类型的复制成本、身份语义、并发约束和接口使用方式，都要一起考虑。[Go FAQ 的接收者说明](https://go.dev/doc/faq#methods_on_values_or_pointers)可以作为进一步阅读。

本文讨论 Go 自身的方法集，因此使用 Go 示例；TypeScript 和 Python 没有同一套方法集与隐式取地址规则，不提供形式上的 API 翻译。

## 面试官继续追问

### 只读方法为什么也有人用指针接收者？

可能是为了避免复制大对象，也可能是类型的其他方法已经依赖同一个可变对象。尤其结构体中有 `sync.Mutex` 时，不能为了读取字段就复制一把已经使用过的锁。接收者要和类型的使用约定保持一致。

### 换成指针接收者以后，并发修改就安全了吗？

没有。指针只让多个调用能够访问同一个对象，反而更需要明确同步方式。可以用锁、原子操作或者单 goroutine 所有权来保护状态，不能把“修改的是原对象”当作“修改过程不会冲突”。

### 怎样验证自己真的理解了？

把 `Counter` 和 `*Counter` 分别赋给接口，再把调用位置换成普通变量、临时返回值和 map 元素，检查哪些能编译。运行结果和编译失败都很有用，但不要只保留能运行的一种情况。

## 面试速记卡

> - 值接收者：复制接收者值，但内部引用的数据不一定复制。
> - 指针接收者：可以修改原对象，不自动提供并发安全。
> - 方法集：`T` 含值方法，`*T` 通常同时含值方法和指针方法。
> - 调用简写：可取地址变量调用指针方法，可以隐式取地址。
> - 接口判断：按实际类型的方法集检查，不按一次调用是否成功检查。
