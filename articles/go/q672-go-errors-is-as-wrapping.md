# Go 的 errors.Is、errors.As 和错误包装怎么用？为什么不能只比较错误字符串？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/go/q672-go-errors-is-as-wrapping/) · [题库目录](../../README.md)

下面是一段模拟面试对话。

🧑‍💻 **面试官：** 你给底层错误加一句“读取配置失败”，上层还能识别原来的错误吗？

🙋‍♂️ **我：** 用 %w 包装，保留底层错误，再用 errors.Is 或 errors.As 判断。

🧑‍💻 **面试官：** 那判断是不是文件不存在，和取出 PathError 里的路径，用同一个方法吗？

🙋‍♂️ **我：** 前者是错误匹配，后者是找类型和取值。

🧑‍💻 **面试官：** 如果用了 %v，打印内容一样，为什么上层的匹配可能失效？

> 错误文字给人看，包装关系给程序判断。把文案和错误身份分开，接口才不容易被一句话改坏。

## 面试速答（60 秒版）

%w 用于在 fmt.Errorf 中保留被包装的错误关系；%v 主要格式化文字，不会仅凭输出相同就建立同样的解包关系。

errors.Is 用来判断错误树里是否存在匹配目标的错误，适合识别约定的错误条件。errors.As 则查找能够匹配目标类型的错误，并取得对应值，例如从包装错误里取出 \*fs.PathError。

直接用 == 或类型断言，通常只检查当前这一层，容易漏掉包装后的底层错误。现在还要知道多错误包装可以形成树，不能把所有情况都理解成一条单链。

工程上应选择性保留底层错误。希望调用方依赖的错误条件，要成为明确契约；不想长期暴露的内部实现细节，不应无意中全部包装成外部接口。Go 1.26 起还可以用类型参数版本 errors.AsType 简化常见类型提取。

## 知识点详解：文字外面还有一层可遍历关系

### 加一句说明，不要把原错误抹掉

假设底层返回“文件不存在”，业务层想补上“读取配置失败”。只拼接字符串，调用者可能只能根据一段文字猜原因。

包装则同时保留两部分：当前层的上下文，以及底层错误关系。这样日志更好读，程序也仍能按约定作分支。[Go 关于错误包装的官方文章](https://go.dev/blog/go1.13-errors)说明了为什么暴露包装关系也是 API 设计决定。

### Is 判断条件，As 取得类型化信息

下面是独立 Go 示例，不读真实文件，也不会依赖机器上某个路径是否存在。其他语言异常链的 API 不同，不机械翻译 Go 的 %w。

```go
package main

import (
    "errors"
    "fmt"
    "io/fs"
)

func main() {
    cause := &fs.PathError{
        Op: "open", Path: "demo.txt", Err: fs.ErrNotExist,
    }
    err := fmt.Errorf("读取配置失败: %w", cause)
    fmt.Println(errors.Is(err, fs.ErrNotExist))

    var pathErr *fs.PathError
    if errors.As(err, &pathErr) {
        fmt.Println(pathErr.Path)
    }
    // Go 1.26 及以上可使用类型参数版本。
    if typed, ok := errors.AsType[*fs.PathError](err); ok {
        fmt.Println(typed.Op)
    }
}
```

Is 回答“是不是文件不存在这一类约定条件”；As 找到 PathError 后，我们才读取它携带的路径。一个是匹配，一个是提取，不要只根据名字长度决定用哪个。

As 的 target 必须符合 API 的指针要求。上面 pathErr 本身是 \*fs.PathError，而传进去的是它的地址，好让 As 写入找到的指针。[errors 包文档](https://pkg.go.dev/errors)还描述了自定义 Is、As 方法和错误树的遍历规则。

![找错误条件，和拿错误字段不同](https://note.lgdsunday.club/img/Q672/02-go-errors-is-as-wrapping.webp)

### 为什么直接 == 和断言不够？

包装后的最外层对象通常不是原来的哨兵错误，所以 `err == fs.ErrNotExist` 未必成立。直接断言 `err.(*fs.PathError)` 也只看到外层，外层如果是包装对象，就无法取得里面的 PathError。

但不能倒过来说 == 永远不能用。明确比较当前层的某个哨兵值，是另一种范围更窄的判断。面试里要说清自己要查当前对象，还是沿包装关系查找。

### 错误可能有多个孩子

多错误包装可以让一份错误关联多个原因，匹配过程会遍历相应错误树。不要自己写一个只调用 `Unwrap() error` 的循环，就宣称覆盖全部标准错误组合。

同样，比较错误文字很脆弱。加上下文、调整语言或更换依赖，都可能改变文本。除非接口本来定义了稳定错误码，否则不要用一段可变文案作为核心分支。

![错误可能是一棵树](https://note.lgdsunday.club/img/Q672/03-go-errors-is-as-wrapping.webp)

### 包装出去，就是在暴露依赖

如果调用者已经依靠某个数据库驱动错误作分支，以后更换驱动就可能影响它。并非每个底层原因都适合成为外部契约。

可以把需要公开的条件映射成服务自己的错误类型或错误码，保留足够诊断信息，但不承诺调用方能直接依赖所有内部细节。日志里也要检查路径、SQL 或凭证是否需要脱敏。

## 面试官继续追问

### errors.Is 就一定是普通相等比较吗？

不完全是。它还支持相应自定义匹配规则。应该依赖 API 契约，而不是推断每个包装节点只会做一次 ==。

### 多加几层包装会丢失信息吗？

只要各层正确保留关系，标准匹配可以继续查找。但某一层改成纯文字格式化，就可能切断程序可遍历的关系。测试应该覆盖经过全部业务层以后的最终错误，而不只测底层函数。

## 面试速记卡

> - %w：保留错误包装关系；%v 不自动等价。
> - Is：判断约定错误条件是否匹配。
> - As：找类型并取出值；Go 1.26 起还有 AsType。
> - 范围：包装可以形成树，直接比较或断言通常只看当前层。
> - 契约：选择性暴露底层原因，不用可变文案代替稳定错误条件。
