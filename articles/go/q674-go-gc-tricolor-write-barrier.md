# Go 垃圾回收怎么工作？三色标记、写屏障和 GOGC 分别做什么？

下面是一段模拟面试对话。

🧑‍💻 **面试官：** Go GC 怎么判断哪些对象可以回收？

🙋‍♂️ **我：** 从根开始找可达对象，可以用白、灰、黑三种状态理解标记过程。

🧑‍💻 **面试官：** 标记还没结束，业务 goroutine 又改了指针，之前扫过的对象会不会多出一个没发现的孩子？

🙋‍♂️ **我：** 需要写屏障配合，不能只扫描一次就完全不管后续修改。

🧑‍💻 **面试官：** 那写屏障和停顿分别在解决什么？现在 Go 的实现还能直接用十年前的一张三色图完整代表吗？

> 三色解释“对象发现到哪一步”；写屏障保证并发修改不会把仍活着的对象藏起来。算法模型和版本实现要分开。

## 面试速答（60 秒版）

Go GC 根据可达性判断对象是否仍需保留。三色模型里，白色是本轮尚未发现，灰色是已发现但还有引用待检查，黑色是相关扫描已完成。标记结束后仍不可达的对象，才具备回收条件。

并发标记期间，业务代码仍可能修改指针。如果垃圾收集器只按旧关系扫描，就可能漏掉仍然活着的对象。写屏障在相关指针写入时记录和处理必要引用，让标记保持正确。

本文核对的 Go 实现采用混合写屏障思路，涉及被覆盖的旧引用与写入的新引用，不能只背“黑色不能指白色”就认为讲完全部实现。当前版本还有 Green Tea 等具体组织优化，三色只是理解入口。

并发 GC 也不等于没有停顿，标记启停等阶段仍需协调。性能上要一起看分配速率、存活堆、扫描工作、CPU 和停顿，不能只盯 GC 次数。

## 知识点详解：业务还在改图，GC 怎样不漏对象？

### 白色不是已经确定的垃圾

假设从根指向 A，A 再指向 B。扫描刚开始时，B 还没被发现，可以是白色；它并没有因此变成应该立即释放的垃圾。

扫描到 A 时，发现 B，就把后续扫描工作安排进去。等相关引用处理完成，再推进状态。只有一轮可达性判断完成以后，才能解释哪些对象仍然没有被保留下来。[Go GC 指南](https://go.dev/doc/gc-guide)解释了追踪式回收和成本模型。

这里的颜色是算法状态，不是在每个对象外面真的放三个颜色字段；当前实现的工作组织和位图结构也不能只凭比喻推断。

![白色，还不能直接判垃圾](https://note.lgdsunday.club/img/Q674/02-go-gc-tricolor-write-barrier.webp)

### 并发修改，让“扫过了”不代表永远不会新增引用

假设 A 已扫描完成，业务代码后来让 A 指向 B，而 B 还没被标记。如果其他能让 GC 找到 B 的路径又被移除，单看旧扫描结果就可能漏掉 B。

关键不在于出现某条箭头就必然错误，而在于业务如何改变了可达关系、收集器是否仍有足够证据发现对象。写屏障就是把必要的指针变更纳入标记协议。

因此它不是给每次字段赋值加一把普通业务锁，也不要求整个标记期间所有 goroutine 都停止工作。

![并发改引用，扫描证据也要跟上](https://note.lgdsunday.club/img/Q674/03-go-gc-tricolor-write-barrier.webp)

### 混合屏障为什么还关心旧引用？

只记住“新指针指到谁”，不足以解释完整协议。覆盖一个堆槽位时，旧引用也可能承担着让 GC 发现对象的那条路径。

本文核对的 [Go runtime mbarrier.go](https://go.dev/src/runtime/mbarrier.go)解释了混合删除与插入屏障的思路：对被覆盖引用进行保护，并结合栈扫描状态处理新引用，防止应用在堆和栈之间移动唯一引用时，把对象藏过扫描。

这是一套完整正确性条件。实际编译器会在哪些写入点生成屏障、运行时怎样批量处理，要看对应版本源码，不能把说明性伪代码当成所有平台一模一样的机器指令。

### Green Tea 改变实现细节，不取消可达性问题

Go 1.26 发布说明已经把 Green Tea 收集器列为默认启用。它涉及扫描工作与内存访问的组织优化，因此今天介绍 Go GC，不该把很早以前的执行细节写成永久现状。[Go 1.26 发布说明](https://go.dev/doc/go1.26)可核对这一版本变化。

但版本更新并不意味着“有新收集器就不需要写屏障”或“不需要考虑存活对象”。本文用三色解释必要关系，源码实验与性能分析则明确记录 Go 1.27.2，不声称复现了所有 GC 内部步骤。

### 调参数前，先看应用把多少东西留活了

高分配速率会增加工作，长期持有大切片、缓存和对象图，也会扩大存活堆和扫描负担。先减少不必要分配、检查长期引用，有时比只调 GOGC 更直接。

GOGC 影响堆增长目标与回收成本的权衡；GOMEMLIMIT 是软内存限制，不是操作系统 RSS 的绝对硬上限。调得更激进，也可能让 GC 花更多 CPU。

验证时记录负载、版本、分配、存活量、GC CPU 与尾延迟。只展示一次“GC 后内存下降”，不能说明线上已经更稳。

![对象仍被引用，GC 就不能替你忘掉](https://note.lgdsunday.club/img/Q674/04-go-gc-tricolor-write-barrier.webp)

## 面试官继续追问

### GC 能防止内存泄漏吗？

它回收不再可达的对象。对象如果仍被缓存、全局变量或未退出 goroutine 引用，即使业务已经不需要，GC 也不能替你判断意图。需要从引用与生命周期排查。

### 写屏障是否完全没有开销？

不会。它增加必要工作，但换来了并发标记的正确性条件。要结合实际写入与分配负载观察，不能从“存在屏障”直接推导某个项目一定慢。

## 面试速记卡

> - 三色：白未发现、灰待扫描、黑已完成相关扫描。
> - 白色：标记中不等于垃圾，不能提前按颜色直接回收。
> - 写屏障：把必要引用变化纳入并发标记协议。
> - 实现：混合屏障与具体扫描策略依版本核对，三色图不是全部源码。
> - 性能：并发不等于零停顿，分配、存活、CPU 与尾延迟一起看。
