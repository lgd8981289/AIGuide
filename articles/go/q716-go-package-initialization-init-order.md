# Go 的 init 按什么顺序执行？包初始化为什么不能依赖文件名？

以下是一段用于讲解的模拟面试对话。

🧑‍💻 **面试官：** Go 的 init 是在 main 之前执行吗？

🙋‍♂️ **我：** 是，包初始化变量，然后执行 init，最后进入 main。

🧑‍💻 **面试官：** 一个包有多个文件、多个 init 呢？被依赖的包又什么时候执行？

🙋‍♂️ **我：** 可以通过给文件加数字前缀控制先后。

🧑‍💻 **面试官：** 如果换了构建方式，或者隐藏的依赖没有被初始化分析识别，这个约定还可靠吗？

> 初始化顺序应当由可见依赖和明确调用表达，文件名最多是工具链的输入顺序，不能代替系统依赖设计。

## 面试速答（60 秒版）

Go 会先初始化被依赖的包，再初始化当前包。一个包里，先完成包级变量初始化，再执行 init 函数；所有相关包初始化结束后，才调用 main。

包级变量并非简单按书写顺序赋值。初始化表达式存在可识别依赖时，要先满足依赖；多个可初始化变量之间再结合声明顺序处理。多个文件的声明顺序还受文件提交给编译器的顺序影响。

常用构建工具会采用可复现的文件顺序，但业务代码不应靠文件名安排连接数据库、加载配置等关键先后关系。复杂且可能失败的准备过程，更适合显式函数调用，让错误能够返回，也方便测试。

init 适合轻量注册之类的工作，它不是一个可以随时重新调用、重试或接收参数的普通启动函数。

## 知识点详解：从 import 到 main，中间发生了什么？

### 先看一个变量依赖

```go
package main

import "fmt"

var a = b + 1
var b = 2

func init() { fmt.Println("init 1:", a, b) }
func init() { fmt.Println("init 2") }
func main() { fmt.Println("main:", a, b) }
```

a 虽然写在 b 前面，但它的初始化需要 b，所以 b 要先准备好。等两个变量初始化完成，才执行本文件按声明顺序出现的两个 init，最后进入 main。

如果把它理解成从文件第一行机械执行到底，就解释不了 a 为什么得到 3。包级声明需要经过初始化依赖分析，和函数体里逐句执行不是一回事。

[Go 包初始化规范](https://go.dev/ref/spec#Package_initialization)说明了如何挑选已经满足依赖的变量，以及多文件声明顺序从哪里来。

![变量顺序，先满足依赖](https://note.lgdsunday.club/img/Q716/02-go-package-initialization-init-order.webp)

### 包之间看依赖，不看 import 排版

假设 main 依赖 config，config 又依赖 parser，那么 parser 必须先完成初始化，config 才能接着初始化。某个被多个包引用的包，也不会因为引用了多次就重复初始化多次。

对于没有依赖关系的包，规范还有确定的选择规则，但不建议业务逻辑依赖这种相对顺序。把 import 语句挪一行，也不是表达业务启动关系的可靠方法。

`import _ "某个驱动包"` 则明确表示只需要这个包的初始化副作用，比如注册驱动。调用方没有直接使用导出标识符，初始化仍然可能发生。这个写法要少而明确，避免依赖来源藏得太深。

### 为什么不能把文件名当启动编排器？

规范鼓励构建系统按词法文件名顺序向编译器提交文件，以便可复现。但“工具通常怎样组织输入”，与“业务应该怎样表达依赖”，是两个层面。

假设 `01_config.go` 读环境配置，`02_client.go` 在 init 里连远程服务。光靠名字，读代码的人很难看出失败怎么处理，测试时也难以只运行其中一部分。构建标签、文件增删和包拆分还可能让约定继续变复杂。

可以把过程改成 `cfg, err := LoadConfig()`，成功后再 `client, err := NewClient(cfg)`。参数就表达了依赖，错误也有明确出口。init 不能返回 error，不适合把可恢复的外部故障都塞进去。

还有一层容易忽略。init 可以启动 goroutine，但这个 goroutine可能和后续初始化并发执行。不能因为包初始化本身顺序推进，就认为它启动的后台任务也自动完成了。

本题使用 Go 初始化机制，不提供不存在同等语义的 TS/Python 版本。

## 面试官继续追问

### 一个包可以有几个 init？

可以有多个，它们不能像普通函数一样被引用或显式调用。在同一文件里按出现顺序执行；跨文件需要结合编译器的文件输入顺序理解。关键启动依赖仍建议使用显式函数。

### init 和 sync.Once 能互换吗？

不能直接互换。init 属于程序包初始化阶段，Once 是运行期间控制某个动作只执行一次的同步工具。需要懒加载、并发访问或者把错误留给调用方时，应单独设计初始化 API。

### 怎样检验初始化代码没有隐藏外部副作用？

让包的普通测试不依赖真实数据库和网络，检查是否一 import 就尝试连接外部资源。对必须注册的行为写小型集成测试；配置、超时和失败处理放在显式启动层验证。

## 面试速记卡

> - 包之间：先完成依赖包，再初始化当前包。
> - 包内部：先包级变量，再 init；变量还要满足初始化依赖。
> - 文件名：工具输入顺序的约定，不是业务依赖的替代品。
> - init：不能显式调用，也不能返回 error。
> - 工程选择：可能失败、需要重试的准备工作，优先显式调用。
