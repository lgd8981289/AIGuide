# Go for range 的循环变量会共享吗？Go 1.22 前后如何理解闭包捕获？

>
> [在线阅读与配图](https://note.lgdsunday.club/go/q713-go-range-loop-variable-closures/) · [题库目录](../../README.md)

以下是一段用于讲解的模拟面试对话。

🧑‍💻 **面试官：** 在 range 循环里保存几个闭包，最后执行时会拿到什么值？

🙋‍♂️ **我：** 可能全是最后一个值，因为闭包共用了循环变量。

🧑‍💻 **面试官：** 使用 Go 1.22 之后，还是这样吗？

🙋‍♂️ **我：** 新版本已经修好了，所以不用管了。

🧑‍💻 **面试官：** 如果循环写的是 `for _, v = range values`，而不是 `:=`，结论又是什么？

> 这道题先看变量在哪里声明，再看包采用的语言版本。新循环语义解决了新声明变量的共享问题，不会替你复制所有被引用的对象。

## 面试速答（60 秒版）

从 Go 1.22 开始，对于采用新语言语义的包，`for _, v := range values` 每轮会有自己的循环变量。闭包捕获这些变量时，不再因为反复覆盖同一个 v，全部读到最后一轮的值。

不过这里有两个条件。第一，要看包的语言版本，不能只看机器安装了哪个 Go 工具链。第二，`:=` 是在循环里声明变量；如果用 `=` 给外部已有变量赋值，仍然是反复修改那个外部变量。

同时，每轮变量独立，也不意味着它们引用的数据独立。如果 values 本身装着同一个对象的指针，多轮闭包仍可能操作同一个对象。并发读写还要单独处理同步问题。

因此排查这类问题，要把语言版本、变量绑定和对象共享分成三层看。

## 知识点详解：闭包留下的是哪一个变量？

### 先不用 goroutine，避免被执行顺序干扰

很多例子一上来就启动 goroutine，输出顺序随机，反而把关键问题遮住了。我们可以先把闭包保存下来，等循环结束后按顺序执行。

```go
package main

import "fmt"

func main() {
    var fresh []func() int
    for _, v := range []int{10, 20, 30} {
        fresh = append(fresh, func() int { return v })
    }
    for _, f := range fresh { fmt.Print(f(), " ") }
    fmt.Println()

    var reused []func() int
    var v int
    for _, v = range []int{10, 20, 30} {
        reused = append(reused, func() int { return v })
    }
    for _, f := range reused { fmt.Print(f(), " ") }
    fmt.Println()
}
```

在 Go 1.22 及之后的语言语义下，第一组是 `10 20 30`，第二组是 `30 30 30`。这里没有并发，也不需要用“协程还没来得及运行”解释，差异来自被捕获的变量本身。

第二个循环沿用了外部 v，三个闭包读的就是同一份变量。语言没有理由把一次普通赋值，悄悄改成三次新声明。

### 工具链新，不代表所有包自动换语义

Go 的循环变量变化从 1.22 引入，包采用的语言版本与模块的 go 指令等设置有关。一个仍按旧语言版本编译的包，不应仅因为本机装了新编译器，就被理解成已经全面使用新规则。[官方变更说明](https://go.dev/blog/loopvar-preview)解释了兼容性安排。

因此看旧面经代码时，先找 go.mod，再看循环是声明还是赋值。没有版本信息的“必定输出三个 30”，不能直接当成当前通用答案。

![工具链版本，还不够](https://note.lgdsunday.club/img/Q713/02-go-range-loop-variable-closures.webp)

### 独立变量不等于独立对象

假设切片里连续三项都是同一个 `*Task`。每轮 p 变量可以独立，但三个 p 的值仍然是同一个地址。闭包同时执行 `p.Count++`，依然可能出现数据竞争。

range 取出的结构体通常也是值副本。写 `v.Count++` 可能只改了循环变量，并没有改到原切片元素。如果要修改原元素，可以按下标访问 `values[i]`，再判断是否需要同步。

这和旧循环变量陷阱不是同一个问题。前者在问“闭包保留了哪份变量”，后者在问“这个变量又引用或复制了什么”。[range 规范](https://go.dev/ref/spec#For_statements_with_range_clause)是判断边界的依据。

本文只演示 Go 的版本化语义，不用 TS/Python 的循环规则代替。

## 面试官继续追问

### 新版本里还需要 `v := v` 吗？

对于已经采用新语义、又使用 `:=` 声明的普通循环变量，通常不需要再为这个原因增加一层复制。但维护兼容旧版本的代码、捕获外部变量或者希望复制特定值时，要根据实际含义判断，不能机械全删。

### 把 v 当参数传给 goroutine 就全安全了吗？

传参可以把参数值交给这次调用，但如果参数是指针、map 或包含共享引用的结构体，底层数据仍可能共享。先确认值传递解决的是哪层问题，再用 `go test -race` 检查实际执行过的并发路径。

### 怎样写一份稳定的验证？

像本文一样，先把闭包延后执行，分别检查 `:=` 和 `=`。再单独增加并发版本，用同步机制等待结束，而不是靠 Sleep 猜测执行完成。版本差异测试与竞争检测也要分开记录。

## 面试速记卡

> - Go 1.22 新语义：循环中用 `:=` 声明的变量，每轮独立。
> - 外部变量：`=` 仍复用已有绑定，不因新版本自动拆开。
> - 版本：看包采用的语言语义，不只看本机 Go 版本。
> - 对象：变量独立，不代表指向的数据独立。
> - 验证：先延后执行闭包确认绑定，再单独测试并发与竞争。
