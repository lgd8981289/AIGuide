# Go 的 slice 和 array 有什么区别？append 为什么可能影响原切片？

下面是一段模拟面试对话。

🧑‍💻 **面试官：** slice 和 array 有什么区别？

🙋‍♂️ **我：** 数组长度固定，切片可以增长。

🧑‍💻 **面试官：** 把切片赋给另一个变量，是不是复制了一份数据？

🙋‍♂️ **我：** 复制的是切片描述信息，底层数组可能还是同一份。

🧑‍💻 **面试官：** 那 append 以后，到底还共享，还是已经分开？判断依据是什么？

> 先把切片画成“指向哪块数组、长度多少、容量多少”，再跟着 append 看引用有没有换地方。

## 面试速答（60 秒版）

array 是长度属于类型的数组值，赋值会复制数组元素；slice 则是对底层数组一段区间的描述，包含相关引用、长度和容量信息。切片赋值不会自动复制所有元素，所以两个切片可能共享底层数据。

append 返回一个新的切片结果。如果原来的容量足够，它可以继续使用原数组，并在长度之外、容量之内写入新增元素；如果不够，就需要新的底层数组，复制后再追加。

所以不能只看变量名不同，就认为互不影响，也不能断言 append 一定扩容。需要看本次操作的 len、cap，以及原数组是否还有其他引用。

想得到独立元素副本，可以明确分配并 copy；想限制子切片追加时复用原数组，可以用完整切片表达式限制容量。但切片中的元素如果又含引用，还要继续考虑浅复制问题。

![切片描述范围，数组保存数据](https://note.lgdsunday.club/img/Q663/01-go-slice-array-append.webp)

## 知识点详解：切片值变了，数组不一定变

### 先看赋值复制了什么

数组作为值赋值，元素会复制；如果元素本身是指针等引用性值，指向的对象当然不会因此递归复制。

切片赋值则复制描述信息。可以把它想成两张相同的范围卡，两张卡都指向同一排存储格。改一张卡指向的某个格子，另一张卡也可能看见变化。[Go 切片官方讲解](https://go.dev/blog/slices-intro)用底层数组解释了这种关系。

这不是说切片变量“完全没有按值传递”。传递和赋值复制的是切片值，只是这个值内部仍关联底层数组。修改元素和重新给切片变量赋值，要分开看。

### 容量足够时，append 可能写到别人看得见的位置

```go
package main

import "fmt"

func main() {
    base := []int{10, 20, 30, 40}
    a := base[:2]
    b := append(a, 99)
    fmt.Println(base)
    fmt.Println(a, b)

    limited := base[:2:2]
    isolated := append(limited, 77)
    fmt.Println(base)
    fmt.Println(isolated)
}
```

第一份 a 的长度为 2，但容量还能覆盖后面的数组位置。append 添加 99，会使用下一个位置，因此 base 中原本的 30 会被覆盖。

a 的长度仍是 2，它不会因为另一个变量接住了 append 结果就自动变长。但底层数组已经改变了。这正是“描述范围”和“存储内容”两层不同的意思。

![容量足够，append 写到哪一格？](https://note.lgdsunday.club/img/Q663/02-go-slice-array-append.webp)

### 限制容量，限制的是以后追加时的复用空间

`base[:2:2]` 同时把长度和容量限制为 2。再追加一个元素，现有容量不足，就需要新的底层数组。此时添加 77 不会再覆盖 base 的第三格。

不过，执行 append 之前，limited 仍然和 base 共享前两格。限制容量不等于立刻深复制。若要从一开始就分离元素存储，应明确分配目标切片并 copy。[规范中的 append 和切片表达式](https://go.dev/ref/spec#Appending_to_and_copying_slices)给出了相应保证。

这里使用 Go 原生例子，不拿 Python list 或 JS 数组的扩容实现推断 Go 的共享关系。

![限制 cap，不等于立刻复制](https://note.lgdsunday.club/img/Q663/03-go-slice-array-append.webp)

### 扩容倍率，不该背成语言保证

具体容量怎么增长，是运行时和分配器实现问题。不同长度、元素大小和版本，结果可能不同。

面试时可以解释所研究版本的策略，但不能说所有切片都永远“先翻倍、后固定倍数增长”。写业务代码更不应该依赖某个 append 后的具体 cap 数字才能正确。

还有一个相邻问题：很小的子切片仍可能引用很大的底层数组。如果长期只需要那一小段，明确复制到独立存储，有时更有利于释放原来的大数组。是否值得复制，需要结合生命周期和实际内存观察。

![切片复制后，引用元素仍可能共享](https://note.lgdsunday.club/img/Q663/04-go-slice-array-append.webp)

## 面试官继续追问

### copy 就是深复制吗？

不是。它复制元素值。元素里如果包含指针、切片或 map，相关引用仍可能共享。需要多深的独立性，要按数据结构继续处理。

### 函数里 append，为什么外面的长度没变？

参数拿到的是切片值的副本。函数里得到新的描述信息，不会自动改写调用方变量，所以通常需要返回新切片并接住。同时，本次 append 仍可能已经改变共享数组，要分别检查两层变化。

## 面试速记卡

> - array：长度属于类型，赋值复制数组元素。
> - slice：复制描述信息，底层数组仍可能共享。
> - append：容量足够可复用，容量不足改用新数组。
> - 限容量：完整切片表达式约束复用空间，不等于立即深复制。
> - 验证：同时看 len、cap、底层引用和其他持有者。
