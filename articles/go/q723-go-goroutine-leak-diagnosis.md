# Go goroutine 泄漏怎么排查？为什么它们一直等待却不会被 GC 清理？

以下是一段用于讲解的模拟面试对话。

🧑‍💻 **面试官：** Go 服务的 goroutine 数量不断上涨，可能是什么问题？

🙋‍♂️ **我：** 可能发生泄漏，需要找出没退出的 goroutine。

🧑‍💻 **面试官：** 请求早就结束了，它拿不到结果也做不了事，为什么 GC 不把它回收？

🙋‍♂️ **我：** 可能还有引用没有断开。

🧑‍💻 **面试官：** 如果它正阻塞在 channel 发送，而接收方已经离开，谁负责把它唤醒并退出？

> goroutine 结束，需要它的函数真正返回。任务失去业务意义，并不会自动变成 GC 能替你终止的对象。

## 面试速答（60 秒版）

goroutine 泄漏通常指任务已经不再需要，却因为等待条件永远无法满足，一直没有返回。比如发送结果时接收方已经退出、等待的通道没人关闭，或者 I/O 没有超时。

GC 不会根据业务意义强行终止 goroutine。阻塞的 goroutine 仍占运行时资源，它栈里可达的对象也可能继续被保留。

排查时先看 goroutine 数量是否随请求持续增加，再比较多份 goroutine profile，找到重复累积的业务栈。沿着栈检查启动位置、阻塞点和退出责任，不要只看某一时刻数量大不大。

修复通常是补取消路径、超时和资源关闭，并确认上游下游都能结束。只有创建了 context，却没有在阻塞操作处使用它，问题依然存在。

## 知识点详解：接收者走了，发送者为什么还留着？

### 先还原一条最小泄漏链路

假设一个请求启动后台查询，查询完成后往无缓冲 channel 发送结果。请求在结果产生前超时返回，接收者消失；后台任务随后走到发送语句，却再也找不到接收者。

这时查询本身可能早就做完了，真正卡住的是最后一次结果交接。只给查询 API 增加超时，不一定能解决发送位置的等待。

可以让发送同时响应取消。下面是一个受控示例，故意不安排结果接收方，而是通过取消结束发送者。

```go
package main

import (
    "context"
    "fmt"
)

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    out := make(chan int)
    done := make(chan struct{})
    go func() {
        defer close(done)
        select {
        case out <- 42:
        case <-ctx.Done():
        }
    }()
    cancel()
    <-done
    fmt.Println("worker exited")
}
```

取消分支真正位于可能卡住的操作旁边，所以这个后台任务能返回。它没有依赖 main 结束时整个进程被一起关闭。

[Go 官方管道文章](https://go.dev/blog/pipelines)解释了下游提前离开时，上游为什么可能泄漏，以及为什么 goroutine 需要自行退出。

![把取消放到真正阻塞的位置](https://note.lgdsunday.club/img/Q723/02-go-goroutine-leak-diagnosis.webp)

### 缓冲只解决有边界的交接

如果任务只发送一个结果，容量为 1 的缓冲通道可能让发送者不必等请求继续接收。但如果生产者会不断产生结果，有限缓冲最终仍可能填满。

因此不能把“给 channel 加 100 个缓冲”当成通用修复。要看总共发送多少值、下游何时可能离开、谁负责通知结束。如果这些都没有边界，增加缓冲通常只是推迟卡住。

同样，不能由接收方随手 close 通道来强制停止发送者。发送者继续发送会 panic。关闭归谁管理，和取消通知如何传播，需要分别安排。

### 排查要比较趋势和调用栈

一个连接池、后台心跳或者固定 worker 本来就可以长期存在。单次看到很多 goroutine，不足以判定泄漏。

更可靠的线索是，停止流量、等待正常任务结束后，同一业务栈仍然一批批增加。通过 goroutine profile 找到它们停在发送、接收、锁还是 I/O，再顺着业务代码追踪退出条件。

调用栈能告诉我们在哪里等待，但不一定直接告诉我们为什么无人再满足条件。还需要把请求取消、通道所有权和后台任务生命周期串起来。[runtime/pprof](https://pkg.go.dev/runtime/pprof)提供相应的栈信息入口。

### 修复之后，要验证所有分支都能收尾

正常成功只是一个分支。还应覆盖请求取消、依赖超时、提前返回、部分结果不再需要，以及服务关闭。

测试中最好给任务一个明确的完成信号，等待它返回，避免用固定 Sleep 推测已经退出。goroutine 总数可能受运行时和测试框架影响，因此不能只断言全局数量完全等于某个常数。

本文是 Go 生命周期与阻塞排查，使用 Go 代码，不提供语义不同的 TS/Python 协程翻译。

## 面试官继续追问

### context 取消后，网络调用一定会立即结束吗？

要看具体库有没有使用 context，以及底层操作是否支持中断。有些调用需要设置 deadline 或显式关闭资源。观察取消到实际退出的延迟，比只确认调用过 cancel 更有意义。

### 一个 goroutine 泄漏会不会只损失一点栈内存？

不一定。栈里可能保留大对象、连接或其他资源引用，造成更多间接保留。但也不能只凭 goroutine 数就换算损失字节，要结合 heap 和资源指标确认。

### 发生部分死锁，运行时一定会报警吗？

不一定。服务里仍有其他任务运行时，一小批业务 goroutine 永久阻塞，未必触发全程序死锁报错。持续观测和退出测试仍然需要存在。

## 面试速记卡

> - 泄漏：任务不再需要，但函数没有返回。
> - GC：不负责按业务意义终止 goroutine，栈引用还可能保留对象。
> - 定位：看趋势，再比较重复累积的业务栈。
> - 修复：取消要进入真正可能阻塞的位置。
> - 验证：成功、取消、超时和提前离开都要能收尾。
