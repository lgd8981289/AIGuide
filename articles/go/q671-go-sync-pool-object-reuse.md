# Go sync.Pool 是什么？为什么不能拿它当连接池或永久缓存？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/go/q671-go-sync-pool-object-reuse/) · [题库目录](../../README.md)

下面是一段模拟面试对话。

🧑‍💻 **面试官：** sync.Pool 可以复用对象，那我把数据库连接放进去可以吗？

🙋‍♂️ **我：** 它不保证对象一直留着，也不负责连接数量和关闭管理。

🧑‍💻 **面试官：** Put 以后，下次 Get 一定能拿回刚才那个对象吗？

🙋‍♂️ **我：** 不保证。

🧑‍💻 **面试官：** 如果拿到的是上个请求留下的 buffer，你怎样避免串数据和重复使用？

> sync.Pool 适合“没有也能重新创建”的临时对象。对象正确性不能依赖它替你保存或清理。

## 面试速答（60 秒版）

sync.Pool 用来保存和复用临时对象，减少部分高频分配与 GC 压力。它允许并发调用 Get、Put，但不保证放进去的对象什么时候被移除，也不保证下一次拿到哪一个。

因此它不是可靠缓存，不适合保存必须存在的业务状态；也不是带容量、借还和连接健康检查的资源池，不能直接替代数据库连接池。

对象取出后，要按约定重置状态，使用期间由当前使用者独占，归还后不再继续访问。大 buffer、敏感内容和对象里残留的引用，也要考虑内存保留与数据泄漏。

我会先用分配剖析确认这里确有热点，再对比复用前后的分配量、内存与延迟。小对象不一定值得池化，不能为了少一次 new 增加更多同步和管理成本。

## 知识点详解：允许丢失，为什么反而适合复用？

### 没有池中对象，也必须能正确运行

假设某个格式化函数频繁创建 bytes.Buffer。每次使用完就丢弃，可能形成稳定的分配热点，于是考虑复用。

Pool.Get 没有可用对象时，可以通过 New 创建新的实例。业务处理必须在这种情况下同样正确。只不过少了复用机会，并不应该影响结果。[sync.Pool 官方契约](https://pkg.go.dev/sync#Pool)明确允许池内对象随时被自动移除。

因此，不要用“上次我 Put 过”证明下一次一定取得。依赖必须存在的状态时，应使用真正管理生命周期的存储或容器。

### 归还以后，就不再属于这次调用

```go
package main

import (
    "bytes"
    "fmt"
    "sync"
)

var buffers = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func format(text string) string {
    buffer := buffers.Get().(*bytes.Buffer)
    buffer.Reset()
    defer buffers.Put(buffer)
    buffer.WriteString(text)
    return buffer.String()
}

func main() {
    fmt.Println(format("hello"))
}
```

这段 Go 示例使用 Buffer.String 返回字符串，再归还 buffer；没有把借来的可变字节切片直接暴露出去。[bytes.Buffer 文档](https://pkg.go.dev/bytes#Buffer)说明了 String 与 Bytes 等方法的差别。

如果返回的是借用底层存储的 Bytes，归还以后另一个调用可能修改同一块存储，原调用者手里的结果也会受影响。需要持有可变字节数据时，应在所有权转移前明确复制或改变归还方式。

其他语言的对象缓存可以比较设计思路，但不能照搬 Go Pool 的清理时机和内存模型，因此这里保留 Go 原生用法。

![归还 buffer 后，还能持有哪种结果？](https://note.lgdsunday.club/img/Q671/02-go-sync-pool-object-reuse.webp)

### Reset 不等于安全擦除，也不一定释放大内存

Reset 让 buffer 逻辑上变空，通常仍会保留底层容量，供下次写入复用。如果某次请求突然写入很大内容，这份大容量就可能被继续保留。

可以根据真实分布，为超大对象设置不归还的边界。这个边界要测量，不是所有项目都照抄同一个字节数。

同时，逻辑长度变成 0，不等于底层字节已经擦除。如果处理敏感信息，需要按系统要求设计生命周期和清理方式，不能把 Reset 当作保密承诺。

### 并发安全，不代表借出的对象也能共享修改

Pool 内部允许多方并发 Get、Put，但一个取出的 buffer 如果同时给多个 goroutine 写，仍会有数据竞争。

更危险的是同一对象重复 Put，或者归还后继续写。它可能被另一个调用取走，两个请求同时使用同一对象，问题就从性能优化变成了数据错误。

所以池化前，要把对象所有权讲清楚：何时取得、谁使用、什么时候归还、返回结果是否仍引用它。没有这条边界，节省分配反而会增加排错难度。

## 面试官继续追问

### 为什么不是连接池？

连接池需要控制总量、并发借用、等待、健康和关闭。Pool 不提供这些完整约束，自动丢掉一个连接引用也不等于正确关闭外部连接。资源池应该用有明确生命周期管理的实现。

### 怎样判断优化有没有收益？

比较真实负载下的 allocs/op、分配字节、保留内存、GC 与尾延迟，并检查大请求后的内存是否合理回落。只看到 New 次数减少，不足以证明总体更好。

## 面试速记卡

> - 用途：复用可重新创建的临时对象，减少部分分配。
> - 不保证：保存时长、取回身份和缓存命中。
> - 所有权：取出独占，重置后使用，归还后不再访问。
> - 内存：Reset 不等于释放容量或擦除敏感字节。
> - 选型：不替代连接池，是否池化以剖析和基准为依据。
