# Go Modules 的 go.mod、go.sum 和 replace 各有什么作用？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/go/q725-go-modules-go-mod-go-sum-replace/) · [题库目录](../../README.md)

以下是一段用于讲解的模拟面试对话。

🧑‍💻 **面试官：** Go 项目里的 go.mod 和 go.sum 分别负责什么？

🙋‍♂️ **我：** go.mod 写依赖，go.sum 把依赖版本锁住。

🧑‍💻 **面试官：** 如果 go.sum 里同一个模块出现多个版本，究竟使用哪个？

🙋‍♂️ **我：** 可能使用最新的一条？

🧑‍💻 **面试官：** 那模块选择发生在哪里？把本地 replace 提交以后，CI 又能不能找到你的电脑目录？

> go.mod 参与选择模块，go.sum 校验取到的内容。校验记录不是依赖选择清单，本地替换也不是可搬到任何环境的依赖地址。

## 面试速答（60 秒版）

go.mod 描述模块路径、go 版本要求以及依赖和替换等指令，参与形成模块图和构建列表。Go 通过最小版本选择，按模块图中的要求选择需要的版本，不是直接把每个依赖升级到当前最新。

go.sum 保存模块内容和 go.mod 文件的校验和，用来验证下载内容。它可能包含不止一个版本的记录，所以不能当作 npm lockfile 那样，单靠它判断这次究竟构建了哪些版本。

replace 可以把某个模块或版本替换成别的版本、分支对应版本或本地目录。替换会改变实际使用的源码，但不会自动把一个无关模块添加成依赖；本地目录还要在其他构建环境中存在。

因此依赖排查时，既看 go.mod/go.sum，也用 go list、go mod graph 查看实际构建结果，并把临时替换和发布依赖区分开。

## 知识点详解：同一个模块出现多个版本，构建到底选谁？

### 先看依赖要求怎样汇合

假设主模块要求某工具库 v1.2.0，而一个依赖要求同一模块 v1.4.0。在没有其他更高要求的前提下，最小版本选择会选择满足这些要求的 v1.4.0。

这个“最小”不是不管其他依赖，永远挑最旧版本；也不是去下载当前最新 v1.9.0。它围绕整个模块图的版本要求作确定性选择。[Go Modules 参考](https://go.dev/ref/mod#minimal-version-selection)解释了构建列表的形成。

主版本路径是另一层规则。某些 v2 模块会在模块路径里带 `/v2`，因此不能把所有不同主版本都当成同一个名字的普通小版本升级。

![最小版本选择，不是永远最旧](https://note.lgdsunday.club/img/Q725/02-go-modules-go-mod-go-sum-replace.webp)

### go.sum 为什么会留下多个条目？

解析模块图时，工具可能需要读取某些版本的 go.mod；实际下载模块源码时，又会记录模块内容的校验和。于是 go.sum 可以出现同一版本的内容记录和 `/go.mod` 记录，也可能保留多个相关版本。

这些条目说明哪些内容曾需要被验证，不是按文件顺序决定版本的命令。删除某条校验和，也不会自动把构建切到另一版本。

代码和依赖变化以后，通常用 `go mod tidy` 整理必要的要求与校验记录，再审查差异。CI 中可以采用只读模块模式检查工作区是否完整，避免构建时静默补文件掩盖缺失。

### replace 改的是使用来源

例如，某项目写了下面的配置。域名和路径只是说明结构的占位示例，不对应一个已验证可下载模块。

```text
module example.com/app

go 1.27.0

require example.com/lib v1.4.0
replace example.com/lib => ../lib
```

require 保留依赖关系，replace 则让构建使用旁边的本地 lib。这个目录需要有匹配的模块定义，也需要在 CI 的相对位置存在。

replace 只对当前主模块等适用上下文生效，不会作为一份可以强制下游采用的全局替换规则。发布库时，不能指望消费者自动沿用你本地测试时的替换目录。

多模块本地开发还可以考虑 go.work，但工作区同样需要管理边界；它也不会神奇地把本地路径变成可发布地址。

### 用实际构建列表回答问题

```bash
go list -m all
go mod graph
go mod why -m example.com/lib
go mod verify
```

前两条帮助看选中的模块和依赖关系，why 查模块为什么被需要，verify 检查下载缓存中已有内容是否被修改。它们不是同一件事。[模块工具文档](https://go.dev/ref/mod#go-mod-verify)还说明了 verify 的范围，不能把它说成发现所有恶意依赖的安全扫描。

本题以 Go 模块配置和命令解释，不需要补 TS/Python 代码。

## 面试官继续追问

### go 指令只是注释吗？

不是。它影响模块要求的 Go 版本和语言行为，现代工具链还会据此检查或选择合适工具链。toolchain 指令与 go 指令也有不同职责，应结合项目的构建策略管理。

### go.sum 可以不提交吗？

一般应随应用源码提交必要的 go.mod 和 go.sum，让构建与审查有确定依据。私有模块、校验数据库和代理配置还要按组织策略处理，不能因为下载失败就随手关闭所有校验。

### 如何发现某次提交意外依赖了本机目录？

在干净环境中按 CI 命令构建，检查 replace、go.work 以及本地未提交文件；把实际模块列表留作比对。本机编译成功，只能说明本机当前环境满足了它。

## 面试速记卡

> - go.mod：模块身份、版本要求与依赖选择规则。
> - go.sum：内容校验，不是单独决定构建版本的锁文件。
> - MVS：满足模块图版本要求，不自动追最新。
> - replace：改变源码来源，不自动补齐所有依赖关系。
> - 验证：实际构建列表、模块图和干净环境构建一起看。
