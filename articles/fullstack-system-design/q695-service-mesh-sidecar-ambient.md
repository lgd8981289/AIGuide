下面是一段模拟面试对话。

🧑‍💻 面试官：Service Mesh 解决什么问题？

🙋‍♂️ 我：给每个服务加 Sidecar，统一处理通信、安全和监控。

🧑‍💻 面试官：如果不在每个 Pod 旁边放 Sidecar，还能不能做服务网格？

🙋‍♂️ 我：那流量没人处理了吧？

🧑‍💻 面试官：Istio 的 Ambient 就没有这种逐 Pod 注入。代理放在哪里，和代理要做什么，是不是两件事？

> Service Mesh 的关键是把服务间通信能力交给基础设施管理。Sidecar 与 Ambient 改变的是代理的部署和职责分配，不是有没有代理。

## 面试速答（60 秒版）

Service Mesh 是管理服务间通信的一层基础设施，可以统一处理身份认证、流量策略和通信观测。应用仍然实现自己的业务逻辑。

以 Istio 为例，控制平面负责发现服务、生成配置和管理证书；数据平面的代理实际处理流量，不需要每个请求都绕到控制平面。

Sidecar 模式通常在每个应用 Pod 内放一个 Envoy 代理。Ambient 则把基础能力交给节点级的 ztunnel，负责四层通信安全和策略；需要 HTTP 路由等七层能力时，再为目标服务配置 waypoint。

选型要看需要哪些能力、现有平台是否兼容，以及延迟、资源和故障影响。Ambient 不等于零代理、零成本，mTLS 也不等于业务权限已经完成。对于服务很少、现有方案够用的系统，不必为了架构名词直接引入网格。

## 知识点详解：请求到底经过谁？

### 先把控制平面和数据平面分开

假设服务 A 要调用服务 B。我们希望通信能使用服务身份、应用流量规则，并留下可检查的通信指标。如果每个团队、每种语言都自己实现一遍，配置和行为就容易不一致。

网格把这类共用能力交给代理和管理组件。以 [Istio 架构文档](https://istio.io/latest/docs/ops/deployment/architecture/)为例，Istiod 负责服务发现、配置分发及证书管理；代理根据得到的配置处理请求。

因此，正常请求的数据路径并不是“A → Istiod → B”。Istiod 下发规则，数据平面执行规则，这两条路径要分别画清楚。

控制平面暂时不可用时，已有代理可能继续使用已拿到的配置，但新配置、发现信息和证书更新会受影响。不能从“不逐请求经过控制平面”推导出“控制平面永远不影响业务”。

### Sidecar 把代理放在应用旁边

在典型跨 Pod 调用里，A 的出站流量经过 A 侧代理，再到 B 侧代理，最后交给 B 应用。具体截获和绕过范围取决于部署配置，并非任何流量都无条件进入网格。

这种方式能把代理与工作负载靠近部署，代理可处理四层和七层能力。但每个 Pod 都有一份代理，也就要考虑额外资源、生命周期、升级以及应用启动和退出的协调。

这里的“放在旁边”通常指同一个 Pod 的独立容器，不是把代理代码嵌进应用进程。官方对两种模式的职责比较见 [Sidecar 与 Ambient](https://istio.io/latest/docs/overview/dataplane-modes/)。

![Sidecar 代理，跟随应用 Pod](https://note.lgdsunday.club/img/Q695/02-service-mesh-sidecar-ambient.webp)

### Ambient 将四层基础能力和七层处理拆开

Ambient 的基础组件是节点级 ztunnel。它为加入网格的工作负载处理四层流量，提供 mTLS、身份相关的四层策略和 TCP 观测能力。

如果目标只需要这些能力，可以不增加七层代理。需要按 HTTP 路径做权限或路由等处理时，再配置 waypoint。它可以由一组目标工作负载共享，不要求每个 Pod 一份。

按 [Ambient 数据路径文档](https://istio.io/latest/docs/ambient/architecture/data-plane/)，一次需要七层处理的调用，可以用下面的逻辑关系理解。

`源应用 → 源侧 ztunnel → 目标 waypoint → 目标侧 ztunnel → 目标应用`

这里画的是逻辑处理角色。ztunnel 可在工作负载网络命名空间内处理隧道，不能把简化图当成每一跳的物理网络拓扑。是否经过 waypoint 也与目标配置和来源能力有关。

所以，Ambient 去掉的是逐 Pod 的 Sidecar 注入方式，代理并没有消失。四层代理也不会仅凭 TCP 流量就自然获得完整 HTTP 语义。

![Ambient 按需增加七层处理](https://note.lgdsunday.club/img/Q695/03-service-mesh-sidecar-ambient.webp)

### mTLS 证明了服务身份，业务权限还要另外判断

假设 A 用合法的工作负载身份连接 B，且通信已加密。这能帮助 B 判断对端是谁，并保护传输过程。

但它不能直接回答“当前登录用户能否修改这条记录”。这个问题还涉及用户身份、资源归属和业务规则。你可以把部分请求级检查放到七层代理或外部授权服务，但要明确配置，不能认为开了 mTLS 就已经完成所有授权。

同样，代理重试也不能让非幂等写操作自动安全。是否允许重试、总超时是多少、重复请求怎么识别，仍然需要应用与平台共同约定。

![服务身份，与业务权限分开](https://note.lgdsunday.club/img/Q695/04-service-mesh-sidecar-ambient.webp)

### 怎么判断引入网格是否值得？

我会先列出现在真正难以统一的能力，例如跨语言的身份认证、证书轮换、流量治理或基础观测，再检查网格是否能解决，而不是先决定必须上网格。

验证时，保持相同业务负载，对比应用端延迟、错误率和代理资源；再单独模拟代理重启、证书更新、策略错误以及控制平面故障。节点级组件还要关注同节点工作负载的共同影响，waypoint 则需要容量和可用性设计。

官方不同页面的功能表可能更新不同步。例如当前概览中仍有旧的多集群限制描述，不能只抄一张表来判定所有新版本能力。落地时应固定所选版本，再核对该版本的功能状态、迁移说明和环境限制。本文核验日期为 2026-10-15，没有把官方示例性能数据当作本系统实测。

## 面试官继续追问

### Service Mesh 和 API Gateway 是同一个东西吗？

常见关注范围不同。网关通常管理进入系统或离开系统的边界流量，网格主要管理服务间通信。实际产品能力可能交叉，也可以共享代理技术，但不代表二者可以直接互换。

### 有了代理指标，还需要应用埋点吗？

需要。代理能观察通信，但不天然知道一次请求内部调用哪个业务步骤、为什么做某个决定。完整 Trace 通常还需要应用传递上下文并补充业务跨度。

### 能不能直接把所有 Sidecar 换成 Ambient？

先检查所用七层策略、扩展、协议以及网关和其他模式的互操作支持，再分批迁移。对照真实流量验证策略确实生效，并保留回退路径，不能只以“Pod 里少了一个容器”作为成功标准。本文未实际部署集群。

## 面试速记卡

> - 控制平面管理配置和证书，数据平面代理处理流量。
> - Sidecar 通常逐 Pod 部署代理，不等于嵌入应用进程。
> - Ambient 以节点级 ztunnel 提供四层能力，七层需求按需引入 waypoint。
> - 没有 Sidecar 不代表没有代理，mTLS 不代替业务授权。
> - 固定版本、检查功能兼容，并验证延迟、资源及故障影响后再选型。
