# Deep Agents 是什么？它和 LangChain、LangGraph 有什么关系？

[字节后端面试真题](../companies/bytedance-backend.md)

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/langchain/q509-deep-agents-langchain-langgraph/) · [题库目录](../../README.md)

下面是一段模拟面试对话。

🧑‍💻 面试官：已经有 LangChain 和 LangGraph，为什么还需要 Deep Agents？

🙋‍♂️ 我：它应该更适合复杂任务，可以做计划，也能调用多个 Agent。

🧑‍💻 面试官：这些能力自己用 LangGraph 也能做。Deep Agents 到底替你省了哪部分工作？

🙋‍♂️ 我：它把一些常用的 Agent 能力提前组合好了，不需要从运行循环开始搭。

🧑‍💻 面试官：那接上文件工具，就能保证任务恢复、文件持久保存，还能安全执行代码吗？

> 这道题要分清「已经组装的能力」和「仍需配置的运行条件」：名字里的 Deep，并不表示任务会自动做得更好。

## 面试速答（60 秒版）

Deep Agents 是 LangChain 生态中的一套 Agent 开发库。它在底层模型与工具调用之上，预先组合了文件处理、上下文管理、子 Agent 等能力，方便我们搭建需要持续执行多步的应用。

它和 LangChain、LangGraph 不是三套互不相关的系统。LangChain 提供模型、工具和 Agent 等开发抽象，LangGraph 提供有状态的执行能力，Deep Agents 则在这些基础上提供一套可以继续定制的运行组合。[官方概览](https://docs.langchain.com/oss/python/deepagents/overview)。

例如做研究助手，需要查资料、保存中间结果，再安排不同任务分别处理。使用 Deep Agents 可以少写一些组合代码。不过，文件保存在什么位置、任务怎样恢复、工具有什么权限，仍然需要开发者配置。

因此，选它主要看预置能力是否符合任务。流程已经很明确，需要精细控制每条分支时，可以直接设计 LangGraph；简单的工具调用任务，也不必为了名字更高级而引入更多组件。

## 知识点详解：从一次研究任务看清三层职责

### 先弄清它们分别替开发者处理什么

假设咱们要做一个研究助手：读取几份公开资料，比较产品差异，最后形成报告。

第一件事是连接模型和工具。例如模型接口怎样调用，搜索工具接受什么参数，结果怎样变成下一轮输入。这类开发工作可以使用 LangChain 的抽象。

接下来，任务可能持续很久。应用需要保存进度，控制下一步进入哪个节点，在需要时等待人工确认。这是运行时的问题，可以由 LangGraph 承担。不过，能否真正跨进程恢复，还取决于检查点、存储和部署配置。

Deep Agents 在这些基础上，进一步提供一套已经组合的 Agent。我们不是先画完所有执行分支，而是给它目标和可用能力，让它在运行过程中继续判断。

所以，比较时应该问：“这次需要自己设计哪些行为，哪些行为可以接受库已经提供的做法？”它们不是按简单、中等、复杂排成三个互斥等级。

### 文件工具解决的是信息如何放，不是自动获得一块安全磁盘

研究中遇到很长的搜索结果，可以把内容放到文件后端，再按需要读取。模型当轮输入不必一直塞着全部原文。

但是，文件路径指向哪里，要看后端配置。它可能对应任务状态中的虚拟文件，也可能连接持久存储或实际文件系统。[官方后端说明](https://docs.langchain.com/oss/python/deepagents/backends)。

假设前一轮写入了“资料摘要”，下一轮确实能够读取，不代表服务重启以后仍然能找到它。还要检查：数据由谁保存，是否跨任务共享，是否可能被另一位用户读取。

执行命令又是另一项能力。能够读写文件，并不等于已经具备沙箱、网络限制和系统级权限隔离。把这几件事混在一起，很容易让 Demo 的行为被误认为生产保证。

![文件接口相同，保存范围不同](https://note.lgdsunday.club/img/Q509/02-file-backends.webp)

### 子 Agent 的价值，是把独立工作交出去

如果报告需要分别分析产品 A、产品 B，可以让两个子任务各自读取相关材料，再把必要结果交回主 Agent。

子 Agent 可以在相对独立的上下文中处理工作，减少主 Agent 需要携带的过程信息。[子 Agent 文档](https://docs.langchain.com/oss/python/deepagents/subagents)。但“有两个子 Agent”不自动说明它们会同时执行，也不自动保证分析可靠。

主 Agent 仍然要检查结果能否使用。例如子任务只返回“产品 A 更便宜”，却没有价格条件和来源，后面的报告依然缺证据。我们需要提前规定交付内容，如结论、依据和未确认的问题。

任务计划也应按版本和配置理解。当前文档将 planning、skills 列为可选扩展，不能把“每次都会先生成完整计划”当成固定行为。

![子任务交回什么，主任务才能继续](https://note.lgdsunday.club/img/Q509/03-subagent-handoff.webp)

### 判断它值不值得用，要和较小的方案比较

可以先准备一批固定研究任务，包括资料缺失、来源互相矛盾、中途暂停和需要用户补充条件的情况。

保持模型和工具条件尽量一致，比较一个基础 Agent 与增加文件、子任务等能力后的方案。除了报告能否完成，还要检查必要来源有没有被保留，调用次数和执行成本是否增加。

如果子任务返回内容需要主 Agent 重新检查一遍，任务反而更慢，就要重新看分工方式。预置能力减少的是搭建工作；任务质量还得由结果证明。

## 面试官继续追问

### 已经保存了文件，为什么还需要检查点？

文件通常保存内容，例如资料和报告草稿；检查点保存任务执行状态，例如当前消息、进度和等待中的动作。

恢复任务时，这两类信息需要对得上。只拿到报告文件，却不知道它属于哪次执行、已经完成到哪里，仍然可能重复工作。

### 可以把自己的工具直接交给它吗？

可以接入，但工具描述不能替代应用授权。

例如查询内部资料时，工具执行层仍应检查用户身份和可访问范围；写入或外发报告时，可以增加人工审批。把工具交给 Agent，只是允许它提出调用，不是让它决定所有权限。

### 怎么确定子 Agent 没有白白增加成本？

让同一批任务分别使用和不使用子 Agent，检查结果、耗时和工具轨迹。还可以观察子任务是否真正减少了主任务的上下文，还是只把同样的内容换个地方重复一遍。

## 面试速记卡

> - Deep Agents：在 LangChain、LangGraph 基础上组合常用 Agent 能力。
> - 层次关系：开发抽象、执行运行时与预置 Agent 各有职责。
> - 文件后端：读写接口相似，保存范围和持久性可能不同。
> - 子 Agent：帮助分工，不自动保证并行或正确。
> - 选型依据：能省多少搭建工作，以及固定任务上是否有实际收益。
