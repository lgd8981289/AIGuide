# LangGraph 的 sync、async、exit 持久化模式有什么区别？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/langchain/q701-langgraph-durability-sync-async-exit/) · [题库目录](../../README.md)

*下面是一段用于讲题的模拟面试对话。*

🧑‍💻 面试官：LangGraph 配了 Checkpointer，进程突然退出后就一定能从最新一步接着执行吗？

🙋‍♂️ 我：需要看状态是否已经写入持久化存储。

🧑‍💻 面试官：那 `sync`、`async` 和 `exit`，具体差在哪个时间点？

🙋‍♂️ 我：差在什么时候等待检查点写入。同步模式会在进入下一步前等保存完成，异步模式让保存与下一步执行重叠。

🧑‍💻 面试官：如果节点里已经调用了退款接口，但检查点还没保存，恢复时会不会再退一次？换成 `sync` 能彻底解决吗？

> 这道题要沿时间线看两件事：检查点什么时候保存，外部动作又是什么时候真正发生的。

## 面试速答（60 秒版）

LangGraph 的三种持久化模式，主要是在检查点的保存时机上做取舍，需要先给图配置 Checkpointer。

`sync` 会等本步检查点保存完成，再进入下一步。`async` 在下一步执行的同时保存前一步结果，减少等待，但进程恰好在写入完成前崩溃，就可能丢掉最近的进度。

`exit` 在本次图执行退出时保存，包括正常结束、执行报错和人工中断；它不在中间每一步都保存，所以运行过程中进程崩溃，不能指望从最新中间步骤恢复。

实际选择时，要看重复计算能否接受、状态写入的开销，以及任务的重要程度。不过，即使用了 `sync`，它也只是让图状态更及时地保存，不能把远端付款和本地检查点变成同一笔事务。写操作依然需要业务幂等和结果核对。

## 知识点详解：把“节点做完”和“状态存好”分开看

### 为什么有了 Checkpointer，还会有恢复差异？

假设一条图按顺序执行“读取资料 → 整理结论 → 生成回复”。整理节点已经完成时，它的结果先出现在当前运行进程中。接下来，还要交给 Checkpointer 写入存储。

如果进程在这段时间消失，内存里的结果也会一起消失。恢复时能读到什么，要以实际保存成功的内容为准，不能以日志里那句“节点完成”为准。

LangGraph 按 super-step 推进执行。同一步里可以有并行节点，因此“每一步保存”也不能机械理解成每执行一行代码就保存。检查点、节点写入与恢复的关系，可以结合[官方 Checkpointer 说明](https://docs.langchain.com/oss/python/langgraph/checkpointers)理解。

### 三种模式，改变的是保存与下一步的先后关系

`sync` 的顺序比较直观。本步产生状态更新，等待保存，然后开始下一步。存储慢时，这段等待会体现在任务延迟里。

`async` 会把这两件事重叠起来。一边保存本步，一边执行下一步。假设下一步正在组织模型输入，上一步的写入仍在进行，此时进程崩溃，就要检查最后成功保存的位置，而不是默认进度完整。

`exit` 则把中间保存的成本省下来，到本次执行退出时再保存。这里的“退出”包含受控的报错和人工中断，不等于只在成功时保存；但直接杀掉进程、机器掉电，并不是一个能可靠完成保存的受控退出。

[JavaScript 官方文档](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)给出了相同的三种模式。别把它们当成数据库的三种事务隔离级别，它们描述的是图执行期间的持久化时机。

### 调用入口怎样设置？

下面是调用片段，前提是 `graph` 已经编译并配置 Checkpointer。Python 的 `durability` 是执行方法参数，TypeScript 则放在调用配置中，两边不要照着名字机械翻译。

#### TypeScript

```ts
await graph.invoke(input, {
  configurable: { thread_id: "task-1" },
  durability: "sync",
});
```

#### Python

```python
graph.invoke(
    inputs,
    {"configurable": {"thread_id": "task-1"}},
    durability="sync",
)
```

本次用 JS LangGraph 1.5.0、Python LangGraph 1.2.15，给同一份简单图分别设置三种模式，验证了正常运行结果与最终检查点。这个实验没有模拟断电，也没有测试远端支付，不能把它当成故障恢复的完整验收。

### sync 为什么仍然挡不住重复退款？

再看面试官最后的问题。假设节点先请求退款，远端成功后，节点还没来得及返回状态，进程就退出了。

这时根本还没有“本步成功结果已经保存”这件事。恢复后再次执行节点，仍可能再次请求退款。`sync` 再认真地等待，也不能等待一个尚未产生的节点结果。

因此，退款服务应该接受稳定的业务请求标识，重复请求返回同一次处理结果；遇到“请求超时，不知道是否成功”，先查询远端记录，再决定是否重试。图检查点记录执行进度，支付系统记录真实资金变化，两者要配合，但不能互相冒充。

![远端已退款，本地还没记下来](https://note.lgdsunday.club/img/Q701/03-external-action-gap.webp)

### 上线前应该怎么验证？

至少把中断位置放在“节点完成前、检查点写入期间、下一步开始后”分别测试。记录恢复位置、是否重复计算，以及外部动作是否重复执行，再比较保存延迟。

还要确认使用的是什么存储。`MemorySaver` 或 `InMemorySaver` 方便本地实验，但同一个进程里的内存保存，不代表进程重启以后数据还在。生产恢复要依靠真实持久化存储与对应的运维保障。

## 面试官继续追问

### 只要追求稳定，就全部用 sync 吗？

先看状态大小、写入频率、存储延迟和任务恢复要求。可重复计算的低风险步骤未必值得每步等待；高价值进度更适合及时落盘。选择要基于实测，不能承诺某个模式必然快多少。

### exit 遇到人工审批中断，会保存吗？

会，官方把人工中断列为退出保存的情况。但业务数据依然要核对，审批时的身份也要重新验证；这不意味着整个运行过程都已经逐步保存。

### 三种模式能代替长期记忆吗？

不能。它们解决当前图状态何时保存。跨会话要记什么、怎样检索、保留多久，是另一组设计问题。

## 面试速记卡

> - sync：先保存本步检查点，再进入下一步。
> - async：保存与下一步执行重叠，崩溃时最近进度可能尚未落盘。
> - exit：本次执行退出时保存，不提供逐步保存的中途恢复能力。
> - 持久化模式不等于数据库事务，也不保证外部动作只执行一次。
> - 内存 Checkpointer 适合实验，进程重启恢复需要真实持久化存储。
