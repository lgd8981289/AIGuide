# LangMem 是什么？Agent 的记忆应该同步写入，还是后台整理？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/langchain/q505-langmem-hot-path-background-memory/) · [题库目录](../../README.md)

*下面是一段教学模拟，代码助手为假设场景。*

🧑‍💻 面试官：“用户刚说这个项目以后用 Python，你什么时候写入记忆？”

🙋‍♂️ 我：“放到后台整理，回答就不用等了。”

🧑‍💻 面试官：“用户马上又问一个代码问题，后台还没完成，怎么办？”

🙋‍♂️ 我：“当前会话先保留这条要求，让下一轮按 Python 回答。”

🧑‍💻 面试官：“用户换个会话呢？早先那项 TypeScript 整理任务最后才完成呢？服务重启后，还有谁继续写？”

> 一条要求什么时候生效、何时对新会话可见、晚到结果是否仍有效，需要分别说明。

## 面试速答（60 秒版）

LangMem 是帮助 Agent 整理和管理记忆的工具库，可以从交互中提取信息，并结合存储供后续使用。应用仍需决定写入时机和失败处理。

请求内写入，把整理或存储放进当前请求；回答前等待完成，就能确认结果，也会增加等待。后台整理允许先回答，再处理长期记忆，但新会话可能暂时读到旧内容，还要处理失败和乱序。

我会让马上影响行为的要求先进入当前任务状态。跨会话必须立即生效的明确设置，确认持久化后再告知保存成功；可以延后的提炼和整理放到后台。

后台结果要关联用户、项目、来源版本和任务标识，在提交时原子地检查有效性，避免旧结果覆盖或重复写入。任务不能丢时，还需要持久任务记录、重试和恢复。函数用了 async，并不能说明这些问题已经解决。

![请求内写入需要等待确认，后台整理先让当前状态生效，再完成长期存储](https://note.lgdsunday.club/img/Q505/01-langmem-overview.webp)

## 沿着一条项目偏好，拆开记忆写入的全过程

### LangMem 参与了哪一段工作？

假设咱们做了一个代码助手。它需要从对话中整理用户偏好和项目习惯，在后续回答前读取相关记录。

可以先把这个过程拆开。应用接收对话，记忆管理组件从中提取或更新信息，存储保存结果；下一次请求再选择相关记录，放进模型输入。LangMem 可以参与信息整理，并通过相应集成与存储配合。[官方概念指南](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)介绍了这些职责及记忆形成的时机。

有了这个边界，再问“同步还是后台”才有明确对象。需要安排的工作可能是模型提炼一段对话，也可能是保存一个用户明确指定的字段。这两项工作的成本与失败影响不同。

本文只讨论写入时机，不展开记忆检索算法。接下来始终用同一个假设例子，用户将项目 A 的示例语言从 TypeScript 改为 Python。

### 如果回答前写入，用户到底在等什么？

先假设应用这样处理请求。收到新要求，调用模型整理记忆，写入存储，确认成功，再回答用户。

用户等待时间里包含整理和存储这两段工作。把调用改成异步函数，可以让执行环境在等待时处理其他工作；如果当前请求仍然 `await` 整理和写入完成，用户还是要等。

因此，请求内写入描述的是业务执行位置。代码是否使用异步 API，是另一件事。图中的上方路线会等待写入确认，再向用户发出回答。

这条路线适合需要确认保存结果的操作。例如用户在设置界面把项目 A 的语言切为 Python，应用可以直接保存结构化字段，等存储确认后显示“已保存”。明确字段通常不必再让模型猜一次用户想设置什么。

如果写入失败，系统仍可在本轮按 Python 回答，但不能宣称设置已经长期保存。回答是否继续、界面如何提示，都要与产品承诺一致。

### 先回答再整理，下一轮为什么仍可能用错语言？

后台路线先把新要求放进当前会话状态，生成回答，再安排长期整理。当前会话继续时，应用把这个有效要求补入模型输入，就可以遵守 Python 的要求。

但长期存储可能仍然是 TypeScript。用户这时开一个新会话，若应用只读取旧记忆，新请求就可能又使用 TypeScript。

![同一用户的当前会话已使用 Python，后台未完成时新会话仍可能读到旧记录](https://note.lgdsunday.club/img/Q505/02-immediate-persistent.webp)

这张图比较的是同一用户、同一项目在不同会话的可见内容。它说明当前状态生效与长期存储更新之间存在时间差，并不意味着换会话必然失效。若新请求还能读取权威设置或最新要求记录，应用就能补上这段差异。

咱们先根据承诺选择路线。

| 信息和承诺                      | 写入安排                     | 怎样确认        |
| -------------------------- | ------------------------ | ----------- |
| 本轮代码用 Python               | 先保留当前任务要求并带进输入           | 当前回答遵守要求    |
| 项目 A 以后都用 Python，新会话也应立即生效 | 保存项目设置或权威要求记录，新请求按同一范围读取 | 确认持久化与读取可见性 |
| 从多次互动中提炼讲解习惯               | 允许后台整理，并保留适用范围与来源        | 整理完成后检查有效内容 |

**同一个应用可以同时采用这些安排。** 后台模型整理没有完成，也不妨碍应用先保存一项明确设置。读取时若设置与旧记忆冲突，就要优先遵守有效的明确要求，并安排旧记录更新。

### 两项后台任务，为什么后完成的反而更旧？

现在把时间继续往后推。假设用户先说“项目 A 用 TypeScript”，接着改成“项目 A 用 Python”。应用分别接收为来源版本 v1 和 v2，并触发任务 J1、J2。版本按同一用户、同一项目、同一偏好字段的权威更新顺序分配。

J1 整理得慢，J2 整理得快。J2 先写入 Python，J1 随后才交回 TypeScript。如果存储按任务完成顺序直接覆盖，偏好就被改回去了。

![旧的 TypeScript 任务晚到，版本检查阻止其覆盖同一项目已更新的 Python 偏好](https://note.lgdsunday.club/img/Q505/03-out-of-order-write.webp)

这张图先展示失败条件，再提示版本检查。下面把检查具体展开。应用可以保留这样的来源与结果记录，这是本文的设计示例，不是 LangMem 的默认协议。

| 记录     | 需要明确的内容                            |
| ------ | ---------------------------------- |
| 权威要求   | 用户 U、项目 A、示例语言，当前来源版本 v2，值为 Python |
| 任务 J1  | 从 v1 生成，候选值 TypeScript             |
| 任务 J2  | 从 v2 生成，候选值 Python                 |
| 长期整理结果 | 已采用哪个来源版本，来源消息在哪里                  |

这里比较的版本表示用户要求的新旧。它不能由整理任务完成时间、模型生成时间或哪项任务最后返回来代替。项目 B 的偏好也不能拿来覆盖项目 A。

### 比较版本以后再写，为什么还不够？

假设 J1 提交前查到当前还是 v1，于是准备写入。就在查询和写入之间，用户又更新到了 v2。如果 J1 仍然照刚才的查询结果写，检查就白做了。

需要把有效性检查和提交放进同一项原子操作。本文假设整理先返回候选结果，由应用控制最后提交，来源与结果可以由同一业务事务协调。事务里锁定对应的权威记录，检查来源版本与当前版本一致、来源没有撤销，再更新结果并登记任务已应用。用户要求的更新也要遵守同一套并发规则。

如果记忆组件在内部直接写存储，就要在实际提交层落实检查。若来源与结果分属不同存储，也要设计相应的一致性方案，不能只把两步包进一个函数，就宣称提交是原子的。

![检查当前来源版本、提交结果及登记已应用作为同一项原子操作，v1 旧结果在当前 v2 时被拒绝](https://note.lgdsunday.club/img/Q505/04-atomic-commit-pilot.webp)

图中闸门处理的是“现在还能不能采用这份结果”。当当前来源已经是 v2，J1 的 v1 结果直接过期；不能因为 J1 完成得晚，就改写当前偏好。过期任务可以跳过，也可以基于最新来源重新整理。

再考虑重试。J2 可能已经写成功，只是确认消息在网络中丢失了。应用再次执行 J2 时，应通过稳定任务标识和已应用记录识别重复提交，避免重复追加同一条记忆。这项检查也要与写入一致，不能先写完再随意登记。

以上规则针对单个偏好字段。若一次整理会修改整份用户资料，还需要明确各字段版本或合并规则。只在整份记录上标一个“最后更新时间”，往往不足以判断每个字段是否还适用。

### 延迟整理能减少次数，能否保证任务不会丢？

用户连续发消息时，每条都立即整理，可能反复处理相似内容。LangMem 的 `ReflectionExecutor` 可以按会话延后处理，新的提交会取消并替换尚待处理的旧任务。这样可以等待一段交互趋于稳定再整理。[官方延迟处理指南](https://langchain-ai.github.io/langmem/guides/delayed_processing/)给出了这一用法。

这里有两个条件需要说明。应用要提供正确的会话标识，并为最新任务传入需要整理的对话内容。推迟执行本身，不会替应用补全没有提交的历史。也不能把取消待执行任务理解成已经撤销一笔完成的写入。相关行为可以对照 [ReflectionExecutor 源码](https://github.com/langchain-ai/langmem/blob/main/src/langmem/reflection.py)。

延迟处理解决了部分重复工作，可靠恢复还需要另外设计。指南明确提醒，本地线程会受到服务进程生命周期影响，serverless 场景应采用相应远程执行方式。一次本地提交返回，不足以证明任务已经持久保存。

如果业务允许少量整理失败，可以记录错误，并在下一次交互重新整理。如果产品承诺任务不能丢，就要持久保存任务及来源，让其他执行实例能在失败后接着处理。

![持久任务记录由工作进程读取，失败后重试，写入成功再确认；服务重启后仍可恢复](https://note.lgdsunday.club/img/Q505/05-durable-work-pilot-v4.webp)

沿图读完整个过程。应用先确认任务记录已经保存，工作进程读取来源并整理，经过版本检查后写入，再把任务标记为完成。工作进程退出，未完成记录仍然存在，可以被重新领取。重试仍要经过上一节的过期与重复提交检查。

若接收要求和保存任务必须一起成功，可以通过同一事务登记要求与待处理记录，再由后台领取。这是可靠任务的一种应用设计；采用远程执行器时，也要核对实际服务提供的持久化、重试和恢复保证。

### 什么时候可以告诉用户“已经记住了”？

“已提交”“处理中”“已写入”和“失败”分别对应不同进度。排进队列只说明接下来准备做，后台结果真正提交成功后，才适合显示长期保存完成。

要验证这套设计，可以固定同一用户、同一项目的要求，刻意改变任务执行条件。

| 测试变化              | 要观察的结果                 |
| ----------------- | ---------------------- |
| 后台还没完成，立即继续当前会话   | 新要求已经进入本轮输入            |
| 立即开启新会话           | 按承诺读到最新设置，或准确呈现尚未保存状态  |
| J2 先完成，J1 后完成     | v1 不覆盖 v2              |
| 写入成功后确认丢失，再次执行 J2 | 不重复追加或回退状态             |
| 服务在处理中重启          | 按选定恢复方案继续，不能把未完成显示为已保存 |
| 用户撤销或删除要求         | 旧任务重试不能重新启用它           |

这些是验证目标，本文没有运行真实模型、远程 SDK 或生产故障实验。实际还要分别记录回答耗时与长期记忆可见延迟，避免只看当前请求变快，就忽略后续读取是否正确。

## 面试官继续追问

### 所有记忆都放后台，是不是就最好？

先看哪些要求必须立即影响下一步。当前任务约束先进本轮状态；跨会话立即可见的设置确认持久化；允许延后的信息提炼进入后台。写入安排要符合具体承诺。

### 用户删了一条偏好，为什么旧任务还能写回来？

物理删除结果记录后，旧任务手里可能还留着原始来源。删除或撤销也要更新权威版本与有效性状态；提交时检查撤销标记。否则旧任务重试会重新生成并写入这条偏好。

### 已经做了持久队列，还需要版本检查吗？

需要。队列帮助任务恢复执行，不保证结果仍符合当前要求。并发、重试和处理速度差异仍可能让旧任务晚到，所以恢复后的提交也要检查来源版本、范围和重复执行。

## 面试速记卡

> - LangMem 参与信息提取与记忆管理，执行承诺由应用定义。
> - 请求内是否等待写入完成，决定用户是否承担这段耗时。
> - 当前状态生效与新会话可见分别检查。
> - 明确设置可以直接持久化，信息提炼可以延后整理。
> - 来源版本按同一范围的权威更新分配，完成时间不能代替它。
> - 检查有效性、写入与登记已应用，需要一致的原子提交规则。
> - 延迟整理控制执行时机，可靠恢复还要核对持久化与重试。
> - 删除、撤销和重试同样经过有效性检查。
