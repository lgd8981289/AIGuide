# LLMLingua 是什么？提示词压缩和对话摘要有什么区别？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/llm/q506-llmlingua-prompt-compression-vs-summary/) · [题库目录](../../README.md)

*下面是一段模拟面试追问。*

🧑‍💻 面试官：一份输入太长，你怎样减少 Token？

🙋‍♂️ 我：先让模型总结一下，再给后面的模型。

🧑‍💻 面试官：如果原文写“只修改测试，不修改生产配置”，摘要漏了“不修改”呢？

🙋‍♂️ 我：要保留关键约束。

🧑‍💻 面试官：LLMLingua 也能压缩提示词。它跟摘要一样吗？少了 Token，就一定更快、效果不变吗？

> 压缩不只是把文字变短，还要检查：后面的模型是否仍然理解了任务、条件和证据。

## 面试速答（60 秒版）

LLMLingua 是一组提示词压缩方法，目标是在减少输入 Token 的同时，尽量保留后续模型完成任务所需要的信息。

它和对话摘要不能简单画等号。摘要通常把原文重新组织成一段更短的表达；提示词压缩还可以通过选择、删减原始内容来控制输入长度。不同版本的 LLMLingua，具体方法也不一样。[官方项目](https://github.com/microsoft/LLMLingua)。

实际使用时，要先确定哪些部分允许压缩。任务目标、否定条件、关键数字和代码标识等，不能因为整体文本变短就被当成可随意删掉的内容。

最后要测整个处理过程：压缩花了多少时间，目标模型实际接收了多少 Token，答案和行为有没有变化。Token 减少不等于没有损失，也不保证整条链路更快或更便宜。

![区分重表达与选删减，强调各版本机制不同](https://note.lgdsunday.club/img/Q506/01-compression-overview.webp)

## 知识点详解：少了一半文字，为什么不一定更好？

### 摘要和压缩，在做什么？

假设输入是一段较长的排查记录，包含操作要求、日志和讨论过程。

摘要会尝试用新的表达概括重点。它可能把多轮讨论整理成“问题原因、已做检查、下一步建议”。读者更容易看懂，但原来的措辞和细节也可能被改变。

选择式压缩则可能保留部分原始内容，删掉被判断为不重要的部分。压缩结果未必像一篇通顺的摘要，它主要是交给后续模型使用。

两者的边界并不是绝对的。“压缩”可以作为更广义的目标，摘要也是减少输入的一种办法。但不能把 LLMLingua 的不同方法都解释成“调用另一个模型写摘要”。

原始 LLMLingua 研究使用较小语言模型参与预算控制与逐步压缩。LLMLingua-2 则采用了经过训练的 Token 分类方法。具体使用哪个版本，会影响依赖、适用内容与执行开销。[原始论文](https://arxiv.org/abs/2310.05736)、[项目版本说明](https://github.com/microsoft/LLMLingua)。

### 最怕丢掉的，不一定是最长的段落

继续假设任务要求是：

> 只修改测试。不要修改生产配置。超时阈值保留为 30 秒。

这是手写的教学例子，不是 LLMLingua 的实际输出。

如果压缩后变成“修改测试、生产配置，超时 30 秒”，字数确实少了，但“不修改”的限制丢了。后续模型可能做出相反操作。

类似地，日志里的日期、金额、版本号，代码中的函数名、参数名，都可能很短，却直接决定答案。

因此，不能只看一段文本是否重复、是否占了很多篇幅。还要看其中是否包含任务必须遵守的条件。

![展示否定丢失如何反转行为，独立于一般压缩概念](https://note.lgdsunday.club/img/Q506/02-negation-loss.webp)

### 可以先分区，再决定压缩什么

我们可以把输入按用途分开：

| 输入部分         | 一种可采用的处理方式   | 原因         |
| ------------ | ------------ | ---------- |
| 当前目标与必须遵守的约束 | 尽量保留原文，单独核对  | 丢失条件可能改变行为 |
| 重复解释与较长背景    | 尝试摘要或选择式压缩   | 有机会减少重复内容  |
| 原始证据、日志与代码   | 按问题选择片段，保留出处 | 后续需要核对具体内容 |

这只是设计建议，不是 LLMLingua 自动识别所有安全边界的保证。

如果系统能够明确排除某些区域，就不必把全部输入一次交给压缩器。压缩后的材料也要与当前目标一起重新检查，看看关系和条件是否还清楚。

当任务要引用原文，或要求逐字分析时，不能只保留摘要。应该留下原文位置，并在需要时回查。

### 压缩以后，目标模型究竟拿到了什么？

系统保存着原始资料，不代表目标模型还能看到它。

如果后续请求只发送压缩文本，目标模型只能依据这段内容回答。除非另外提供检索或读取工具，它不会自动恢复被删除的部分。

所以，排查压缩问题时，要保存压缩前内容、压缩结果与实际发送给目标模型的输入。不能只看压缩器输出的统计值。

如果压缩结果还保留了来源与范围，却在输入拼装时被丢掉，也会造成错误。这是整条输入链路的问题，不一定全由压缩算法引起。

### 该怎样验证收益？

准备同一批任务，让原始输入和压缩输入分别完成。

先看目标是否完成，否定条件是否遵守，数字、标识和证据是否准确。再看目标模型的实际 Token 数，以及压缩步骤与后续生成加起来的耗时和费用。

目标模型使用自己的分词方式，压缩器报告的比例不一定等于最终请求的比例。

如果任务本来不长，压缩计算可能比节省的成本更多。不能拿某个论文实验中的压缩倍率，直接当成自己系统的收益。

## 面试官继续追问

### 压缩比例是不是越高越好？

不是。比例提高，通常意味着后续模型能看到的信息更少。

要在固定任务上检查质量，再决定允许的压缩范围。高风险约束和精确证据，应单独设检查要求。

### 中文、代码和自然语言可以用同一套配置吗？

不能默认可以。使用的模型、训练数据与任务类型会影响效果。

至少要分别测试中文材料、代码标识和混合输入，不能只因为英文说明能压缩，就推断所有输入都一样。

### TypeScript 项目怎样接入 LLMLingua？

LLMLingua 官方示例主要使用 Python 实现。如果现有应用使用 TypeScript，可以把压缩放到独立的 Python 服务中，由应用提交允许压缩的内容，再读取处理结果。

这样还要计入跨服务请求的耗时，并处理超时或服务不可用。压缩失败时是否回退原始输入，要先检查目标模型的输入预算，不能直接把过长原文继续发送。

## 面试速记卡

> - LLMLingua：提示词压缩方法，不是一个固定的摘要 API。
> - 摘要与删减：前者重新表达，后者可能保留选择后的原始内容。
> - 保护内容：目标、否定条件、数字、标识与证据优先核对。
> - 真实输入：保存原文、压缩结果和目标模型实际收到的内容。
> - 收益验证：任务质量、实际 Token、端到端耗时与费用一起看。
