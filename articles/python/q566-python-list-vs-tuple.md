# Python 的 list 和 tuple 有什么区别？什么情况下应该用元组？

*下面是模拟面试对话，用来讲解本题，不是真实面经。*

🧑‍💻 面试官：Python 的列表和元组有什么区别？

🙋‍♂️ 我：列表可以修改，元组不能修改。

🧑‍💻 面试官：那 tuple 里放了一个 list，这个 list 也不能改吗？

🙋‍♂️ 我：它自己的内容应该还能改。

🧑‍💻 面试官：所以你说的“不能改”到底限制了哪一层？接口返回数据时，又该怎么选？

> 这道题要看清容器保存了哪些成员，以及调用方有没有权利替换这些成员。元组的限制不会自动传到内部对象。

## 面试速答（60 秒版）

list 和 tuple 都是有顺序的序列，可以按下标读取，也可以遍历。主要区别是，列表允许修改自己的成员位置和数量，元组创建以后，这些成员引用就固定下来了。

因此，任务不断追加、删除数据时，列表通常更自然。几个位置含义固定的数据，比如一对坐标，可以用元组表达。

但是，元组里如果保存了一个列表，内部列表仍然可以修改。我们不能把 tuple 当成整个对象结构已经被冻结。

实际写接口时，还需要看字段能不能被读者认出来。一个返回值有很多位置，即使用 tuple 固定住，也容易把顺序用错。需要清楚字段名的数据，可以考虑 namedtuple、dataclass 或字典。

## 知识点详解：固定成员的位置，不等于冻结整个数据

### 列表能改变哪些东西？

假设我们正在收集一批任务。开始只有两个任务，后来继续追加一个，完成后又删除一个。这里数量和成员都会变化，用列表就很直接。

append 可以在尾部追加成员，给 tasks\[0] 重新赋值可以替换首项，删除和切片赋值也能调整列表。列表保存的是成员对象的引用，所以修改容器和修改某个成员本身，是两种动作。

这一区分在元组里会更加明显。元组同样能引用很多对象，只是不能在创建之后把某个位置的引用换成另一个。

### 为什么元组里的列表还能改？

假设一条记录写成 ("课程A", \["草稿"])。外层有两个成员，课程名称和一个状态列表。

元组不能把第一个位置改成另一个课程名称，也不能换掉第二个位置保存的列表。但取出第二个成员以后，调用它的 append，修改的是那个列表自己的内容。外层保存的引用没有变化，这次操作就符合元组的规则。

#### Python

```python
record = ("课程A", ["草稿"])
record[1].append("待审核")
print(record)  # ('课程A', ['草稿', '待审核'])
try:
    record[0] = "课程B"
except TypeError:
    print("不能替换元组成员")
```

#### TypeScript（只读元组的静态检查对照）

```typescript
const record: readonly [string, string[]] = ["课程A", ["草稿"]];
record[1].push("待审核");
console.log(record);
// record[0] = "课程B"; // TypeScript 会报告只读成员赋值错误
```

这里也要注意两种语言的差异。Python tuple 的成员限制在运行时生效；TS 的 readonly 主要交给类型检查器，编译后这份数据仍然是 JavaScript 数组。这个对照帮助理解限制的层次，不能当成两种实现完全相同。

![元组不换成员，列表仍能追加](https://note.lgdsunday.club/img/Q566/02-nested.webp)

### 固定几个位置时，元组比较合适

例如函数返回二维坐标 (x, y)，调用方把它解包成两个变量。两个位置的含义很稳定，这时候元组能够清楚表达“这是一组一起返回的数据”。

那么，是不是函数返回多个结果就都应该用元组？也要看位置多不多。假设返回五六个状态和计数，调用方需要反复翻定义，才能确认第三项是什么。把它改成有名字的记录，通常更容易读懂。

列表则更适合表示同类元素组成的一组数据。即使当前只有两项，语义也是“任务集合”，将来可能变成零项或十项；不需要因为数量刚好是二，就改成元组。

![固定记录和可增长集合，表达不同数据](https://note.lgdsunday.club/img/Q566/03-semantics.webp)

### 性能和哈希能力，需要分别核对

在 CPython 中，元组和列表的存储安排不同，同样的简单成员数量下，内存开销可能不同。但这不足以推出“元组在任何操作里都更快”。创建方式、访问模式和数据规模都会影响比较结果。

只为少用一点空间，把需要反复追加的列表换成元组，可能还得不停创建新元组，反而增加工作。

另外，元组也不保证能用作字典键。前面那份包含列表的记录就不能直接作为键，具体条件在已有的可哈希对象题里已经讲过。本题选容器时，先考虑数据含义和修改需求，再检查必要的性能或哈希约束。

你可以用三个小用例确认理解。列表追加成员，元组尝试替换成员，元组内部列表追加成员。分别观察容器身份和内容，三个结果应该能被同一套引用关系解释。

## 面试官继续追问

### 把列表转成 tuple，原来的成员也复制了吗？

通常只是构造新的外层元组，里面继续引用那些成员对象。成员需要独立副本时，要另外明确复制要求。

### 元组只有一项，为什么还要写逗号？

单元素元组通常写成 (value,)，逗号决定元组构造；只写 (value) 通常是给表达式加括号。

### 既然有序，元组是不是已经排好大小？

有序说的是成员位置和遍历顺序，并不表示按某个值排序。列表和元组都可以保存乱序数字。

## 面试速记卡

> - list 与 tuple 都保留成员顺序。
> - 列表允许调整成员和数量，元组固定成员引用。
> - 外层元组固定，内部可变对象仍能修改。
> - 动态同类集合常用列表，少量固定位置可用元组。
> - 位置太多时考虑具名记录，性能按具体操作验证。
