# Python 的 Ruff、mypy 和 Pyright 有什么区别？格式检查能代替类型检查吗？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/python/q613-python-ruff-mypy-pyright/) · [题库目录](../../README.md)

*下面是模拟面试对话，用来讲解本题，不是真实面经。*

🧑‍💻 面试官：Ruff、mypy 和 Pyright 有什么区别？

🙋‍♂️ 我：Ruff 做 Lint 和格式，mypy、Pyright 做静态类型检查。

🧑‍💻 面试官：函数标注返回 int，实际返回字符串，格式化以后会修好吗？

🙋‍♂️ 我：不会，这属于类型和实现问题。

🧑‍💻 面试官：那三个工具都检查通过，为什么请求还是可能报错？检查范围会不会漏掉没写注解的代码？

> 先看每项检查承诺发现什么。代码整齐、静态类型合理和实际功能正确，需要三类不同证据。

## 面试速答（60 秒版）

Ruff 提供 Lint 与格式化能力，检查启用的规则和代码布局；mypy、Pyright 主要根据类型信息分析成员访问、参数和返回等静态约束。

格式化不会把错误返回值改成正确业务结果，Lint 也不能完整替代类型检查。类型检查器又受注解、Any、第三方类型信息和配置范围影响，不能保证所有运行时输入都安全。

实际项目可以配合使用，但不必为了工具数量同时重复跑所有同类检查。我会确定团队主类型检查器，记录 Python 目标版本与严格程度，在 CI 对齐编辑器配置。

检查通过以后仍要运行测试，覆盖动态输入、文件和网络错误等路径。忽略诊断要写清原因，不能用大范围 ignore 把“没有报错”伪装成“没有问题”。

## 知识点详解：格式、规则和类型，检查层次不同

### 格式化让代码一致，不替代码做业务决定

假设两个开发者用了不同引号、换行和缩进，格式化器可以把布局统一。Ruff 的 formatter 负责这类可重复排版，check 的 Lint 则依据启用规则检查未使用导入等问题。

某条 Lint 规则可能指出实际风险，但不能推出它已经覆盖所有类型关系。项目只运行了格式检查，也不能对外宣称已经做静态类型校验。

先把各命令的角色列清楚，CI 才能解释为什么失败，以及应该人工修正还是使用格式工具调整。

### 返回类型错误，应该由类型分析发现

下面是故意写错的诊断样例，不是推荐实现。格式完全整齐，返回值仍和注解冲突。

#### Python

```python
# 诊断样例：预期类型检查报告返回类型不符
def read_count() -> int:
    return "三"

# 正确实现应根据实际数据合同返回整数，或修改合同。
```

#### TypeScript（同类静态诊断）

```typescript
// 诊断样例：预期 tsc 报告 string 不能赋给 number
function readCount(): number {
  return "三";
}
```

mypy 和 Pyright 都能针对这类清楚的注解检查。复杂泛型、推断和配置下的诊断可能不同，所以迁移检查器时应检查项目真实结果，不能承诺一个配置文件换名字就无差别。

![排版没问题，返回类型仍然冲突](https://note.lgdsunday.club/img/Q613/02-error.webp)

### 为什么有些函数没有被充分检查？

没有足够注解、使用 Any 或缺少第三方类型信息时，检查范围可能变弱。mypy 默认对未注解函数体的处理和严格选项有自己的合同；Pyright 的检查模式也会决定哪些诊断启用。

排除目录、ignore 和 stub 都会影响结果。把所有错误简单设为忽略，会让通过状态失去原本含义。更合理的做法是分模块收紧，把剩余例外写成可追踪的具体原因。

同时确认目标 Python 版本。工具支持新语法，不等于部署解释器已经能执行它；配置里写明版本，有助于避免编辑器与 CI 得出不同结论。

![没有看到目标文件，绿色不说明问题](https://note.lgdsunday.club/img/Q613/03-coverage.webp)

### 工具选型，也要避免重复劳动

常见流程可以分为格式检查、Lint、一个主静态类型检查器，再运行测试。mypy 和 Pyright 不是强制同时用，是否双跑要看项目是否获得额外收益，以及诊断维护成本。

编辑器和 CI 使用一致配置与版本，能减少“本地绿、CI 红”。自动修复也要分清安全修复与可能改变语义的改动，不因为工具提供 fix 就不审 diff。

最终验证至少放一份故意错误样例，确认类型检查确实看到了对应文件；再放运行时错误输入的测试，确认动态边界有人负责。配置成功不能只靠命令退出码为零，尤其命令可能根本没检查目标目录。

依据：[Ruff Linter](https://docs.astral.sh/ruff/linter/)、[Ruff Formatter](https://docs.astral.sh/ruff/formatter/)、[mypy 运行与导入管理](https://mypy.readthedocs.io/en/stable/running_mypy.html)、[Pyright 官方配置](https://github.com/microsoft/pyright/blob/main/docs/configuration.md)。

## 面试官继续追问

### Ruff 和 Astral 的类型工具是同一个吗？

不能混称。Ruff 的 Lint/格式职责和其他静态类型产品要分别按官方工具说明判断。

### 给所有错误加 ignore 就算迁移完成吗？

这只压住诊断。需要标记例外范围和原因，并逐步缩小，不能把静默当作正确证明。

### mypy 和 Pyright 一定都要上吗？

不一定。先选符合项目的主检查器；双跑要确认额外发现值得维护成本。

## 面试速记卡

> - 格式检查统一布局，不自动修业务返回。
> - Lint 根据启用规则找问题，不替代完整类型分析。
> - mypy、Pyright 分析静态类型合同。
> - Any、未注解、排除范围和配置影响覆盖。
> - 检查通过后仍需实际测试与动态输入校验。
