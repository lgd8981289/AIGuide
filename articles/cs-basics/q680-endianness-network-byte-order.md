# 大端序和小端序有什么区别？网络字节序为什么需要转换？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/cs-basics/q680-endianness-network-byte-order/) · [题库目录](../../README.md)

下面是一段模拟面试对话。

🧑‍💻 **面试官：** 大端和小端怎么区分？

🙋‍♂️ **我：** 看多字节数值的高位字节，放在较低还是较高地址。

🧑‍💻 **面试官：** 0x12345678 用大端写成哪四个字节？

🙋‍♂️ **我：** 从低地址到高地址是 12、34、56、78。

🧑‍💻 **面试官：** 那网络上传一个 JSON 字符串“305419896”，也必须先调用 htonl 吗？

> 字节序讨论多字节数值怎样编码成字节。先确认传输格式，再谈转换，不是所有内容都按主机内存直接发送。

## 面试速答（60 秒版）

大端序把高位字节放在较低地址，小端序把低位字节放在较低地址。它改变的是多字节数值与字节序列的对应关系，不改变这个数值本身。

传统网络字节序指大端，htonl、htons 等接口用于主机序与相应网络序之间转换。不同主机的本地表示可能不同，所以通信协议要明确字节顺序，不能直接发送本机整数内存就期望双方自动理解。

但具体应用格式要具体看。JSON 数字是文本编码，不需要先把那几个十进制字符当作 32 位整数执行 htonl；有些二进制协议也明确采用小端。

我会按协议显式写入宽度、符号和字节序，并用固定字节样例验证。重复转换、直接强转内存、混淆字符串字符顺序，都是常见错误。

![同一个整数，两种字节顺序](https://note.lgdsunday.club/img/Q680/01-endianness-network-byte-order.webp)

## 知识点详解：同一个数，可以有两种字节排列

### 先固定“从低地址到高地址”这个观察方向

以四字节无符号整数 0x12345678 为例。

| 顺序 | 第 0 字节 | 第 1 字节 | 第 2 字节 | 第 3 字节 |
| -- | ------ | ------ | ------ | ------ |
| 大端 | 12     | 34     | 56     | 78     |
| 小端 | 78     | 56     | 34     | 12     |

表里是十六进制字节，不是在把十进制数的数字倒过来写。更不是说一个字节内部的比特传输顺序也必然跟着变化，那是另一个层次。

[Linux byteorder 手册](https://man7.org/linux/man-pages/man3/byteorder.3.html)定义了常见主机序与网络序转换接口，但应用依然要遵守自己协议的编码。

### 直接指定编码，比猜机器是什么序更清楚

以下双语代码都构造相同数值，分别按大端和小端写入四字节，不依赖机器本地字节序。

#### TypeScript（Node.js Buffer）

```typescript
import { Buffer } from "node:buffer";

const value = 0x12345678;
const big = Buffer.alloc(4);
const little = Buffer.alloc(4);
big.writeUInt32BE(value);
little.writeUInt32LE(value);
console.log(big.toString("hex"));
console.log(little.toString("hex"));
console.log(big.readUInt32BE() === value);
```

#### Python（struct）

```python
import struct

value = 0x12345678
big = struct.pack(">I", value)
little = struct.pack("<I", value)
print(big.hex())
print(little.hex())
print(struct.unpack(">I", big)[0] == value)
```

两边应分别打印 12345678、78563412，再确认按匹配规则读回原数值。[Node Buffer 文档](https://nodejs.org/api/buffer.html)和[Python struct 文档](https://docs.python.org/3/library/struct.html)定义了实际 API；这里不是把两种语言的内存布局假设成相同。

![约定编码，接收方才能读对](https://note.lgdsunday.club/img/Q680/02-endianness-network-byte-order.webp)

### 文本协议，已经有另一套表示

如果传输 JSON，数值先变成十进制文本，再按约定字符编码传输。接收方解析文本得到数值，不是拿四个主机序字节直接解释。

因此，不能把“网络字节序大端”扩大成“网络上任何格式都先反转字节”。图片、压缩数据、文本和应用二进制协议，各自有格式规范。

同样，把一份二进制结构体直接写上网络，还可能带进字段对齐、填充、宽度和符号差异。字节序一致，只解决其中一个问题。

### 测试要包含非对称的字节

0、全 1 或某些重复字节，不容易暴露顺序反了的问题。用 0x12345678 这类各字节不同的样例，再加入最大值、边界宽度和非法长度，更容易检查。

编码端和解码端如果一起写错，往返测试仍可能通过。所以还要对照协议规定的固定字节序列，而不是只测“自己写出去又能自己读回来”。

## 面试官继续追问

### 大端一定比小端更快吗？

不能一概而论。处理器指令、访问方式和协议转换都会影响成本。先按格式正确读写，再根据目标平台测量，别把表示顺序当性能排名。

### 已经用 BE 写入，还需要 htonl 吗？

不能无条件再转一次。写入 API 已经按大端编码，再对数据重复交换可能改坏结果。明确当前拿到的是数值，还是已经编码好的字节。

## 面试速记卡

> - 大端：高位字节在低地址；小端：低位字节在低地址。
> - 网络序：常见转换接口的大端约定，不代表所有应用格式。
> - 编码：同时明确宽度、符号、字节序和字段边界。
> - 文本：JSON 按文本格式处理，不机械执行整数换序。
> - 验证：固定字节样例与往返测试都要有，避免双端一起写错。
