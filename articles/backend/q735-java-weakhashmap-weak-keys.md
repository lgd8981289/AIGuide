# WeakHashMap 是什么？弱引用为什么不等于一个可靠的缓存？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/backend/q735-java-weakhashmap-weak-keys/) · [题库目录](../../README.md)

*下面是一段用于讲解的模拟面试对话。*

🧑‍💻 **面试官：** 一个普通 HashMap 一直保存临时对象，担心对象不能回收，怎么办？

🙋‍♂️ **我：** 可以换成 WeakHashMap，没用的键会自动清理。

🧑‍💻 **面试官：** 那就能拿来做带过期时间的缓存了吗？

🙋‍♂️ **我：** GC 会回收，应该不用自己清理了。

🧑‍💻 **面试官：** 什么时候回收？如果 value 又指回 key，键还会只剩弱引用吗？

> WeakHashMap 判断的是键的可达性，不是业务上的过期时间、容量上限或缓存命中率。

## 面试速答（60 秒版）

`WeakHashMap` 是使用弱键的映射。当一个键除了这些弱引用以外，已经没有使它保持存活的强引用路径时，GC 就可能回收它，相关条目随后会被清理。

但是，WeakHashMap 对 value 仍然是强引用。如果 value 直接或间接引用了 key，Map 可能通过 value 把 key 留住，弱键就不能达到预期效果。

它也没有提供固定过期时间、最大容量和稳定淘汰策略。GC 什么时候发生、哪些键还被外部引用，都不由缓存业务自己决定。因此，它适合某些“附加数据跟随对象生命周期”的用途，不应该直接当成一个可靠的业务缓存。

使用时还要注意，它并不是线程安全容器，也不能靠一次 System.gc() 就证明条目一定已经消失。验证的重点应该是引用关系与使用边界，而不是等待某一次碰巧发生的回收。

## 知识点详解：弱键到底能帮我们释放什么？

### 普通映射为什么会把对象留住？

假设咱们给临时页面对象保存一份辅助信息。页面已经不用了，但是一个长期存在的 HashMap 还把页面对象当作 key。

从 GC 的角度看，长期 Map 仍能找到这个对象，它就不算可以回收。业务说“页面已经关闭”，不会自动让 Java 的引用关系消失。

WeakHashMap 把“从 Map 的键位置到对象”的关系改成弱引用。如果外部已经不再保持这个键存活，这条弱引用不会单独阻止回收。它适合表达“对象还活着时，附带保存一些信息；对象离开以后，这份附带关系也可以消失”。[WeakHashMap 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/WeakHashMap.html)说明了这种自动移除语义。

### 强 value 会把弱 key 绕回来

这里最需要画清楚的是一条引用路径。Map 强引用一个 value，value 又保存着 key，那么从 Map 出发，仍然可以沿着强引用找到 key。

虽然键槽位那条边是弱的，但另外一条强路径还在。GC 不会因为看见 WeakHashMap 这个名字，就忽略其他强引用。

这种反向关系还可能经过多个对象。比如 value 保存一个回调，回调闭包捕获 key，或者 value 保存的另一个对象又引用 key。检查时要沿引用链看，不能只搜索 value 类里有没有一个叫 key 的字段。

多个条目之间也可能互相把对方的键留住，因此不能只逐条检查自己是否直接引用自己。引用分析要看整个可达图。

![WeakHashMap 强引用 value，而 value 强引用 key 时，键仍有强可达路径](https://note.lgdsunday.club/img/Q735/02-strong-backpath.webp)

### 为什么它不等于自动过期缓存？

假设某个键持续被业务强引用，即使这条数据已经很旧，WeakHashMap 也没有因为“超过五分钟”就淘汰它。反过来，某个键很快失去外部强引用，哪怕刚放进去，相关条目也可能消失。

因此，数据的存活更接近对象生命周期，而不是业务新鲜度。它无法直接回答缓存多大、什么时候刷新、哪些数据应该优先淘汰这些问题。

更容易忽略的是，相等的键不等于同一个存活对象。某个原键被回收以后，之后重新构造一个 equals 相等的键，也不能把已经被移除的条目凭空找回来。普通值缓存通常希望“只要键值相同就能命中”，而弱键生命周期取决于具体键对象，这里存在真实差别。

![弱键的可达性不等于缓存 TTL、容量与新鲜度策略](https://note.lgdsunday.club/img/Q735/03-cache-contract.webp)

### 条目什么时候从表里消失？

键被回收，和 Map 内部已经完成清理，不是必须在同一个瞬间发生。实现可以结合引用队列，在访问映射等过程中清理过期条目。[OpenJDK 21 实现](https://github.com/openjdk/jdk21u/blob/master/src/java.base/share/classes/java/util/WeakHashMap.java)可以看到 ReferenceQueue 与清理过程。

因此，不应该把某次 size 的变化当作精确定时器。System.gc() 也只是请求，不承诺某个对象在某个时刻一定完成回收。

要验证设计，可以先画出 Map、键、值和外部持有者之间的强弱边，再检查值到键的反向路径。回收行为实验应设置观察窗口、承认非确定性，不写一个“调用 GC 后必须 size 为零”的脆弱断言。本文核对的是文档和引用机制，没有虚构一组必然回收的运行结果。

## 面试官继续追问

### 用字符串当 key 合适吗？

要非常小心字符串的来源。字面量、驻留字符串或被其他对象保留的字符串，可能长期有强引用。不能因为业务变量出了作用域，就认定那个字符串对象只剩弱引用。

### value 也改成弱引用，是不是就完整解决了？

这会改变值的生命周期，读取时可能拿到已经消失的值，但仍然没有自动得到容量、过期、加载合并等缓存能力。需要什么语义，就明确设计什么语义。

### JavaScript WeakMap 可以直接照搬这套解释吗？

不能。不同语言对弱集合、键类型、可观察性和可达关系有各自规定。这篇讨论 Java WeakHashMap，不能仅凭名字相近就套用另一种运行时的全部结论。

## 面试速记卡

> - 弱的是 key：Map 的弱键引用不单独阻止键被回收。
> - value 仍强：value 到 key 的强路径可能让键一直存活。
> - 淘汰依据：对象可达性，不是 TTL、容量或业务新鲜度。
> - 验证：先查引用图，不依赖某次 System.gc() 的必然结果。
> - 选型：生命周期附加信息可以考虑，业务缓存需要明确的缓存语义。
