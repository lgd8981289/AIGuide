# Java 性能测试为什么用 JMH？预热、死代码消除和常量折叠如何影响结果？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/backend/q736-java-jmh-microbenchmark-pitfalls/) · [题库目录](../../README.md)

*下面是一段用于讲解的模拟面试对话。*

🧑‍💻 **面试官：** 你说两种转换方法，A 比 B 快，怎么测的？

🙋‍♂️ **我：** 在 main 方法里循环调用，前后记录 nanoTime，再除以次数。

🧑‍💻 **面试官：** 结果用在哪里？

🙋‍♂️ **我：** 没用，只想测执行时间。

🧑‍💻 **面试官：** 那编译器把不影响程序结果的计算消掉以后，你测到的还是这段计算吗？

> 微基准首先要证明“目标工作真的发生了”，然后才轮到计时精度。

## 面试速答（60 秒版）

Java 的执行会受到即时编译和运行时优化影响。直接写一个循环计时，可能把类加载、解释执行、编译过程和稳定后的执行混在一起，也可能因为结果没被使用，目标计算被优化掉。

`JMH` 是专门做 JVM 微基准的工具，可以帮助组织预热、正式测量和独立进程运行。但使用 JMH 不代表测试天然正确，基准代码仍然要让输入和真实用途相符，并且消费计算结果。

比如返回结果，或者在适当场景使用 Blackhole，减少死代码消除的影响；不要把所有输入写成编译器很容易提前算好的常量；还要记录 JDK、参数、数据规模和运行环境。

微基准适合比较一小段操作，不直接等于整个接口的吞吐量和 P99。最后是否值得改，仍要回到实际链路里验证。

## 知识点详解：跑得特别快，也可能根本没干活

### 先问这段计算有没有可观察的结果

假设咱们反复把一段字符串转换成某个值，转完以后既不返回，也不保存，更没有任何外部效果。如果编译器能够证明这段工作不会影响程序结果，就有机会消除它。

此时，计时器依然正常工作，循环也可能还留着一部分，但你想比较的计算已经不一定存在。多测几次，平均得再精细，也不能修复“测错对象”。

JMH 允许基准方法返回计算结果，工具会对返回结果进行消费；也可以根据基准需要显式使用 Blackhole。[官方死代码示例](https://raw.githubusercontent.com/openjdk/jmh/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_08_DeadCode.java)展示的正是这种差别。

不过，不要为了让结果被使用，每次都打印到终端。打印可能比目标计算贵得多，最后主要测到的是 I/O。

### 输入固定，为什么也会测偏？

如果测试始终计算一个编译期就很容易确定的表达式，编译器可能提前算出结果，或者把不变计算移到测量循环之外。代码里看起来调用了一百万次，实际执行不一定如此。

因此，输入应当来自适合基准的数据状态，并覆盖你真正关心的分布。需要比较短字符串和长字符串，就明确设参数组；需要考虑命中和未命中，就分别准备对应输入。不要在每次基准调用里临时创建大量随机数据，把数据生成成本也算进目标操作。

[JMH 常量折叠示例](https://raw.githubusercontent.com/openjdk/jmh/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_10_ConstantFold.java)解释了状态字段与可预测常量的差别。它是在提醒基准作者控制优化条件，不是在建议业务代码为了测速故意去掉所有 final。

![死代码消除与常量折叠会让微基准没有执行原本想测的工作](https://note.lgdsunday.club/img/Q736/02-optimizer-traps.webp)

### 预热与 fork 分别在解决什么？

同一段 Java 代码，启动时可能主要由解释器执行，调用一段时间以后，热点代码才被即时编译。把前面几次与后面几次混在一起，容易比较到不同运行阶段。

预热给运行时积累执行信息的机会，正式测量再单独记录。但是预热轮数不是越多越科学，也不能承诺预热以后所有状态都永久稳定。要根据目标操作、编译状态和结果波动检查是否足够。

fork 则把基准放到独立 JVM 进程中运行，减少前一个测试积累的类型信息等状态对下一个测试的影响。[官方 fork 示例](https://raw.githubusercontent.com/openjdk/jmh/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_12_Forking.java)说明了测试间画像污染的问题。线程数与共享状态也应符合真实使用方式，不能用单线程局部变量成绩替代共享容器的并发效果。

![预热隔开运行阶段，独立 fork 减少不同基准的运行时画像污染](https://note.lgdsunday.club/img/Q736/03-warmup-fork.webp)

### 结果里哪些信息不能省？

至少保留 JDK 与 JVM 版本、关键 VM 参数、硬件与资源限制、输入规模、预热和测量设置、fork 数量、测试代码版本。看平均时间时，也要看误差和各轮结果，差异小于波动范围，就不应该宣布一个确定胜者。

如果优化目标是减少分配，应结合相应 profiler 看分配量；如果是业务接口，应该再检查真实负载下的吞吐、延迟分位数和错误率。操作本身快了一点，并不能证明数据库等待、锁竞争和网络成本一起变好了。

本文依据 JMH 官方样例解释设计方法，没有运行本篇性能基准，也不提供虚构的纳秒成绩或加速倍数。实际验证应先让两种实现通过同一批正确性测试，再比较性能，最后到目标应用中复测。

## 面试官继续追问

### 使用 nanoTime 本身有问题吗？

它适合测量经过时间。问题通常在测试设计、运行阶段和编译优化，不是换一个时钟 API 就能解决。极短操作还需要考虑测量开销，但也不能随意堆循环让优化条件改变。

### JMH 结果稳定，就能直接决定线上方案吗？

不能。输入分布、线程竞争、分配压力和周边调用可能与线上不同。微基准可以支持一个局部判断，但需要说明这个判断如何落回真实应用。

### 为什么不在基准里手写一大段循环？

循环可能触发展开、合并计算等优化，让每次操作的成本失真。JMH 本身会组织调用，是否自己写循环，要根据测量对象和官方相关样例单独判断。

## 面试速记卡

> - 先验真：目标计算必须真实发生，正确性先于性能。
> - 防误测：消费结果、控制常量折叠，别用终端打印替代结果消费。
> - 预热：区分运行阶段；fork：减少不同测试之间的状态污染。
> - 留证据：环境、参数、输入、误差与代码版本要一起记录。
> - 范围：微操作成绩不等于接口容量，更不等于线上 P99。
