# JVM 逃逸分析和 TLAB 是什么？对象一定分配在堆上吗？

*下面是一段用于讲解的模拟面试对话。*

🧑‍💻 **面试官：** Java 代码里写了 new，就一定会产生一个实际堆对象吗？

🙋‍♂️ **我：** 对象在堆上，局部变量在栈上。

🧑‍💻 **面试官：** 如果对象只有两个数字字段，算完一个和就再也不用了，JIT 有必要保留整个对象吗？

🙋‍♂️ **我：** 那没有逃逸，可以放在线程的 TLAB，应该相当于栈上分配。

🧑‍💻 **面试官：** TLAB 在哪里？减少竞争，和消除对象分配，是同一件事吗？

> 先分清对象有没有被真正分配，再看分配发生在哪里。TLAB 仍属于堆，标量替换则可能让对象分配本身消失。

## 面试速答（60 秒版）

Java 虚拟机规范从逻辑上把类实例和数组放在堆里，但具体实现可以在不改变程序可观察行为的前提下优化代码。因此，源码中的一次 new，不一定对应运行时留下一个实际对象。

HotSpot 的逃逸分析会分析对象的引用是否离开相关方法或线程范围，为标量替换、锁消除等优化提供条件。标量替换可以把对象拆成单独需要的字段值，从而消除某些实际分配；这不应该简单说成“对象搬到栈上”。

`TLAB` 则是在线程私有的分配缓冲区里快速分配对象，缓冲区本身仍在堆中。它主要减少分配时的线程竞争，不会把对象变成线程永远独占，也不会免除 GC。

实际优化能否发生，要看 JDK、编译器、内联和代码形态，不能只看变量写在方法里面就下结论。

## 知识点详解：别把三种不同的事情混在一起

### 局部引用，与它指向的对象分开看

假设一个方法里声明局部变量 p，p 指向一个包含 x、y 的对象。p 是引用变量，对象是另一件东西。不能因为 p 的名字只出现在当前方法，就直接认定对象一定不会被外面看到。

如果把 p 放进一个全局集合、交给一个会长期保存它的回调，引用就可能离开当前范围。反过来，源码里即使经过了一次方法调用，JIT 内联以后，也可能看清整个使用过程，发现对象根本不用实际保留。

因此，逃逸是编译器在具体代码上下文里分析出来的性质，不是 local、new、return 这些关键字各自附带的一条永久结论。[HotSpot 性能增强说明](https://docs.oracle.com/en/java/javase/21/vm/java-hotspot-virtual-machine-performance-enhancements.html)解释了逃逸分析与相关优化。

### 标量替换，是把对象需求拆开

假设对象只用来保存 x=3、y=5，后面立即读取它们相加。如果编译器确认没有其他代码需要观察这个对象的身份，也没有必须保留的可见效果，就可能直接处理这两个字段值，最后得到 8。

这种情况下，实际运行不一定需要分配一个完整对象。字段值可能被放进寄存器、栈位置，或者继续参与优化，不能固定画成“一个完整对象从堆搬到了栈”。

逃逸分析提供条件，也不保证每个不逃逸对象都一定能被消除。对象形态、控制流、编译阶段和具体实现都有影响。开启了某个优化选项，也不能替代对实际代码的观察。

锁消除同样依赖分析。如果锁保护的对象根本不会被其他线程同时看到，编译器可能消除某些同步成本，但不能因此删除源码中的所有 synchronized。业务真正共享的对象，仍然需要正确的同步规则。

![满足条件时，标量替换可保留字段计算而消除完整对象分配](https://note.lgdsunday.club/img/Q740/02-scalar-replacement.webp)

### TLAB 解决的是分配时的竞争

现在换一种情况，对象确实需要创建，不能被优化掉。多个线程都从堆里申请空间，如果每个小对象都去竞争同一份分配位置，成本就会增加。

TLAB 给线程准备一段可以快速使用的堆空间。线程在自己的缓冲区中推进分配位置，常见的小对象分配就不需要每次争抢同一个全局位置。空间不足或不适合在当前缓冲区分配时，还会进入相应的补充与其他分配路径。

但是，“分配缓冲区归某个线程使用”，不等于“从这里创建的对象永远只能被这个线程访问”。对象后面完全可能被正确发布给其他线程。[OpenJDK TLAB 实现](https://github.com/openjdk/jdk21u/blob/master/src/hotspot/share/gc/shared/threadLocalAllocBuffer.hpp)把它作为堆分配缓冲来管理。

所以，TLAB 内创建的对象仍然属于堆对象，仍然可能变成共享对象，也仍然由 GC 管理。线程局部的是分配动作的快速路径，不是业务对象的永久归属。

![线程在堆内 TLAB 快速分配对象，但对象可发布共享且仍由 GC 管理](https://note.lgdsunday.club/img/Q740/03-tlab-heap.webp)

### 怎么证明优化真的发生了？

先固定 JDK 与 JVM 版本、编译器和关键参数，再准备正确性一致的最小实验。使用适合的基准与分配观测，检查稳定执行阶段的分配量，同时排除整个计算被死代码消除的情况。

如果关闭某项优化后分配增加，可以作为线索，但还要考虑关闭选项改变了哪些其他编译行为。不能只用执行时间变快，就断言“一定发生了栈上分配”。[JVM 规范](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.5.3)描述的是逻辑堆区域，不替某个基准承诺物理布局。

本文以 Java 21 HotSpot 文档和源码说明机制，没有运行 JIT 反汇编或分配基准，因此不虚构“某段代码已经被消除”的实验结果。面试时也应把机制判断和实际观测分开说。

## 面试官继续追问

### 方法返回对象，是不是一定逃逸到堆？

不能脱离调用上下文。保留方法边界分析时，与被内联到调用方以后，编译器能看到的信息不同。也不能拿 Go 编译器的日志规则直接解释 HotSpot。

### 有了 TLAB，就没有分配竞争了吗？

不是。补充缓冲、特殊大小对象和其他分配路径仍有自己的成本。它是在常见路径上减少竞争，不是让全部分配免费。

### 为了减少 new，要不要统一改成对象池？

先测真实热点。池化会增加生命周期、清理、共享和内存保留问题，还可能妨碍原本可以消除的短命对象分配。别为了减少源码中的 new，把简单代码改成复杂共享状态。

## 面试速记卡

> - 逻辑与物理：规范描述堆对象，JIT 可以消除不影响行为的实际分配。
> - 逃逸分析：分析引用范围，为后续优化提供条件。
> - 标量替换：拆分对象所需的字段值，不等于完整对象搬到栈上。
> - TLAB：线程使用的堆内分配缓冲，减少常见分配竞争。
> - 验证：固定环境看实际分配与编译证据，不按 new 的数量判断性能。
