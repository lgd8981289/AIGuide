# Spring MVC 和 WebFlux 有什么区别？用了响应式就一定更快吗？

下面是一段模拟面试对话。

🧑‍💻 **面试官：** Spring MVC 和 WebFlux 怎么选？

🙋‍♂️ **我：** WebFlux 非阻塞，所以性能更好，高并发就选它。

🧑‍💻 **面试官：** 如果数据库访问仍然是阻塞的 JDBC，你把它包进 Mono，线程就不会阻塞了吗？

🙋‍♂️ **我：** 不会，实际调用还是会等待。

🧑‍💻 **面试官：** 那你要比较的到底是响应时间、吞吐量，还是为了等 I/O 占用了多少线程？

> 先找请求把时间花在了哪里，再谈执行模型。写成响应式返回值，不会自动改造底下的阻塞依赖。

## 面试速答（60 秒版）

Spring MVC 建立在 Servlet 模型上，常见应用用请求处理线程执行同步逻辑；WebFlux 使用响应式、非阻塞的处理模型，适合大量请求需要等待 I/O 的场景。

但非阻塞不等于单个操作变快。它主要让线程在等待时可以处理别的任务。如果在事件循环里直接执行阻塞 JDBC、同步 HTTP 或长时间 CPU 计算，仍会拖住其他请求。

选型要看整条调用链。如果现有依赖和团队开发方式以同步为主，MVC 往往更直接；如果并发 I/O 很多、依赖能够非阻塞配合，才更值得评估 WebFlux。

两者都要控制超时、并发和下游容量。用同样负载比较吞吐、尾延迟、资源和错误率，不能仅凭 Mono、Flux 或“响应式”这几个名字宣布性能更好。

## 知识点详解：等待期间，线程在做什么？

### 请求慢，不一定是 CPU 忙

假设一个接口需要查数据库，再调用两个外部服务。其中大部分时间都在等网络返回，真正执行 Java 计算只占一小部分。

在常见同步执行方式中，处理线程会随着阻塞调用一起等待。请求多起来，等待中的线程数量也可能增加，带来线程资源和调度压力。

非阻塞 I/O 的目标，是让发起操作的线程不必一直守在原地。数据就绪以后，再由后续处理继续推进。它改变的是等待和调度方式，不会让外部服务原本 100 毫秒的处理自然缩短成 10 毫秒。[Spring WebFlux 官方概览](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html)也明确区分了可扩展性与单次执行速度。

### 把阻塞调用包进 Mono，问题可能只是换了位置

假设代码在事件循环线程里调用同步 JDBC。这段调用没有因为返回类型变成 Mono，就获得非阻塞能力。数据库没返回，执行它的线程照样被占着。

必要时可以把阻塞工作隔离到合适的、有边界的执行资源中，但要继续问：排队能有多长？线程池多大？数据库连接池能承受多少？超时以后底层操作是否真的取消？

这是一种兼容与隔离措施，不等于整条链路已经非阻塞。若大部分依赖都要这样搬运，响应式模型的收益可能被额外复杂度抵消。

![包进 Mono，阻塞调用仍然会等](https://note.lgdsunday.club/img/Q659/02-spring-mvc-vs-webflux.webp)

### 背压，也不能替你扩大数据库容量

响应式流里的请求数量协调，有助于上下游表达消费能力。但并非每个外部系统都能无损地响应这种节奏。

HTTP 接口、消息来源、数据库驱动和应用缓存，需要分别看实际支持。下游只能稳定处理有限请求时，仍要有并发限制、排队上限或拒绝策略，不能默认所有压力都会自动传回最初的用户。

CPU 密集型工作也一样。一段复杂计算需要的 CPU 时间，并不会因为使用 Flux 就减少，必要时仍要分配计算资源或改算法。

### 怎么做一场有意义的选型实验？

先固定真实依赖、请求分布和超时规则。不能让 MVC 版本串行调用三个接口，却让 WebFlux 版本并行调用，然后把全部收益归因于框架。

接着从可承受负载逐步加压，观察成功吞吐、P95/P99、CPU、内存、线程、连接池和下游错误。尤其要测试慢依赖，看看队列增长以后是否还能恢复。

还要把开发成本算进去。异常链路、上下文传递和调试方式都会变化。系统已经以同步依赖为主、流量也没到当前模型瓶颈时，保留 MVC 可能是更可解释的选择。虚拟线程又提供了另一种同步编程下的并发方案，应单独评估，不能直接套用这篇对平台线程的资源观察。

## 面试官继续追问

### MVC 就完全不能异步吗？

不是。MVC 也支持异步请求处理和部分响应式返回类型，不能把“框架名字”与“代码里每一步都阻塞”画等号。两者差异要结合运行环境及整条执行链说明。[MVC 异步请求处理文档](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html)介绍了对应能力。

### 如果团队只想提高一个慢接口呢？

先拆延迟：查询、网络、串行依赖还是计算。能用索引、缓存、合理并行或连接复用解决的问题，未必需要全项目切换执行模型。确定瓶颈之后，再验证改动收益。

## 面试速记卡

> - 模型：MVC 常见同步处理；WebFlux 面向响应式、非阻塞链路。
> - 收益：减少等待对线程的占用，不承诺单个下游更快。
> - 陷阱：Mono 包装不会自动消除阻塞，事件循环不适合长时间占用。
> - 边界：背压不替代连接池、并发限制和下游容量规划。
> - 选型：同负载看吞吐、尾延迟、资源与维护成本。
