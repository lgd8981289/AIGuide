# Java JFR 是什么？和线程 Dump、Heap Dump 各适合查什么？

>
> [在线阅读与配图](https://note.lgdsunday.club/backend/q737-java-jfr-thread-heap-dump/) · [题库目录](../../README.md)

*下面是一段用于讲解的模拟面试对话。*

🧑‍💻 **面试官：** 接口偶尔卡两秒，你拿到了一个线程 Dump，就能确定原因吗？

🙋‍♂️ **我：** 可以看线程当时卡在哪个方法。

🧑‍💻 **面试官：** 如果抓取时它已经恢复了呢？

🙋‍♂️ **我：** 那再抓几次，或者抓 Heap Dump。

🧑‍💻 **面试官：** Heap Dump 能告诉你刚才那两秒，哪个线程等了多久吗？

> 线程与堆转储主要留下某个时刻的状态，JFR 则把一段时间里的事件关联起来。先选对证据形态，再讨论工具名字。

## 面试速答（60 秒版）

`JFR` 是 JDK 的事件记录机制，可以在一段时间里收集执行采样、锁等待、GC、分配等配置允许的事件，帮助我们把问题放回发生时的时间范围里分析。

线程 Dump 主要看某个时刻线程在执行什么、等待什么；Heap Dump 主要看堆里有哪些对象，以及它们之间的引用关系。它们很有用，但不能直接还原完整的历史过程。

因此，偶发卡顿或持续性能变化，可以考虑用 JFR 留下一段时间的线索；怀疑死锁或线程阻塞，先看合适的线程转储；怀疑对象长期被保留，再分析堆转储。

同时，JFR 不是记录每一次方法调用的万能录像。事件开关、阈值、采样和保留范围都会影响能看到什么。采集前还要评估开销与敏感信息，不能只因为工具常用就直接开最重配置。

## 知识点详解：一次卡顿，需要留下哪一种证据？

### 线程 Dump 能回答“现在在哪里”

假设某个接口正在等待一把锁。恰好在等待期间抓到线程转储，就可能看到等待状态、栈和锁信息。连续抓几份，还能观察同一个位置是否长期不动。

但是，如果卡顿只持续很短一段时间，等你开始抓，它已经结束，转储可能看起来完全正常。这不表示故障不存在，只表示这份瞬时证据没有覆盖到它。

线程转储也不是每个线程的完整执行历史。某种状态出现一次，与它占用了大量时间，是两种结论。[jcmd 文档](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html)列出了线程、堆与 JFR 相关诊断命令，实际要按目标 JDK 和线程类型选择。

### Heap Dump 能回答“谁把对象留住了”

Heap Dump 保存堆对象及其引用关系，适合分析哪些对象占用内存、哪些引用链让它们无法回收。比如某个长期集合一直持有请求结果，就可以沿着引用关系找到保留来源。

但对象现在还在，不等于已经证明它是什么时候分配、刚才哪一次请求创建的。也不能仅凭一个堆快照，直接知道某线程一分钟内等锁的总时间。

此外，堆转储可能包含业务数据、凭证和用户内容，文件也可能很大。采集和传输都要控制访问、磁盘空间与保存期限。不能为了排查一次短暂卡顿，未经评估就生成一份包含全部敏感对象的堆文件。

### JFR 把事件放到同一段时间里

JFR 记录的是事件。事件可以带时间戳、持续时间、线程和栈等信息，具体有哪些字段要看事件类型。我们可以选择故障窗口，再检查当时是否出现 GC 暂停、监视器等待或相关执行采样。[JFR API](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.jfr/jdk/jfr/package-summary.html)说明了事件与设置模型。

比如，卡顿窗口里有一段较长的锁等待，是值得继续追的证据；但时间上重叠还不能自动证明它就是全部原因。需要继续结合等待栈、锁竞争对象、请求日志和重复出现的模式来核对。

执行采样同样不是逐调用计数。某方法在样本里频繁出现，说明它值得关注，不代表可以直接把样本数当成它被调用的精确次数。分配相关事件也应按事件类型、采样与设置解释，不能都当成每次分配的完整账本。

![JFR 将采样、锁等待和 GC 等事件放到同一时间窗口中辅助分析](https://note.lgdsunday.club/img/Q737/02-jfr-timeline.webp)

### 设置决定了这份记录能回答什么

采集前先写清问题。要看锁等待，就检查相关事件是否启用、阈值会不会漏掉关注范围；要看分配压力，就确认采集的事件与需要的分析匹配。记录保留时间、文件上限和输出目录也要明确，别等故障发生以后才发现目标时间段已经被覆盖。

JFR 支持不同记录配置，也能通过 jcmd 控制。命令执行前可以先查看目标进程支持的帮助信息，确认当前 JDK 的选项。进程权限、容器环境和磁盘可写性同样会影响采集，工具存在不代表一定能连接成功。

验证时可以在隔离环境分别制造可控的睡眠、锁等待和短时分配压力，看看目标配置确实留下了哪些事件，再决定生产采集范围。本文按 Java 21 文档核验工具边界，没有把模拟场景冒充线上事故，也没有实际采集某个业务进程的数据。

## 面试官继续追问

### JFR 开销低，可以一直无条件开启吗？

是否长期运行取决于配置、事件量、环境和开销预算。可以评估持续记录，但“通常可控”不等于所有自定义事件、栈采集和高频设置都免费。

### 没看到锁等待事件，就能排除锁问题吗？

不能先这么下结论。先检查记录时间段、事件开关、阈值与目标 JDK 是否支持，再判断证据有没有覆盖。缺少事件可能是没有发生，也可能是没有被记录。

### 三种证据是否必须全部收集？

不用。先根据问题选成本合适、最可能回答当前疑问的证据。需要时再补另一种，而不是把全部诊断文件都生成一遍。

## 面试速记卡

> - 线程 Dump：某个时刻线程的栈与等待状态。
> - Heap Dump：堆对象与引用关系，重点看保留原因。
> - JFR：一段时间里的事件，帮助关联发生过程。
> - 解读边界：采样、阈值、事件开关和保留窗口决定可见范围。
> - 操作边界：评估开销、权限、磁盘与敏感数据，不以工具名替代证据。
