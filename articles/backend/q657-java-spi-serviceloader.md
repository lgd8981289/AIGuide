下面是一段模拟面试对话。

🧑‍💻 **面试官：** Java SPI 解决什么问题？

🙋‍♂️ **我：** 面向接口编程，通过反射找到实现。

🧑‍💻 **面试官：** 接口有十个实现，ServiceLoader 怎么知道哪些是提供者？难道扫描整个 classpath？

🙋‍♂️ **我：** 需要按约定登记提供者。

🧑‍💻 **面试官：** 登记两个实现以后，谁决定使用哪一个？又是谁负责保证配置文件被打进包里？

> SPI 把“依赖谁”改成“按约定发现谁”。发现、选择和生命周期管理，仍然是三件不同的事。

## 面试速答（60 秒版）

SPI 是服务提供者接口机制。调用方依赖稳定的服务类型，实现方按约定声明自己的提供者，运行时再通过 ServiceLoader 发现这些实现，减少调用方对具体类的硬编码。

在传统 classpath 场景中，提供者通常在 `META-INF/services/服务接口全限定名` 文件里登记实现类。在 Java 模块系统中，则通过 uses、provides 等模块声明配合发现。

ServiceLoader 的发现和实例化带有惰性，不是 load 一调用就保证把所有实现都创建完。实现缺失、构造失败或服务声明错误，也可能在遍历和获取提供者时暴露。

它主要解决发现问题，不自动替应用完成优先级、依赖注入和业务路由。遇到多个实现，要由应用明确选择规则，也不能把所有框架的扩展机制都说成同一套 Java SPI。

## 知识点详解：一份接口，怎样找到包里的实现？

### 调用方为什么不直接 new？

假设我们在做一个文件解析组件，应用只想说“请解析这份文档”，不希望每增加一种实现，就修改一处创建具体类的代码。

于是，先定义服务接口，再让不同的实现包提供解析器。应用依赖接口，通过发现机制获得可用实现。新增实现时，变化主要发生在提供者包及其声明中。

但这不意味着随便丢一个 jar 就必然生效。它还必须位于正确的运行环境，服务声明格式正确，且类加载或模块边界允许发现。[ServiceLoader 官方文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/ServiceLoader.html)分别描述了 classpath 和模块场景。

### 文件名声明“提供谁”，文件内容声明“谁来提供”

在 classpath 场景里，服务配置文件的名字是接口的全限定名，内容则列提供者的全限定类名。

这份映射很关键。ServiceLoader 不是看见某个类实现了接口，就自动扫到并注册它。没有按约定提供声明，发现过程可能根本不知道它的存在。

所以排查“本地能用，打包以后没实现”，不能只确认实现类的 class 文件还在。还要检查 `META-INF/services` 资源有没有被合并、覆盖或遗漏。多个依赖带有同名服务文件时，打包工具的资源处理规则同样重要。

![服务文件，关联的是哪两个名字？](https://note.lgdsunday.club/img/Q657/02-java-spi-serviceloader.webp)

### 发现提供者，不等于已经执行了业务方法

先取得 ServiceLoader，再遍历或读取 provider，过程中才会按 API 路径逐步加载、创建提供者。

这里要分开“知道有这个提供者”“创建出这个对象”“调用它解析文件”。一个阶段成功，并不能证明后面都没有问题。

例如配置里写错类名，或者提供者不满足创建要求，就可能在后续访问时抛出 ServiceConfigurationError。使用模块化提供者时，构造方式的规则又与传统 classpath 场景有差别，不能只背一句“必须无参构造”覆盖所有情况。

### 选择规则，要写在应用能解释的地方

假设发现两个解析器，都声称支持某个扩展名。到底取第一个，还是按配置优先级选择？如果提供者能力不同，是每次路由，还是启动时固定？

这些都不是“ServiceLoader 找到类”之后自然得到的答案。应用应当定义稳定规则，遇到重复和缺失时给出明确报错。依赖包顺序变化，不应该悄悄改变关键业务行为。

还要注意，标准 ServiceLoader 本身不提供对任意外部插件的安全隔离。加载不可信提供者，本质上是在进程内引入不可信代码，不能因为它叫插件就放松来源检查。

## 面试官继续追问

### 和 Spring 的自动装配一样吗？

有共同的扩展思想，但具体登记入口、条件判断、对象创建和生命周期不同。要分别查看所用框架版本的机制，不能把某个框架资源文件直接当成 Java 标准服务文件。

### 怎么验证打包后的发现能力？

对最终产物启动一个最小发现测试，检查预期提供者数量、名称和实际调用结果；再加入缺失、重复、错误声明用例。仅在 IDE 中运行通过，不足以证明发布包保留了所有资源。

## 面试速记卡

> - 目标：调用方依赖接口，提供者按约定被发现。
> - classpath：META-INF/services 文件关联接口和实现。
> - 模块：使用 uses、provides 等模块声明，不机械套旧配置。
> - 时机：发现、实例化、业务调用要分开，惰性过程也可能报错。
> - 工程边界：选择优先级、依赖注入、安全隔离不会自动完成。
