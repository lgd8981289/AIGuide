# CopyOnWriteArrayList 是什么？为什么适合读多写少的场景？

下面是一段模拟面试对话。

🧑‍💻 面试官：监听器列表一直在遍历，偶尔增加一个监听器，你选什么集合？

🙋‍♂️ 我：可以用 CopyOnWriteArrayList，写入时复制，读的时候不用加锁。

🧑‍💻 面试官：遍历到一半新增一个监听器，这次迭代能看到吗？

🙋‍♂️ 我：看不到，这个迭代器使用创建时的数组快照。

🧑‍💻 面试官：那修改列表里面某个监听器对象的字段，旧迭代器也完全看不到吗？列表有几十万个元素，写入还划算吗？

> 要区分「数组结构的快照」和「元素对象的状态」。复制一份引用数组，不是复制全部对象。

## 面试速答（60 秒版）

CopyOnWriteArrayList 是 Java 的一种并发列表。发生实际修改时，它通常通过复制并发布新数组，让读取和已有迭代器不必跟着修改同一份数组。

例如监听器列表原来是 A、B。创建迭代器后再加入 C，新的列表可以看到 A、B、C，旧迭代器仍然遍历 A、B。[Java API 对快照的说明](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/CopyOnWriteArrayList.html)。

因此，它适合遍历远多于修改，而且允许一次遍历不立即看到新增项的场景。

代价是写入需要复制引用数组，并可能同时保留旧数组。元素很多或频繁修改时，时间和内存成本都会增加。同时，它只提供结构快照；元素对象如果本身可变，还需要自己的同步或不可变设计。

## 知识点详解：一次增加怎样让读写分开

### 新增元素时，先准备新数组

假设列表当前指向数组 A，里面有两个监听器。一个线程准备增加第三个监听器。

它不是直接把旧数组改成更长，而是按相应写入逻辑准备数组 B，复制原有引用，再把新增项放进去，最后发布新的数组引用。修改操作之间仍然需要同步，不能理解成写线程也完全不用协调。

发布以前，读取者观察原数组；发布以后，新读取可以取得新数组。旧数组本身没有因为这个新增动作发生结构变化。

写入发布的线程安全保证来自集合实现，不能仅靠普通变量赋值模仿一份自己的“无锁 COW 列表”。

![写操作怎样发布新数组](https://note.lgdsunday.club/img/Q521/02-publish-array.webp)

### 迭代器固定的是创建时那份数组

如果迭代器 I 在增加 C 之前创建，它持有数组 A。列表随后指向 B，也不会让 I 自动切过去。

所以，一次遍历具有稳定的元素序列。监听器 C 可以从后续遍历开始接收通知，而不是在当前遍历进行到某个位置时突然加入。

普通 get 等读取与已有迭代器需要分开理解。新读取可能观察当前数组；旧迭代器持续观察自己的快照。不能说“所有读操作都永远看到旧数据”。

迭代器也不支持通过 remove、set、add 等相应方法修改快照，具体能力按 iterator／listIterator API 区分。不能因为列表支持 remove，就认为迭代器也支持。

![旧迭代器与新的 get 看到不同版本](https://note.lgdsunday.club/img/Q521/03-iterator-snapshot.webp)

右侧 A、B、C 表示 V2 中的元素范围，单次 `get(i)` 只返回指定位置的一个元素，并不是返回整份数组。多次 `get` 之间还可能发生新的写入，不能把它们当成同一次快照遍历。

### 数组里保存的仍然是同一批对象引用

现在假设监听器 A 有一个 enabled 字段。新旧数组里面的 A，可能指向同一个对象。

如果另一个线程修改 A.enabled，数组快照并不会给旧迭代器保存一份过去的 enabled 值。这个字段如何可见、是否会出现竞争，要由元素对象自己的设计决定。

因此，这种集合适合稳定地管理“当前要遍历哪些对象”，不能自动实现对象内容的历史版本。

若需要一整份不可变化的数据视图，应采用不可变元素，或在业务上创建明确的数据快照。

### 读多写少，还要加上三个条件

首先看规模。同样是每分钟写一次，复制十个引用和复制几十万个引用不是同一代价。

其次看旧快照保留多久。迭代器长期存活，就可能让旧数组无法及时回收，出现多份数组并存。

最后看读者能否接受延迟看见结构变化。监听器刚移除，已创建的迭代器仍可能持有它；如果要求“移除返回后绝不能再调用”，还需要额外状态检查和协调。

所以，适用判断不能只比较读写次数，还要看列表长度、快照寿命和业务一致性要求。

## 面试官继续追问

### 可以在遍历时调用列表自己的 remove 吗？

集合可以执行自己的修改，旧迭代器仍然遍历原快照。但这不表示旧迭代器中的对象已经消失。

还要区分对集合调用 remove，与对快照迭代器调用 remove，后者不受支持。

### size 然后 get，一定能组成安全的复合操作吗？

不一定。每个调用自己的线程安全，并不保证两个调用之间没人修改列表。

需要遍历稳定序列时，可以使用快照迭代方式；需要特定复合语义时，则应另外设计协调。

### 怎样验证是否值得选它？

用实际列表规模和修改频率比较吞吐、延迟、分配量和 GC，并加入长期迭代器用例。

本文根据 Java 25 API 解释机制，没有提供模拟 COW 的 TypeScript／Python 代码来冒充 Java 的线程安全保证，也没有虚构压测结果。

## 面试速记卡

> - 写入路径：准备新数组，再发布新引用。
> - 迭代快照：保留创建时的元素序列，不自动看到后续增删。
> - 元素状态：复制引用不等于深拷贝对象。
> - 使用条件：遍历多、修改少、规模可接受，且允许快照语义。
> - 代价检查：复制开销、旧数组寿命和业务一致性要求。
