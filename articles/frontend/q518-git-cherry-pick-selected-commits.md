# git cherry-pick 是什么？如何只合并某几个提交？

> [在线阅读与配图](https://note.lgdsunday.club/frontend/q518-git-cherry-pick-selected-commits/) · [题库目录](../../README.md)

下面是一段模拟面试对话。

🧑‍💻 面试官：功能分支有三个提交，发布分支只需要其中一项修复，怎么办？

🙋‍♂️ 我：可以 cherry-pick 那个提交。

🧑‍💻 面试官：这个提交用了前一个提交新增的函数。只选它，编译能过吗？

🙋‍♂️ 我：不一定，得检查这项修复依赖哪些改动。

🧑‍💻 面试官：后来整个功能分支再合过来，会不会重复？发生冲突以后，又怎样恢复？

> cherry-pick 选择的是「某个提交引入的改动」，没有替你证明这份改动可以脱离前后提交独立使用。

## 面试速答（60 秒版）

git cherry-pick 会把选中提交引入的改动应用到当前分支。通常会形成一个新的提交，父提交和提交身份与原来不同；某些显式快进用法需要另外区分。[官方手册](https://git-scm.com/docs/git-cherry-pick)。

它适合把一项修复从开发分支带到发布分支，又不想合并整个功能。例如只回移一个补丁。

操作前要检查提交依赖，不能看到修改行数少，就认为它可以独立应用。操作后也要重新测试，因为目标分支的代码环境可能不同。

遇到冲突，可以解决冲突并继续，也可以中止这次操作。以后合并原分支时，仍需要检查最终差异；cherry-pick 不会让两条分支自动拥有同一个历史节点。

![cherry-pick：移植提交改动](https://note.lgdsunday.club/img/Q518/01-pick-overview.webp)

## 知识点详解：一项修复怎样进入另一条分支

### 新分支得到改动，但不会得到整个开发历史

假设功能分支依次有 A、B、C 三个提交，B 修复了一个校验错误。发布分支仍停在另一条历史上。

在发布分支 cherry-pick B，Git 会尝试把 B 相对其父提交的改动应用过来。通常，新生成的 B' 以发布分支当前提交为父节点。

B 和 B' 可以含有相似补丁，但不是相同提交。提交身份还与父关系等信息有关，不只由代码是否看起来相同决定。

这和 merge 的目标不同。merge 连接分支历史；cherry-pick 选择性应用改动，不表示 A 和 C 也已经进入发布分支。

![B′ 的父提交在目标分支](https://note.lgdsunday.club/img/Q518/02-commit-replay.webp)

### 无冲突，不代表没有遗漏依赖

假设 A 新增了 validateAmount，B 改成调用这个函数。发布分支没有 A，却能够把 B 中的调用行应用进来。

Git 可能没有遇到文本冲突，但编译会失败。还有更隐蔽的情况：函数名存在，行为却与功能分支不同，代码能运行，结果仍然错误。

因此，先用 git show 看提交改了什么，再检查新增调用、配置、数据库结构和测试是否依赖前面的工作。必要时回移一组有顺序的提交，或者针对发布分支重新制作补丁。

### 一个常见的回移流程

下面是教学命令，其中提交标识需要替换成经过确认的真实值。开始前应保证工作区状态适合操作，避免把未提交修改混进去。

```bash
git switch release
git show <修复提交>
git cherry-pick -x <修复提交>
# 检查差异并执行本项目测试
```

-x 会在新提交信息中记录来源，方便后续追踪，不会因此保留原提交身份。

若出现冲突，先检查 git status，编辑冲突文件并核对结果，然后：

```bash
git add <已解决的文件>
git cherry-pick --continue
```

如果确认不应该继续这次操作，可以使用 git cherry-pick --abort。它处理的是当前进行中的 cherry-pick，不能拿来撤销任意已经结束的历史。

### 多个提交与合并提交需要额外理解

多个提交应按依赖顺序检查。范围写法的边界可能包含或排除起始提交，不清楚时先列出具体提交，不要把一串哈希当成无依赖的文件清单。

合并提交有不止一个父提交。cherry-pick 合并提交时，需要通过 mainline 选择把哪位父提交作为比较基线。选择基线不是“把整个分支再合并一次”，补丁内容会因此变化。

初学者遇到这类情况，最好先检查父关系和实际差异，再决定是否回移其中的普通提交。不能为了让命令跑完就随意指定一个数字。

## 面试官继续追问

### 以后再 merge 原分支，一定重复修改吗？

不一定。合并算法会按共同祖先和两边差异处理，完全一致的部分可能自然合并，也可能因为后续编辑发生冲突。

但 cherry-pick 没有建立完整的历史合并关系，因此仍需检查最终结果，不能承诺“一定重复”或“永远没问题”。

### 补丁在目标分支已经存在，会怎样？

可能形成空结果或需要按版本、选项决定如何处理。先确认是相同变更已存在，还是冲突解决意外丢掉了修改，不要看到空提交就直接忽略。

### 怎样验证这次回移是完整的？

除了看 diff，还要运行目标分支的相关测试，检查 API、配置和迁移依赖。提交能生成，只能证明 Git 完成了操作，不能证明补丁适合该分支。

## 面试速记卡

> - cherry-pick：选择性应用提交的改动。
> - 提交身份：通常生成新提交，不连接完整分支历史。
> - 依赖检查：无文本冲突，不代表代码可以独立运行。
> - 冲突处理：解决后 continue，放弃当前操作用 abort。
> - 验证重点：在目标分支检查差异并执行相关测试。
