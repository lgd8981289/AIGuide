# CSS content-visibility 是什么？和 display:none、虚拟列表有什么区别？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/frontend/q748-css-content-visibility-contain-intrinsic-size/) · [题库目录](../../README.md)

*以下对话为教学模拟，用来讲解这道题。*

🧑‍💻 面试官：一个很长的文章页，屏幕外还有几百个复杂章节，怎样减少首屏渲染工作？

🙋‍♂️ 我：可以给屏幕外的章节设置 display:none，滚动到附近再显示。

🧑‍💻 面试官：那滚动条的高度从哪里来？页面内搜索还能找到那些内容吗？

🙋‍♂️ 我：直接隐藏会改变布局，也影响查找。

🧑‍💻 面试官：如果改成 content-visibility:auto，它和只创建少量 DOM 的虚拟列表，是同一种优化吗？

> 先问省掉的是哪一部分工作。跳过屏外内容的渲染，和根本不创建那些 DOM，是两条不同路线。

## 面试速答（60 秒版）

content-visibility 可以让浏览器跳过暂时不需要显示的内容渲染。长页面常用 auto，由浏览器根据内容是否与用户相关等条件，决定是否跳过后代的布局和绘制；不能把它理解成开发者精确指定“超出屏幕一像素就不画”。

auto 不会把 DOM 删除，内容仍应可被页面内搜索和辅助技术访问。display:none 则不生成布局盒，也不会保留原来那块空间，两者用途不同。

为了避免跳过内容时尺寸失真，可以配合 contain-intrinsic-size 提供占位估计，auto 长度组合还能在测量后使用记住的实际尺寸。

虚拟列表则主动限制实际渲染的项目和 DOM 数量。content-visibility 不会自动减少组件创建、数据量或 JavaScript 执行，所以几万条交互复杂的数据，仍可能需要虚拟列表。

## 知识点详解：内容还在，浏览器可以暂时少画一点

### 长页面的成本，不只发生在眼前这一屏

咱们假设一个文档页，已经把所有章节放进 DOM。读者只看第一屏，但后面的复杂内容也可能参与样式、布局和绘制相关工作。

content-visibility:auto 为浏览器提供一条优化路径。暂时不相关的章节，可以跳过部分渲染工作；滚动靠近或因为搜索、焦点等原因需要它时，再正常处理。

这里负责判断的是浏览器。不能用它承诺一个固定预加载距离，也不能在元素仍然与用户相关时，要求浏览器必然跳过。

一个针对纵向章节的 CSS 示例是：

```css
.chapter {
  content-visibility: auto;
  contain-intrinsic-block-size: auto 600px;
}
```

CSS 配置不需要对应的 TypeScript 或 Python 实现。这段 600px 是假设章节的尺寸估计，不是推荐所有网站都照抄的性能参数。

### 不做内部布局，章节高度怎么知道？

如果章节内部暂时没有布局，浏览器就不能像正常渲染时那样，靠全部后代精确算出高度。没有合理占位时，滚动条长度或内容位置可能发生明显变化。

上面的 intrinsic block size 为纵向尺寸提供估计。auto 600px 表示尚未获得合适的记忆尺寸时使用估计；内容实际渲染后，浏览器可以记住其尺寸，之后再次跳过时使用。

这不是给章节设置一个永远不变的 height。章节真实内容比估计长，进入正常渲染后仍然需要调整。因此，要选接近实际内容的估计，并检查图片加载、字体变化和窗口缩放后的滚动体验。

[CSS Containment 规范](https://drafts.csswg.org/css-contain-2/#content-visibility)定义的是渲染跳过与包含关系，不是内容加载协议。图片请求、业务脚本、计时器和 React 组件执行，都不会因为写上这个属性，就自动按同样的方式暂停。

![auto估计与实际尺寸记忆的两阶段关系](https://note.lgdsunday.club/img/Q748/02-intrinsic-placeholder.webp)

### auto、hidden、display:none 不能混为一谈

auto 的目标是优化当前不需要渲染的内容，同时保留它参与文档功能的能力。浏览器查找命中屏外文字时，内容仍然应该能被定位。

content-visibility:hidden 则明确跳过内容，并使被跳过的内容不参与查找、焦点等用户代理功能。外层元素自身仍然可以有布局盒，不能把它直接等同为整个元素 display:none。

display:none 不生成相应布局盒，原来内容的占位也不再照旧存在。需要折叠一段 UI 时，它可能正好合适，但不是长文屏外渲染优化的直接替代。

访问性还要单独检查。auto 的屏外内容仍可能处于无障碍树中；内部某些隐藏状态不能只凭“屏幕上没有显示”判断。真正不应被读到的内容，需要按语义和交互状态正确处理，不能随手给整个章节 aria-hidden，把正文一起藏掉。

### 为什么它代替不了虚拟列表？

虚拟列表通常只把当前窗口附近的数据项目渲染出来，其他位置由占位尺寸表示。项目组件的数量、DOM 数量因此都能减少。

content-visibility 让已经存在的内容少做一部分渲染工作。假设十万条记录早就创建成组件，它不会把这些实例和对应数据收回。

因此，长文、分区内容可以先评估 CSS 优化；超长交互列表要结合组件数量、内存和更新成本判断是否虚拟化。二者也可以配合，但先量出瓶颈，不要同时打开一堆优化以后，只剩下一句“好像快了”。

## 面试官继续追问

### 读取屏外元素的尺寸会怎样？

某些几何读取可能迫使浏览器处理原本能跳过的内容。不要一边要求跳过布局，一边每帧读取全部后代的位置；在性能面板里检查是否把收益抵消了。

### auto 会自动暂停屏外 canvas 动画吗？

不会保证。应用自己的绘制循环需要自己处理，可以评估 contentvisibilityautostatechange 等状态通知和实际浏览器支持，明确什么时候停止自己的工作。

### 怎样验证有收益又没破坏阅读？

对照同一份长文的渲染时间与主线程工作，再测试滚动、页面内搜索、锚点、键盘焦点和读屏。旧浏览器不支持时应保持可读，而不是以这个属性承担内容显隐的唯一正确性。

## 面试速记卡

> - auto：DOM 仍在，浏览器可以跳过暂时不相关内容的渲染。
> - 占位尺寸：估计帮助保留空间，auto 组合可利用记住的尺寸。
> - display:none：不生成布局盒，不是同一种优化。
> - 虚拟列表：进一步减少实际组件和 DOM 数量。
> - 验收：性能之外，还要检查搜索、滚动、焦点与访问性。
