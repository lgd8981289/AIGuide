# MCP 为什么改为无状态协议？2026-07-28 版本如何处理能力声明与兼容？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/agent/q642-mcp-stateless-protocol-versioning/) · [题库目录](../../README.md)

*下面是用于讲题的模拟面试对话。*

🧑‍💻 面试官：MCP 请求第一次到 A 实例，第二次到 B 实例，为什么旧实现可能出问题？

🙋‍♂️ 我：如果 B 依赖 A 保存的协议会话，换实例以后就缺少之前的状态。

🧑‍💻 面试官：那新版无状态以后，用户的任务记录都不能保存了？

🙋‍♂️ 我：取消的是隐含的协议会话依赖，业务数据还是可以保存。

🧑‍💻 面试官：老客户端还会发 initialize，能直接把服务端切到新版吗？

> 讨论 MCP 的会话机制，先说版本。协议请求不依赖上一次握手，和应用是否保存任务，是两件事。

## 面试速答（60 秒版）

MCP 的 2026-07-28 版本采用无状态协议核心，取消了旧的 initialize/initialized 交换和 Mcp-Session-Id。请求需要携带解释自身所需的版本、客户端信息和能力信息，减少对之前协议会话的依赖。

这样，请求更容易交给不同服务实例处理。客户端如果想先了解服务端能力，可以使用可选的 server/discover，而不必把它理解成旧握手换了一个名字。

但无状态不要求业务也不保存数据。比如一次资料处理任务，仍然可以生成明确的任务句柄，后续请求带着它访问业务状态，并在每次访问时检查权限。

升级时要核对客户端、服务端和 SDK 的协议支持。旧版的握手与会话语义仍然属于旧版实现，不能只删一个 Header，就宣称完成了新版迁移。

## 知识点详解：不靠旧会话，请求怎样被正确理解？

### 旧会话依赖给扩容增加了什么条件？

假设有两个 MCP 服务实例。如果服务端要靠先前的初始化结果解释本次请求，后续请求就需要找到那份上下文。部署时可能需要固定路由到原实例，或者管理共享状态。

新版把解释请求所需的信息放进当前交互，减少这类协议级依赖。这是官方 [2026-07-28 发布说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)介绍无状态核心时强调的变化。

这里的“更容易扩容”只描述协议层。数据库连接、任务数据、限流和认证仍然有自己的部署要求，不能由此推断所有服务都不再需要共享存储。

### 能力发现可以提前做，但不是必经握手

新版提供 `server/discover` 供客户端了解服务端能力。它是可选发现步骤，不能再按“必须先握手才能发任何正常请求”的旧理解解释所有调用。

版本与能力信息也不能互相替代。版本说明双方按哪套协议规则解释消息，能力说明支持哪些功能；知道版本，不代表所有扩展都已经启用。无状态提案见 [SEP-2575](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2575)，实现时还应以最终发布规范和所用 SDK 为准。

另外，请求中声明“客户端是谁”不等于身份已经通过认证。认证凭据、服务端权限和声明信息的可信来源仍需要单独处理。

![发现能力，和维持会话不同](https://note.lgdsunday.club/img/Q642/02-mcp-stateless-protocol-versioning.webp)

### 业务状态用明确对象承接

假设工具启动一项文档处理任务，返回一个任务句柄。后续查询携带这个句柄，服务端就能找到任务进度，而不必偷偷假定“这个连接最近启动的任务就是它”。

这使数据依赖更清楚，也方便把请求路由到其他实例。相关设计见 [显式状态句柄提案 SEP-2567](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2567)。

不过，句柄本身未必是授权凭证。服务端仍要确认任务属于当前主体，不能因为用户猜中了一个 ID 就返回进度或内容。任务句柄、HTTP 连接和用户身份也不应该共用一个概念。

![协议会话没了，任务记录仍可保存](https://note.lgdsunday.club/img/Q642/03-mcp-stateless-protocol-versioning.webp)

### 迁移要检查整条协议路径

升级前，先列出实际客户端和服务端支持的版本。再检查初始化、元信息、能力发现、传输请求头，以及原来依赖持久双向连接的交互怎样迁移。

可以用两个服务实例交替接收请求，确认不依赖原进程的隐藏协议数据；再测试旧客户端和未知版本，检查是否得到明确的兼容处理，而不是偶尔成功、偶尔失败。

本文核对了官方发布说明和提案入口。新版 versioning 页面本轮访问失败，未把它列为已成功读取的依据，也没有据此编造完整请求 Schema 或 SDK 迁移代码。

## 面试官继续追问

### 无状态是不是就不用保存登录了？

身份认证和协议会话不是同一层。访问令牌、授权服务器和应用自己的登录状态仍按各自机制处理，不能把取消 Mcp-Session-Id 当成取消认证。

### 现在线上还在握手，是否说明实现错误？

先确认协商和实现的是哪个版本。旧版本采用旧流程并不因为新规范发布就自动变成错误。真正需要检查的是文档、SDK 和对端行为是否匹配。

### 业务句柄可以一直保存不清理吗？

应给任务定义归属、保留期、删除和失效行为。协议不保存隐含会话以后，应用更需要把这些业务生命周期明确写出来。

## 面试速记卡

> - 无状态核心属于 MCP 2026-07-28 的版本变化。
> - 当前请求携带所需协议信息，可选发现不等于旧必经握手。
> - 协议无状态不限制应用保存业务状态。
> - 显式句柄标识对象，访问权限仍由服务端判断。
> - 迁移检查双方、SDK 和完整交互，不能只改一个 Header。
