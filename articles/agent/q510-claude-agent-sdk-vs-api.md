# Claude Agent SDK 是什么？和直接调用 Claude API 有什么区别？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/agent/q510-claude-agent-sdk-vs-api/) · [题库目录](../../README.md)

下面是一段模拟面试对话。

🧑‍💻 面试官：项目已经能调用 Claude API，换成 Agent SDK 有什么变化？

🙋‍♂️ 我：SDK 把接口封装得更方便，还提供了一些工具。

🧑‍💻 面试官：模型要求读文件以后，谁去读？读完以后，谁把结果送回模型？

🙋‍♂️ 我：Agent SDK 已经有相应的运行循环，不需要每一步都由应用重新组织。

🧑‍💻 面试官：那给它一个服务器账号，是否就能直接上线？多位用户的工作目录和写文件权限，又是谁负责？

> 这里真正要讲清的是「责任变在哪里」：SDK 接管一部分 Agent 执行，应用仍然要把运行环境和授权安排好。

## 面试速答（60 秒版）

直接调用 Claude API，主要是把输入发给模型，再处理模型返回的内容。模型如果提出工具调用，应用通常还要执行工具、回填结果，并控制后面的循环。使用客户端提供的工具运行助手时，也要核对它实际接管了哪些部分。

Claude Agent SDK 提供的范围更大。它把 Claude Code 的 Agent 运行循环、内置工具和上下文管理能力，以库的形式提供给 Python 和 TypeScript 应用。[官方说明](https://code.claude.com/docs/en/agent-sdk/overview)。

例如做一个读代码、修改文件、运行测试的助手，SDK 可以处理连续的工具执行和模型交互，开发者不用从零写这套循环。

不过，SDK 的运行进程仍然由我们部署和维护。工作目录、用户隔离、工具权限、执行预算和任务验收，都需要应用继续负责。它适合需要完整 Agent 行为的任务；如果只做一次分类或文本生成，直接调用模型 API 通常更清楚。

## 知识点详解：从修改代码看 SDK 接管了哪些工作

### 直接调用 API，拿到的首先是模型输出

假设用户要求：“找到这个项目中导致测试失败的代码，修改以后重新执行测试。”

如果应用只调用模型 API，模型可能先返回一个工具请求，要求读取文件。应用需要检查这个请求，真正读取文件，再把读取结果放进下一次请求。

后面模型还可能要求搜索引用、修改文件、执行命令。每一轮都要处理工具结果、错误和结束条件。

这里不能只看 API 名称。客户端 SDK 也可能提供工具运行辅助功能，但要逐项核对：它是否负责内置文件工具、会话保存和执行环境，而不只是帮助重复发送请求。

### Agent SDK 把运行循环作为可用能力交给应用

使用 Agent SDK 后，应用给出任务和配置，SDK 运行能力负责把模型判断、工具执行、结果回填串起来。

一个任务可以经历“读文件 → 发现相关调用 → 修改 → 执行测试 → 根据错误继续修改”。它不需要开发者预先规定每个文件名，却仍然只能使用已经开放的能力。

应用拿到的不只是最后一句话，还可以处理执行中的消息和结果，向用户展示进度。任务什么时候算交付，也不能只看“模型停止了”。

假设模型说测试通过，但进程退出码不为零，应用应以实际测试结果为依据。这一层判断仍然属于自己的产品逻辑。

![工具请求怎样进入下一轮](https://note.lgdsunday.club/img/Q510/02-tool-loop.webp)

### 权限配置决定工具请求能不能执行

SDK 提供权限模式、规则和审批等控制方式，具体行为应按所用版本配置。[权限文档](https://code.claude.com/docs/en/agent-sdk/permissions)。

例如，代码检查任务只需要读文件，就不要同时开放写文件和任意命令。需要修改时，也可以让敏感动作先经过确认。

更重要的是，工具层限制还要与运行环境配合。即使提示词说“不要访问其他用户”，同一个进程如果仍能读取全部用户目录，隔离就没有真正成立。

因此，可以为任务准备独立目录，在环境中限制可访问文件和网络，再给 SDK 配置允许的工具。涉及生产数据的工具，应在服务端根据可信身份重新授权。

![允许读文件，不代表允许写文件](https://note.lgdsunday.club/img/Q510/03-permission-gate.webp)

图中是配置只读策略和受控环境后的示意。沙箱、网络边界和授权规则仍需配置，不是引入 SDK 后自动获得的保证。

### SDK 是库，托管服务是另一种交付方式

Agent SDK 会运行相应的 Claude Code 能力，承载它的进程由使用方运维。[部署说明](https://code.claude.com/docs/en/agent-sdk/hosting)。

所以，我们还要考虑任务持续多久、服务重启后如何恢复、临时文件怎样清理，以及取消请求如何到达执行进程。这和发出一次短 HTTP 请求不一样。

官方的 Managed Agents 是不同的托管形态，不能因为名字都带 Agent，就认为 SDK 自带云端持久运行。

选型时可以把责任列出来：模型推理由谁提供，Agent 循环由谁提供，进程和文件由谁维护，敏感动作由谁审批。这样比只比较“哪套 API 代码少”更容易选对。

![用了 SDK，仍要管理运行环境](https://note.lgdsunday.club/img/Q510/04-process-lifecycle.webp)

## 面试官继续追问

### SDK 可以替代项目里的业务工具吗？

不能完全替代。文件和命令工具可以完成通用操作，业务系统还需要自己的接口、参数验证和身份检查。

例如退款工具必须根据当前账号校验订单和金额，不能因为模型生成了合法参数就执行。

### 怎么验证只读模式真的有效？

准备一个明确要求修改文件的测试任务，再检查它是否被权限配置拒绝，目录内容有没有变化。还要覆盖间接路径，例如通过命令工具执行写操作。

不能只检查 SDK 返回了什么说明，要核对执行环境的实际结果。

### 模型已经输出最终答案，还要做哪些检查？

对代码任务，可以检查文件差异、测试退出状态和任务范围；对报告任务，可以检查交付文件与来源。任务验收条件应在执行前定义，避免让 Agent 自己重新解释“完成”。

## 面试速记卡

> - API 调用：获得模型输出，工具执行与循环责任要按实际客户端确认。
> - Agent SDK：提供可嵌入的 Agent 循环、工具和上下文管理能力。
> - 运行责任：SDK 进程、文件目录和任务生命周期由应用维护。
> - 权限边界：工具规则与环境隔离要一起设计。
> - 完成判断：检查真实产物和执行结果，不能只听模型宣布成功。
