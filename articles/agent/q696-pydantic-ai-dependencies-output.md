# PydanticAI 是什么？依赖注入和类型化输出如何组织 Agent？

>
> [在线阅读与配图](https://note.lgdsunday.club/agent/q696-pydantic-ai-dependencies-output/) · [题库目录](../../README.md)

*下面是一段用于讲题的模拟面试对话。*

🧑‍💻 面试官：PydanticAI 和直接调用模型 API 相比，主要多做了什么？

🙋‍♂️ 我：它把模型调用、工具执行、依赖传递和输出校验组织成一个 Agent，可以用 Python 类型描述工具和结果。

🧑‍💻 面试官：查询客户资料需要当前登录人的身份，这个参数也让模型填吗？

🙋‍♂️ 我：身份应该由应用传进去，工具从运行上下文中取得。

🧑‍💻 面试官：最后结果通过了 Pydantic 校验，就说明客户资料查对了，而且能直接退款了？

> 类型把“数据应该长什么样”说清楚；可信依赖、真实数据和业务授权，还得分别检查。

## 面试速答（60 秒版）

PydanticAI 是面向 Python 的 Agent 开发框架。开发者可以给 Agent 配置模型、指令、工具、依赖类型和输出类型，由框架组织模型与工具之间的运行过程。

这里比较值得注意的是依赖和模型参数的区别。例如查询订单时，订单号可以由模型从用户问题中提取；当前用户是谁、使用哪条数据库连接，则应该由应用在运行时传入，工具通过 `RunContext` 取得这些依赖。

输出类型可以使用 Pydantic 模型，帮助应用得到有明确字段、能经过校验的结果。不过，字段合法不代表结论真实，更不代表已经获得操作权限。

因此，Python 项目希望把工具、依赖和返回结果的契约写得明确时，可以考虑 PydanticAI。真正接入业务以后，仍然需要处理权限、重试、状态保存和结果验收，不能把类型安全理解成任务自动正确。

## 知识点详解：模型参数和应用依赖，要走两条不同的路

### 先把 Agent 看成一份可以复用的配置

假设咱们要做一个订单查询助手。它允许查询订单和物流，最后返回“订单状态、物流摘要、是否需要人工处理”。

这时，Agent 定义里需要说明允许使用哪些工具、结果包含哪些字段。一次具体运行还需要用户的问题、当前身份，以及已经建立的数据库连接。

两部分不要混在一起。Agent 配置可以复用，用户身份却会随着请求改变。如果为了省事把用户 ID 写进全局可变字段，两个请求并发执行时，就可能拿错身份。[官方 Agent 说明](https://pydantic.dev/docs/ai/core-concepts/agents/)把 Agent 的配置与运行入口分开介绍。

### 依赖类型告诉代码能取什么，依赖实例才是这次真的用什么

`deps_type` 描述依赖的类型；调用 Agent 时传入的 `deps`，才是本次运行的具体依赖。工具通过 `RunContext` 的依赖入口访问它们。

例如，依赖里可以保存经过登录校验的用户 ID 和订单服务客户端。模型看到的工具参数只需要订单号，不需要一个允许它随便填写的 `current_user_id`。

那么，依赖没有出现在工具参数里，是不是就绝对不会泄露给模型？

也不能这样理解。如果工具把整个依赖对象转成字符串返回，或者动态指令主动写进了密钥，数据照样会进入模型输入。隐藏参数只是避免模型负责生成它，并不是一层自动的数据脱敏。依赖的定义、传入与读取方式可核对[官方依赖文档](https://pydantic.dev/docs/ai/core-concepts/dependencies/)。

![订单号让模型填，用户身份由应用给](https://note.lgdsunday.club/img/Q696/02-pydanticai-trusted-deps.webp)

### 输出校验处理的是约定，不替你证明事实

假设约定结果中必须有 `order_id`、`status` 和 `needs_human`。框架可以帮助检查字段类型和约束；模型给了不符合约定的结果时，也可以按配置反馈错误、继续尝试。

但一个真实存在的订单号，也可能属于另一个用户。一个类型正确的“已退款”，也可能只是模型猜的。

因此，结果要分层看。先检查结构能否被应用接住，再确认订单数据来自可信工具，最后检查当前动作是否经过业务规则与授权。高风险写入应该由受控工具完成，不能在“输出校验成功”后无条件执行。

官方还区分了工具输出、模型原生结构化输出等[输出方式](https://pydantic.dev/docs/ai/core-concepts/output/)。选择哪一种，需要看模型和供应商的实际支持，不是写一个类型就保证所有模型具有相同约束能力。

![字段合法，不等于这笔退款能执行](https://note.lgdsunday.club/img/Q696/03-pydanticai-validation-boundaries.webp)

### 框架可以换掉一些胶水代码，业务责任不会一起消失

如果项目只做一次文本改写，直接调用模型接口就可能够用。工具、依赖和输出约定逐渐增多以后，统一的运行结构更容易维护和测试。

可以用假的订单服务替换真实依赖，分别验证“自己的订单、他人的订单、订单不存在、服务超时”。再故意提供字段不合法或业务事实不符的结果，确认系统在哪一层拒绝。

这篇介绍框架职责，没有运行真实模型或订单服务，也没有给出性能对比。PydanticAI 是 Python 框架，不能把 TypeScript 中相似的 Schema 库包装成同一套官方实现。

## 面试官继续追问

### 和直接使用 Pydantic 有什么区别？

Pydantic 主要处理数据建模与校验。PydanticAI 在此基础上组织 Agent 的模型调用、工具、依赖和输出过程。只需要校验请求体时，不一定需要引入整套 Agent 框架。

### 工具超时后，让框架重试就可以了吗？

查询通常可以按条件重试，写操作则必须先弄清第一次是否成功。类型检查无法识别一笔退款是否已经在远端完成，仍需要业务请求标识、结果查询和幂等机制。

### 使用 Pydantic 模型，能完全防止幻觉吗？

不能。它可以限制形状和部分取值约束，无法单凭类型证明资料真实。需要证据的字段，应关联实际查询结果，并用固定任务和人工复核检查事实错误。

## 面试速记卡

> - Agent 配置模型、工具、依赖类型和输出约定，运行时再接收本次输入。
> - 模型填写业务参数，可信身份和服务连接由应用传入。
> - RunContext 让工具取得运行依赖，不自动保证数据不会进入模型。
> - 输出类型合法、事实真实、动作获准，是三项不同检查。
> - PydanticAI 属于 Python 生态，业务幂等与恢复仍需独立设计。
