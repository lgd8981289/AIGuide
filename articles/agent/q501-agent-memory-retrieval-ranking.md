# Agent 如何检索历史记忆？为什么不能只按向量相似度排序？

*下面是一段模拟面试追问。*

🧑‍💻 面试官：Agent 记忆越来越多，怎样选出这次需要的内容？

🙋‍♂️ 我：把问题转成向量，取最相似的几条。

🧑‍💻 面试官：旧记忆写“我喜欢 TypeScript”，新记忆写“这个项目改用 Python”。哪条更相似，就用哪条吗？

🙋‍♂️ 我：还要看适用范围和时间。

🧑‍💻 面试官：那用户问“这个项目上个月用什么语言”，你仍然只保留最新记录吗？

> 相似度回答的是「像不像」，不是「这次该不该用」。当前查询和历史查询，可能需要不同的记忆。

## 面试速答（60 秒版）

Agent 检索历史记忆时，不能只根据向量相似度决定使用哪条内容。表达相似，不代表事实仍有效，也不代表属于当前用户或当前项目。

可以先根据可信身份、任务范围和查询时间缩小候选，再结合相关性、时间因素、重要性与来源选择内容。Generative Agents 论文中的记忆读取就考虑了相关性、近期性与重要性，不过这只是一个具体设计，不是通用评分标准。[原始论文](https://arxiv.org/abs/2304.03442)。

如果用户问当前偏好，已经被纠正的旧信息不应该继续作为当前事实。如果问过去的情况，历史记录反而可能是必要证据。

所以，检索目标不是找出“最像的一段文字”，而是给模型提供足以回答当前问题、条件仍然匹配的历史信息。

![解释记忆适用性不能仅按向量相似度](https://note.lgdsunday.club/img/Q501/01-memory-ranking-overview.webp)

## 知识点详解：一次查询，先确定自己到底在找什么

### 相似度不能判断事实是否适用

假设用户最初说：“我平时喜欢用 TypeScript。”

后来，他又补充：“当前这个项目是 Python，示例也请用 Python。”

这两条信息并不一定互相矛盾。一条说一般偏好，另一条限定当前项目。如果问题是“帮我写这个项目的示例”，项目范围就很关键。

如果应用只把两句话当作普通向量片段，哪条分数高就用哪条，那么结果可能随着问题措辞变化。模型看到的信息虽然很像，却不适合当前任务。

因此，在候选记忆里保留用户、项目、来源和时间等信息，不只是为了方便存储，也是在帮助读取时做判断。

### 查询里的时间，要影响过滤条件

再假设这个项目三月用 TypeScript，六月已经迁移到 Python。

用户问“现在应该补哪种示例”，需要的是当前有效情况。用户问“三月的教程为什么使用 TypeScript”，需要的则是三月的背景。

后一种任务如果把旧记录全部过滤掉，就会丢失正确答案。

应用可以先区分当前状态查询与历史时间查询。对于明确的历史问题，保留对应时间的记录和来源；对于“上次”“最近”这样有歧义的表达，如果不能可靠定位，就向用户确认，而不是凭最新更新时间猜。

这是一种检索策略，不意味着所有记忆库都支持相同的时间字段或过滤语法。

![说明当前查询与历史查询不能统一只取最新](https://note.lgdsunday.club/img/Q501/02-current-history-query.webp)

### 先排除不该出现的内容，再讨论排名

用户范围应由服务端身份确定，不能从模型生成的参数里任意取值。

在允许的数据里，再检查记录是否属于当前项目、是否已撤销，以及查询要的时间是否匹配。这些不是靠“给越权结果扣一点分”解决的条件。

之后才讨论哪些内容更能回答问题。相关性很重要，但有些低频信息也不能忽略。例如用户明确说“不要发送包含个人信息的示例”，即使这条记录很久没用，当前任务仍然可能需要。

重要性也不是抽取模型标了“重要”就直接信任。这个标签可以参与候选选择，但不能因此获得更高权限或覆盖当前要求。

![展示访问约束与排名分开，越权内容不应进入候选](https://note.lgdsunday.club/img/Q501/03-filter-before-rank.webp)

### 最终送入模型的内容，还要说明依据

假设检索到了项目语言的两条记录。不要只把正文拼在一起，让模型自行猜谁覆盖谁。

应用可以保留简短的来源与条件，例如“当前项目要求 Python，来自用户本轮确认”“历史教程使用 TypeScript，适用于三月版本”。

如果资料不足，可以不给确定结论，或先查权威项目配置。记忆是辅助信息，不能让模型把不确定的历史当成已经证实的现实。

当前资料的失效处理可以继续看 Q060；本题重点是读取时怎样解释查询与候选之间的关系。

## 面试官继续追问

### 能不能把时间衰减权重调大，让旧记忆自然消失？

不能当成通用办法。

新信息不一定更重要，历史问题更需要旧证据。可以针对某类偏好做时间策略，但应先验证它是否会误伤长期限制或历史查询。

### 向量检索命中了，但模型仍然用错，怎样排查？

把检索候选与最终输入分开看。

先确认正确记忆有没有在候选中，再看是否被过滤、被挤出，或者丢掉了范围和来源。证据完整仍然用错，再检查模型如何理解了这些条件。

### 排名策略怎样评测？

用同一组事实构造当前查询、历史查询、项目切换和证据不足的问题，记录需要的来源 ID。

不只看命中数量，也看模型是否把过期事实用作当前事实、是否引入其他用户信息，以及是否在没有证据时编出了答案。

## 面试速记卡

> - 相似度：帮助找到候选，不单独证明事实适用。
> - 范围过滤：身份、项目与有效状态先确定，再讨论排名。
> - 时间条件：当前查询和历史查询需要不同证据。
> - 排名取舍：相关性、时间和重要性按任务验证，不套万能权重。
> - 最终输入：保留必要来源与条件，不能只拼记忆正文。
