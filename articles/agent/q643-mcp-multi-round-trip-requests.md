# MCP 的 MRTR 是什么？无状态请求如何承接服务端的补充输入请求？

> [在线阅读与配图](https://note.lgdsunday.club/agent/q643-mcp-multi-round-trip-requests/) · [题库目录](../../README.md)

*下面是用于讲题的模拟面试对话。*

🧑‍💻 面试官：MCP 工具执行到一半发现缺少地区，无状态协议里怎么向客户端要信息？

🙋‍♂️ 我：可以返回还需要输入的结果，由客户端拿到信息后继续请求。

🧑‍💻 面试官：客户端再次发送，难道把前面的副作用也再做一遍？

🙋‍♂️ 我：补充输入的再次请求，需要和原任务对应，也要处理重复执行。

🧑‍💻 面试官：用户补了地区，是不是连付款也一起同意了？

> MRTR 让补充输入跨请求往返传递。信息补齐、执行授权和动作去重，仍然各有自己的判断。

## 面试速答（60 秒版）

MRTR 是 Multi Round-Trip Requests，用多个请求往返承接一次交互过程中需要补充输入的情况。它是 MCP 2026-07-28 无状态核心配套的新机制。

当服务端还需要客户端提供信息时，可以返回 `resultType: "input_required"`，并说明需要处理的输入请求。客户端处理以后，再次发起原调用，把回答放进 `inputResponses`。

因此，服务端不需要为了这次补问一直占着一条双向请求流。客户端接到需要输入的结果后，负责怎样呈现、收集和带回答回来；服务端再验证回答，决定后续处理。

这里的再次请求不等于可以随便重复写操作。应用还要确认原任务、参数版本和已执行结果；用户提供一个字段，也不自动等于授权其他高风险动作。

## 知识点详解：缺一个输入，为什么要多走一趟？

### 从一个明确的缺参场景开始

假设工具要生成一份地区政策报告，用户只说了主题，没有指定地区。不同地区会改变资料范围，所以服务端需要补充信息。

旧式持久双向交互可以由服务端在连接里发起请求。无状态核心下，需要把“还缺什么”变成本次返回的一部分，再由客户端带着回答重新请求。[官方发布说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)介绍了 MRTR 的这条路径。

它传递的是补充输入请求，也可以承接不同类型的客户端参与。具体字段与支持方式要按协议及 SDK 核对，不能把所有情况都写成“服务端直接弹一个网页表单”。

### 一次交互可以拆成四个可观察动作

先是客户端发起报告工具调用。然后服务端返回需要输入，要求明确地区。客户端向用户收集到答案，最后再次提交原调用并携带 `inputResponses`，服务端才能继续处理。

“再次提交原调用”说的是继续这项交互，不是新建一个毫不相关的报告任务。输入请求和回答需要能够对应，服务端也不能把上一个报告的回答错误地用到另一个报告里。

相关机制的设计入口见 [SEP-2322](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2322)。本文只展示已核对的关键字段与过程，没有把提案讨论中的旧字段拼成一份声称可直接运行的完整协议报文。

![补充回答要对上原来的问题](https://note.lgdsunday.club/img/Q643/02-mcp-multi-round-trip-requests.webp)

### 再次请求，最容易混淆哪几种情况？

第一种是正常补齐输入。原任务没有完成，客户端带回所需答案，后续处理继续。

第二种是网络重发。服务端已经收到回答，但客户端没有拿到结果，又提交了一次。此时不能再次创建报告、重复计费或执行其他写动作。应用应使用稳定的业务身份检查已有进度和结果。

第三种是参数变了。用户补问时不仅提供地区，还改变了主题。这时需要重新判断哪些已有工作还能复用，不能把新旧任务条件不加检查地拼起来。这部分属于应用业务设计，MRTR 不会替开发者决定。

![再次发送，为什么要分清三种情况？](https://note.lgdsunday.club/img/Q643/03-mcp-multi-round-trip-requests.webp)

### 补充信息之后，仍要检查权限和范围

例如客户端带回“上海”，服务端要确认它确实是在回答当前任务的地区问题，值也符合预期范围。如果答案或任务引用被篡改，需要拒绝或重新澄清。

同时，收集地区没有授予发布报告、扣费或发送邮件的权限。如果后续包含这些动作，应按已有授权范围决定是否可执行；需要确认时，确认内容要对应具体对象与动作。

记录过程时，可以保存任务标识、待输入项、收到的回答和状态变化。敏感回答不要无差别写进日志。客户端退出、用户拒绝或等待过期时，也要让任务进入明确状态，不能永远保持“处理中”。

![补了地区，没有顺便授权发送邮件](https://note.lgdsunday.club/img/Q643/04-mcp-multi-round-trip-requests.webp)

### 这套机制怎样测？

至少测试正常回答、拒绝回答、重复提交、回答错配和中途改参数。再把相邻请求交给不同服务实例，确认它们能按明确的交互数据找到同一个业务任务。

检查的重点是回答有没有匹配、任务有没有继续，以及是否产生重复效果。连接没有一直打开，只说明传输方式变化，不足以证明任务可靠。本文没有运行 MRTR SDK 联调。

## 面试官继续追问

### MRTR 和重新问模型一次有什么区别？

MRTR 是客户端与服务端承接输入请求的协议机制。客户端可能调用模型，也可能询问用户或处理其他受支持的输入类型。不能把协议往返简单等同于一次额外模型生成。

### 服务端可以把任务状态全塞进客户端返回值吗？

可以有不同状态承接设计，但必须考虑完整性、保密、过期和主体绑定。客户端带回的数据不能未经验证就当作已审批状态；具体方案取决于 SDK 和应用约束。

### 是否可以把它当成普通失败重试？

需要输入是一种明确的交互状态，客户端要先处理待输入项。网络失败重试则处理交付不确定性。两条路径可能都导致再次发送，但触发原因与检查条件不同。

## 面试速记卡

> - MRTR 用多个请求往返承接补充输入，属于新版 MCP 机制。
> - input\_required 表示还需要输入，inputResponses 携带处理结果。
> - 再次请求要对应原交互，不能混入其他任务的回答。
> - 正常补齐、网络重发和参数变化分别处理。
> - 补信息不自动扩大授权，业务副作用仍需去重。
