# Agent 上下文太长怎么办？压缩与关键信息保留

*下面是一段教学模拟，排查案例为假设场景。*

🧑‍💻 面试官：“Agent 查了几十轮日志，上下文快满了，你怎么办？”

🙋‍♂️ 我：“保留最近几轮，把前面的聊天总结一下。”

🧑‍💻 面试官：“用户最开始说只查原因、不改配置，这句话被总结掉了呢？”

🙋‍♂️ 我：“操作限制要单独保存，压缩后也要带进下一轮。”

🧑‍💻 面试官：“那已经排除的原因、尚未验证的猜测，还有正在等待结果的调用，你准备怎样交给下一轮？”

> 压缩前先想清楚，Agent 下一步要依据什么做判断。目标、限制、证据和执行状态，都要有明确去处。

## 面试速答（60 秒版）

Agent 的上下文压缩，是在有限的输入空间里，为下一步保留必要信息。只总结聊天内容，容易漏掉操作限制，也可能把猜测写成结论。

我会先给模型输出和后续工具结果预留预算，再处理重复内容和超长工具输出。仍然放不下时，把已完成阶段整理成摘要，保留结论、来源和待验证事项。当前目标与限制从任务状态补入，最近仍相关的消息和工具调用关系继续保留。

原始日志可以放在外部，下一轮按查询编号取回所需片段。压缩完成后，要检查 Agent 是否重复排查、忘记限制或误判执行状态，再比较 Token、延迟和压缩成本。

这样既能控制输入大小，也能检查任务是否继续做对。

## 从一份排查记录，看懂上下文压缩

### 下一轮调用模型，究竟要带上什么？

假设用户让 Agent 排查一个问题。

> 昨天开始，销售报表生成得很慢。只允许查询，不允许修改配置或数据。

Agent 先查接口耗时，再查数据库日志和发布记录。几十次调用以后，对话越来越长。用户眼里，这是一项连续执行的任务；应用发起下一次模型请求时，仍然要组装这一次的输入。

历史记录保存在数据库里，只解决了“系统有记录”。模型能否利用其中的信息，还取决于应用把哪些内容选进了本轮上下文。假设本轮只带最近一段 SQL 日志，最早的只读要求就可能从模型可见内容中消失。

所以，接下来咱们处理的是**下一次请求的输入**。原始记录是否继续保存，是另一项存储决策。

### 窗口还没满，为什么就要开始处理？

先把空间算清楚。本轮输入包括系统说明、工具定义、任务状态、历史消息，以及读入的材料；模型接下来还要生成回答或工具请求。如果后续会读到一大段查询结果，应用也要提前安排处理方式。

可以把预算理解成三个部分。已经占用多少，下一次生成最多留多少，后续新增材料预计需要多少。具体如何计入上下文窗口，要核对所用模型 API 的限制，后续工具结果也会进入之后的请求。

![上下文预算包含当前输入，并提前安排模型输出和后续工具材料的空间](https://note.lgdsunday.club/img/Q056/02-context-budget-pilot.webp)

图中预留区域表示应用的预算安排，并不意味着未来的工具结果已经装进当前请求。

如果直到窗口耗尽才压缩，连“请总结这段历史”的请求都可能放不下。应用可以在组装请求时检查预算，并让日志查询支持分页、筛选和按需读取，减少一次性读入的材料。

**没有通用的“达到 80% 就压缩”规则。** 预留多少，取决于输出限制、工具返回大小和任务特点。先缩减重复日志、反复出现的文件内容，再判断是否需要摘要，可以避免为很小的收益反复调用模型。

### 聊天摘要很短，为什么仍然可能坏事？

回到报表案例。假设当前已知的是，接口主要耗时发生在数据库查询；网络耗时没有明显变化，对应监控查询 M12；发布 R8 改过相关 SQL，但还没证明它导致了变慢。下一步准备查看执行计划。

如果把这些内容总结成“已查看监控，数据库有问题”，下一轮会遇到三个空缺。它不知道网络已经查过，不知道 R8 只是线索，也不知道查看执行计划尚未完成。

这几处空缺会改变行动。Agent 可能重复查网络，也可能直接建议回滚 R8。若只读限制也被漏掉，后果就更严重了。

一份能继续使用的摘要，需要明确写出这些区别。

> 当前目标是查明报表变慢的原因，保持只读排查。
>
> 已确认接口主要耗时发生在数据库查询。网络耗时没有明显变化，证据为 M12。
>
> 发布 R8 修改过相关 SQL，关联仍待验证。下一步查看执行计划，目前尚未完成。

![普通摘要丢失只读限制与状态，任务摘要保留已确认、待验证、待执行及证据来源](https://note.lgdsunday.club/img/Q056/03-summary-state-pilot.webp)

注意右边的“待验证”和“待执行”。它们需要明确的状态标记，不能与完成事项共用绿色勾选。摘要写得流畅，也可能把“准备查看”改成“已经查看”，审校时要逐项核对原记录。

### 哪些信息进摘要，哪些应该留在别处？

摘要模型会做信息取舍。对持续有效的约束，可以由应用保存在独立任务字段中，每次组装输入时补入。工具执行前也要检查只读权限，模型看见限制不能替代后端授权。

其余内容按下一步用途安排。下面是本文的应用设计示例，不是某个框架的固定数据结构。

| 原始内容             | 压缩后放在哪里        | 下一轮怎样用         |
| ---------------- | -------------- | -------------- |
| 排查报表变慢、只读操作      | 当前任务状态         | 每轮补入目标与有效限制    |
| 已确认数据库查询耗时、已查过网络 | 阶段摘要，附 M12 等来源 | 决定哪些检查可以跳过     |
| R8 与 SQL 的关联尚未验证 | 待验证事项          | 继续寻找证据，暂不认定根因  |
| 几千行原始日志          | 外部材料存储         | 留查询编号，按需读取关键片段 |
| 最近讨论的 SQL 与新的报错  | 相关近期消息         | 保留正在分析的细节      |
| 已发出、尚未返回的工具调用    | 运行器的调用状态及必要消息  | 等待结果，不标记为完成    |

表里最后一项尤其容易被粗暴裁剪伤到。调用已经发出，返回还没到，这时不能凭摘要推断成功，也不能因为旧消息被删就再次执行。运行器要保留调用标识与实际状态；送给模型的消息还必须符合所用 API 对工具请求、结果和排列方式的要求。

### 真正执行一次压缩，输入怎样重新组装？

咱们可以先选出一个已完成阶段，例如“查接口耗时和网络监控”。它适合整理成摘要。正在讨论的 SQL 和尚未完成的调用，暂时保留必要细节。裁剪边界应结合调用状态选择，不能按字符长度拦腰切断。

整理好以后，应用重新组装下一轮输入。

![已完成历史整理成摘要，与独立任务状态、相关近期消息共同组成下一轮输入，长日志保存在外部](https://note.lgdsunday.club/img/Q056/04-rebuild-input-pilot-v2.webp)

沿着图读一遍。旧阶段的完整过程缩成摘要；任务状态提供只读限制；近期消息提供当前 SQL 细节。外部材料没有全部复制回来，只带能够定位原文的来源信息。相关组件占用的空间加在一起，才是下一轮实际要检查的预算。

如果 Agent 后面发现 M12 与新日志矛盾，先按来源取回 M12 的相关片段，再判断是否要修改结论。这样，摘要中的一句话仍然有材料可以核对。查询编号需要能定位对应记录，保存期限和访问权限也要覆盖这项任务。

[Anthropic 的上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)讨论了压缩、外部笔记和按需检索。本文把这些思路展开成报表排查的设计示例，字段、预算和压缩边界仍需由具体应用确定。

### 怎样证明下一步仍然做得对？

可以固定一个执行到一半的任务状态，分别给 Agent 完整历史和压缩后的输入，再让它继续。这里要比较具体行为，摘要长短本身无法说明信息有没有保住。

报表案例可以检查下面几项。

| 检查条件      | 应观察到的行为            | 暴露的问题      |
| --------- | ------------------ | ---------- |
| M12 已排查网络 | 不无故重复同一次检查         | 进度或结论丢失    |
| R8 尚待验证   | 不直接宣告 R8 是根因       | 猜测被写成事实    |
| 执行计划尚未返回  | 不宣称已经验证，也不重复发起同一调用 | 调用状态丢失     |
| 用户要求只读    | 不尝试修改配置；执行层也拒绝越权   | 约束或授权检查缺失  |
| 需要核对 M12  | 能取回对应原文片段          | 来源无法定位或已失效 |

同时记录输入 Token、继续执行的延迟和生成摘要的成本。若频繁压缩增加了额外等待，却没有改善任务完成表现，就要重新选择触发时机或压缩粒度。本文给出的是验证方法，没有把这组假设检查写成已经完成的模型实验。

## 面试官继续追问

### 最近几轮保留完整，旧消息全部删除，可以吗？

先检查旧消息里有没有仍然有效的限制、证据和未完成事项。短任务可以尝试滑动窗口；长任务通常需要再补入独立任务状态和阶段摘要。消息出现得早，不代表已经失效。

### 连续压缩多次，怎样避免越传越偏？

重要事实保留来源，更新时明确区分已确认、待验证和已撤销。后续摘要可以继承仍有效的结论，但遇到冲突要回读原记录。假设 R8 已经被新证据排除，任务状态和摘要也要更新，不能一直保留早期怀疑。

### 换成长上下文模型，还需要压缩吗？

更大的窗口可以容纳更多内容，但应用仍需选择相关材料，并处理过时结论和冲突约束。是否压缩，要结合任务完成表现、延迟与成本比较；不能只凭窗口容量决定。

## 面试速记卡

> - 每轮输入要明确带入仍有效的目标、限制、证据和执行状态。
> - 预算提前安排，为输出及后续新增材料留出空间。
> - 已完成阶段适合摘要，待验证与待执行要分别标记。
> - 长材料可以外置，来源必须能够定位并按权限取回。
> - 工具调用状态由运行器保存，裁剪遵守实际 API 格式。
> - 用后续行为检查压缩质量，再比较 Token、延迟和成本。
