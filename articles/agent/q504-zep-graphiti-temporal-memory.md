# Zep 和 Graphiti 是什么？Agent 为什么需要时序知识图谱记忆？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/agent/q504-zep-graphiti-temporal-memory/) · [题库目录](../../README.md)

*下面是一段模拟面试追问。*

🧑‍💻 面试官：Agent 记着“项目负责人是小陈”，后来负责人换成了小李，怎么办？

🙋‍♂️ 我：用新记录覆盖旧记录。

🧑‍💻 面试官：那用户问“三月的时候是谁负责”，还能回答吗？

🙋‍♂️ 我：要保留历史和时间。

🧑‍💻 面试官：如果六月换了负责人，我们七月才收到这条消息，六月底系统为什么仍然回答小陈？

> 这里需要分清两个时间：事情什么时候成立，系统什么时候知道。只存一条“最新关系”，解释不了这两类问题。

## 面试速答（60 秒版）

Graphiti 是用于构建和查询动态知识图谱的开源框架，可以从持续到来的记录中提取实体与关系，并保留关系的时间信息。Zep 是相关的托管上下文服务，两者不能简单当成同一个产品。[官方说明](https://help.getzep.com/graphiti/getting-started/overview)。

时序记忆适合处理“谁在什么时间具有什么关系”这类问题。比如负责人发生变化时，我们既需要知道现在是谁，也可能需要查过去是谁。

这时，除了事实的有效时间，还要区分系统何时收到或记录了它。新事实到来，不应该把所有历史意义一起抹掉。

不过，图谱只是一种组织方式。实体是否识别正确、来源是否可信、冲突怎样处理，仍然要单独检查。涉及审批或权限时，应回到权威业务系统，不直接把图谱中的关系当成授权。

## 知识点详解：负责人换了以后，旧关系为什么还要留下？

### 先看普通记录会遇到什么问题

假设我们给团队做一个项目问答助手。

三月的资料写着“小陈负责项目 A”。六月一日起，负责人换成了小李，但助手直到七月才收到这条变更通知。

如果数据库只有一个 `负责人` 字段，更新后就只剩“小李”。它能回答现在是谁，却难以回答三月是谁，也解释不了六月底为什么还给出了旧答案。

当然，普通数据库也能设计历史表来解决这些问题。时序图谱的价值，不是“数据库做不到”，而是在关系多、信息持续变化时，提供一种便于连接实体与追踪时间的组织方式。

### 先有实体和关系，再讨论时间

在这个例子里，“项目 A”“小陈”“小李”可以作为实体。

“小陈负责项目 A”则是一条关系。系统从消息中提取这些信息时，要先确认“小陈”指的是谁，“项目 A”是不是同一个项目，不能只看名字相同就直接合并。

Graphiti 通过持续加入的记录组织实体与关系。原始记录仍然很重要，因为后续需要核对关系来自哪条消息，而不是只看模型抽取出的结论。[记录写入说明](https://help.getzep.com/graphiti/core-concepts/adding-episodes)。

### 两个时间，分别回答不同的问题

把刚才的变更展开：

| 时间   | 发生了什么       | 对查询有什么影响       |
| ---- | ----------- | -------------- |
| 三月   | 小陈负责项目 A    | 查询三月情况，应保留这段历史 |
| 六月一日 | 小李开始负责      | 这是新关系在业务上生效的时间 |
| 七月   | 系统收到六月的变更通知 | 这是系统获知变更的时间    |

“六月十日实际是谁负责？”是在问事实时间。

“六月十日系统当时掌握的信息是什么？”是在问当时的认知记录。

两种问题可能给出不同结果，并不一定是系统自相矛盾。晚到的消息会补充过去发生的事实，但不能假装系统在消息到达前就已经知道。

这就是双时态设计要区分的基本问题。具体字段与更新行为应按使用的 Graphiti 版本核对；本例是在解释查询语义，不是提供一套可直接套用的 SDK 字段。

![区分业务有效时间与系统获知时间](https://note.lgdsunday.club/img/Q504/02-two-times.webp)

*七月收到的通知可以补充六月事实，但不能假装系统在六月就已经知道。*

### 新关系出现，不代表旧关系从未成立

收到变更以后，可以把“小陈当前负责”的有效范围结束在六月一日，同时留下历史；新关系从六月一日起生效。

这里要结束的是旧关系的当前适用性，不是删除它曾经成立的证据。

但实际消息未必这么明确。有人只说“现在找小李”，没有给出交接日期，也可能只是临时代理。系统不应该据此编出精确生效日，更不应该自动推断小陈从此不再参与。

不确定的时间或关系，可以保留为待确认信息，或者回查项目系统与正式通知。模型提取不等于事实已经确认。

### 什么情况下值得引入时序图谱？

如果任务经常沿着多个关系查询，并且关系随时间变化，例如查人员、项目和职责的历史关联，图谱可以帮助组织证据。

如果只是保存几项用户偏好，或者从文档里找一段答案，结构化记录与普通检索可能已经足够。

图谱还会增加实体消歧、关系维护和冲突处理的成本。因此，不能仅因为项目里用了 Agent，就默认需要知识图谱。

权限尤其要独立处理。记忆里出现“小李是负责人”，不代表助手就能替他审批。审批身份和操作权限，仍然由业务服务验证。

## 面试官继续追问

### 向量数据库也能保存时间，为什么还要图谱？

向量库可以保存时间元数据，关系数据库也能维护历史。

是否需要图谱，要看查询是否经常沿实体关系连接，以及现有方案是否难以组织这些关系。不能把“有时间字段”当成图谱独有能力。

### 两个来源对负责人说法不同，谁说了算？

先看来源、适用时间和关系含义。临时代理与正式负责人可能不是同一件事。

如果仍然冲突，可以展示证据或请求确认。高风险流程由权威业务系统决定，不让模型凭相似度或消息数量投票。

### 怎么评测时序记忆？

同一组变更记录，分别提问过去状态、当前状态与“系统当时知道什么”。

还要加入消息晚到、时间缺失、同名实体和冲突通知，检查系统是否混淆时间、错误合并，或凭空补出了结论。

## 面试速记卡

> - Graphiti：组织动态实体、关系与时间信息的开源框架。
> - Zep：相关托管服务，不与 Graphiti 简单画等号。
> - 事实时间：关系在现实中何时成立。
> - 获知时间：系统何时收到或记录这条信息。
> - 更新原则：当前关系可以失效，历史证据仍要能追溯。
> - 权限边界：关系记忆帮助理解，不直接授予业务操作权限。
