# 单 Agent 和多 Agent 应该怎么选？什么时候才需要 Handoff？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/agent/q018-single-vs-multi-agent/) · [题库目录](../../README.md)

🧑‍💻 面试官：你做一个研究助手，要查资料、分析数据、写结论。有人提议直接分成“检索 Agent、分析 Agent、写作 Agent”。你同意吗？

🙋‍♂️ 我：我会先问现在的问题是什么。一个 Agent 调几个清楚的工具就能完成，而且可追踪、可评测，那不一定要拆成三个 Agent。拆分会增加上下文交接和协作成本。

🧑‍💻 面试官：如果分析环节需要访问数据库，但写作环节不该有这个权限？

🙋‍♂️ 我：这就是拆边界的理由之一。可以让分析组件只拿完成任务所需的数据库能力，把分析结论和证据交给写作组件；但权限最终还是由工具和后端执行，不能只靠角色提示词。

🧑‍💻 面试官：分析 Agent 查完以后让写作 Agent 接着和用户聊，这叫 Handoff 吗？

🙋‍♂️ 我：如果控制权真的转给写作 Agent，由它接管后续对话，可以叫 Handoff。若主 Agent 只是请它写一段草稿，然后自己继续决定和回答，那更像把子 Agent 当工具调用。

> 单 Agent 还是多 Agent，不看名字里有几个“Agent”，而看**职责和权限是否需要分离，以及控制权是否真的要转交**。

## 面试速答（60 秒版）

我不会默认把任务拆成多个 Agent。先用单 Agent 加明确工具，看看它是否已经能稳定完成任务。如果主要问题只是步骤多，未必需要多 Agent；真正值得拆分的，往往是专业上下文、工具权限或对话责任需要分开。

多 Agent 里还要区分两种协作：主 Agent 始终负责最终回答，找专业 Agent 做一个有边界的子任务，这更像“Agent 作为工具”；如果当前 Agent 判断自己不适合继续，转给另一个 Agent 接管用户对话，才是 Handoff。转交时要传任务目标、已核实证据和未解决的问题，不把整段噪声聊天直接丢过去。

选型最后要看效果。拿同一批任务比较成功率、错误工具调用、延迟、成本和交接失败。如果多 Agent 只是增加了几轮模型调用，却没有改善质量或治理边界，就没必要为了架构看起来高级而使用它。

## 知识点详解：先判断问题是不是“需要多个人”

### 单 Agent 能解决的，先别拆

假设研究助手收到任务：“整理一家公司的季度财报，算出收入变化，再写一段解释。”一个 Agent 可以先检索财报，再调用计算工具，最后整理文字。只要工具权限清楚、执行可回放、质量达到要求，这已经是一套完整方案。

把它硬拆为三个 Agent，意味着每次交接都要决定交给谁、交什么、等多久、失败后回到哪里。检索 Agent 可能没有告诉分析 Agent 财报币种；分析 Agent 可能只给写作 Agent 一个数字，没有给公式和原文。**多 Agent 增加的不只是角色，还有交接点。**

### 哪些情况值得拆出专业边界

如果数据库分析需要专门的查询策略和受限凭证，而写作只需要已核实的表格与结论，分离组件就有价值。再比如法律条款审阅需要一套独立的核查流程，主 Agent 不应顺手拥有合同修改权限。

拆分的理由应落到可验证的收益：专业任务准确率更高、上下文更聚焦、权限更容易限制、不同部分可独立评测。仅仅因为任务“复杂”，或者想让系统显得像一个“团队”，不够。

而且不是所有分工都要由模型动态决定。用户问题一开始就能按确定规则分类时，代码路由到对应处理流程通常更简单。只有处理过程中才发现需要哪位专家时，动态分派才更有价值。

### “请专家帮忙”和“把对话交出去”不一样

主 Agent 调用分析 Agent，拿回一个计算结果，再由自己写最终答复：主 Agent 仍掌握用户对话和任务收口，这属于“Agent 作为工具”的协作。

Handoff 则把当前轮的主动权转给专业 Agent。比如售后接待 Agent 发现用户要处理复杂计费争议，将对话交给有相应规则和工具的计费 Agent，后者成为当前对话的处理者。转交不等于放弃约束；新 Agent 的权限范围、交接摘要、终止条件和转人工规则仍要由应用设计。

无论哪种方式，交接包都应包含原始目标、已完成步骤、可信来源、未解决问题和允许的下一步。尤其要把“已经查证”和“模型推测”分开，否则错误会在多 Agent 间被层层放大。

### 怎么验证拆分真的有收益

准备几类任务：单一知识查找、检索加计算、需要不同权限的任务、跨领域协作任务。对比单 Agent 和多 Agent 的完成质量、错误工具调用、Token/延迟、交接次数与失败位置。高风险工具的越权调用单独统计，不能被平均完成率掩盖。

如果多 Agent 只是在简单任务上多绕一圈，就把简单任务留在单 Agent 或确定性流程里；只在证明确实需要专业分工的任务上打开协作。

## 面试官继续追问

### 多 Agent 一定比单 Agent 更准确吗？

不一定。专业边界可能提高某些任务的表现，但交接遗漏、错误路由和额外上下文也会带来新错误。必须在相同任务集上比较。

### 把子 Agent 做成工具，算不算 Handoff？

关键看控制权。若主 Agent 拿回子任务结果后仍负责最终回答，不是对话控制权转移；若专业 Agent 接管当前用户会话，才符合 Handoff 的含义。

### 用提示词写“你没有数据库权限”就够了吗？

不够。真正权限由工具暴露范围、身份和后端校验控制。提示词能说明职责，不能替代授权。

## 面试速记卡

> - 起点：单 Agent 加清晰工具能稳定完成，就不必为分工而分工。
> - 拆分依据：专业上下文、权限或对话责任需要明确边界。
> - Agent 作为工具：主 Agent 保持控制，专业 Agent 完成有边界子任务。
> - Handoff：控制权转给专业 Agent，由它继续处理当前对话。
> - 验证收益：对比质量、越权、交接失败、延迟与成本。
