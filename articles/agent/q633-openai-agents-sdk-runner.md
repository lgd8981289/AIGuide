*下面是用于讲题的模拟面试对话。*

🧑‍💻 面试官：接入 OpenAI Agents SDK 以后，工具是谁调用的？

🙋‍♂️ 我：模型先决定用哪个工具，再由 SDK 执行工具，把结果交回模型。

🧑‍💻 面试官：那 SDK 里的 Agent 对象，是一个一直在后台运行的进程吗？

🙋‍♂️ 我：应该不是。它主要保存模型、指令和工具等配置，需要运行器把它跑起来。

🧑‍💻 面试官：如果查询成功了，但写操作的结果不确定，Runner 会替你保证任务恢复和业务幂等吗？

> 把一次任务拆成“配置、运行、业务执行”三层，就能看清 SDK 帮我们省了什么，又有哪些事情仍要自己处理。

## 面试速答（60 秒版）

OpenAI Agents SDK 是一套用代码组织 Agent 运行的开发工具。它把调用模型、处理工具请求、接回工具结果和交接给其他 Agent 这些重复工作封装起来了。

其中，`Agent` 主要描述一个执行角色的配置，例如使用什么模型、遵守什么指令、允许调用哪些工具。`Runner` 负责真正推进运行过程，检查模型返回的是工具调用、交接请求，还是最终结果。

`Responses API` 则是下面的一层模型服务接口。使用默认的 OpenAI 模型集成时，SDK 可以通过它向模型提交输入、取得输出；它和 Agent 配置、运行器不是同一个东西。

因此，接入 SDK 可以少写一套循环，但应用仍然要负责部署、业务权限、状态存储和外部操作的可靠性。比如模型请求退款，工具函数仍需要查当前用户有没有权限，并防止同一笔退款被执行两次。

## 知识点详解：定义一个 Agent 以后，谁让它动起来？

### Agent 对象保存的是做事方式

假设我们要做一个订单查询助手，允许它查询订单和物流，但不允许修改订单。

开发者创建 Agent 时，会给它一个名字，写清任务指令，再挂上查询订单、查询物流两个工具。工具定义描述它们能做什么、需要哪些参数，具体查询逻辑则写在应用提供的函数里。官方的 [Agent 定义说明](https://developers.openai.com/api/docs/guides/agents/define-agents)介绍了这类配置。

这时只是把助手准备好了，还没有因为创建对象就开始处理用户问题。一个配置也可以被多次运行使用，所以不能随手把某个用户的订单数据放成所有请求共享的可变字段。

### Runner 接住模型输出，再决定运行怎样继续

用户问“我的订单到了哪里”，应用把问题和必要上下文交给运行器。接下来可能出现下面这段过程。

1. 运行器把当前输入交给模型。
2. 模型提出查询订单的工具请求，并给出参数。
3. SDK 调用已注册的工具函数，取得订单里的物流单号。
4. 运行器把工具结果带回下一次模型调用。
5. 模型再请求查询物流，收到结果后组织最终回答。

这里最容易混淆的是第三步。SDK 可以负责调用函数，但函数里访问哪套订单服务、使用谁的身份、怎样处理超时，是应用实现的。不能把模型生成的 `user_id` 直接当成可信身份。

运行器也不会每次都执行固定的两次工具调用。模型可能已经有足够信息，直接给出答案；也可能需要更多轮。运行循环及其停止点见官方 [Running agents](https://developers.openai.com/api/docs/guides/agents/running-agents)。

![一次订单查询怎样经过两轮工具反馈](https://note.lgdsunday.club/img/Q633/02-tool-result-loop.webp)

### Responses API 位于模型调用这一层

现在把视角拉到第二步。SDK 需要把输入送给模型，模型服务再返回文本或工具请求。这一段可以由 Responses API 承接。

如果直接调用 API，开发者也能自己写循环，读取工具请求、执行函数，再提交结果。使用 SDK 的价值，是把这些运行细节组合成可复用的代码结构。不要据此推断所有 SDK 模型适配器都必须走 Responses，也不要把本地函数工具和服务端托管工具的执行位置混为一谈。

当前官方还提供其他 Agent 运行产品。面试题指定的是运行在自己应用中的 Agents SDK，讨论时应把产品名字说全，避免把 SDK 和服务端托管的 Agents API 混在一起。[官方 SDK 概览](https://developers.openai.com/api/docs/guides/agents/sdk)明确了这一运行边界。

### 一次运行结束，不代表业务已经闭合

订单查询通常没有写副作用，退款就不同了。假设退款服务收到请求并完成扣账，但工具调用在返回途中超时，运行器看到的是一次失败，业务侧却可能已经执行成功。

因此，退款工具需要带稳定的业务请求标识，超时后先查询处理结果；重复请求则返回同一笔操作的状态。SDK 里有没有历史消息，解决不了这个问题。服务重启后的恢复，也需要应用持久化运行数据和业务进度。

验证这套集成时，可以准备“直接回答、单工具、多工具、工具失败、越权请求”几类任务，检查 Trace 中的模型请求、工具参数和返回结果。再单独测试写操作超时重试，确认最终业务记录没有重复。本文解释职责划分，没有执行真实模型调用或退款实验。

## 面试官继续追问

### 用了 Session，就能保证服务重启后继续吗？

要看 Session 实际使用什么存储，以及保存了哪些数据。内存存储会随进程消失；保存对话历史，也不自动保存外部写操作的处理状态。恢复时还要确认任务执行权和副作用结果。

### Handoff 和把另一个 Agent 当工具调用，有什么区别？

关键是后续由谁负责。Handoff 会把当前执行角色交接出去；把另一个 Agent 作为工具使用时，外层角色仍然负责接回结果和组织后续回答。具体上下文传递还要按 SDK 配置核对，不能理解成两边无条件共享所有消息。

### 小项目有必要一开始就接 SDK 吗？

如果只有固定的一次模型调用，直接 API 调用通常已经清楚。出现多轮工具执行、角色交接、运行追踪等需求以后，SDK 的封装才更容易体现价值。比较时应把同一条任务跑通，再看自己需要维护多少运行代码。

## 面试速记卡

> - Agent 保存角色配置，创建对象不等于启动后台任务。
> - Runner 推进模型、工具与交接组成的运行循环。
> - Responses API 可以承接模型调用，和 SDK 运行器处于不同层。
> - 函数工具由应用实现，身份与业务权限在可信执行端校验。
> - 运行历史、任务恢复和写操作幂等，需要分别设计。
