*下面用模拟对话展开这道题。*

🧑‍💻 面试官：AGENTS.md 和 CLAUDE.md 有什么用？

🙋‍♂️ 我：把项目规则写进去，AI 编程助手以后就会按照规则改代码。

🧑‍💻 面试官：仓库里已经有文件，但助手没有读到呢？后端规则会不会影响前端目录？

🙋‍♂️ 我：还要看具体工具怎样加载，以及规则对应哪个范围。

🧑‍💻 面试官：规则写着“禁止删除数据”，助手就真的没有删除权限了吗？

> 这道题要分开看「规则内容、加载范围和执行权限」：文件存在，不等于已经生效，更不等于动作被强制阻止。

## 面试速答（60 秒版）

AGENTS.md 和 CLAUDE.md 都可以用来给 AI 编程助手提供持久的项目说明，例如怎样安装依赖、运行测试、代码放在哪里，以及哪些改动需要先确认。

AGENTS.md 是面向多种编程工具的开放约定；CLAUDE.md 是 Claude Code 使用的项目指令入口。具体文件怎样加载、子目录规则何时加入，要看工具及版本，不能认为所有助手行为一样。[AGENTS.md 官方说明](https://agents.md/)。

它们和自动记忆也不完全相同。项目规则通常由人维护，自动记忆则是助手从交互里形成的笔记。规则适合记录团队确认的要求，不应该只靠模型自己总结。

同时，规则文件只是模型看到的上下文。真正不能发生的操作，还要通过工具权限、执行环境或强制检查阻止，不能只写一句“不要做”。

## 知识点详解：规则怎样从仓库文件进入当前任务？

### 文件首先要告诉助手具体怎么工作

假设咱们维护一个前后端放在一起的项目。根目录可以记录全项目要求：不要提交敏感配置，修改后运行相关测试，不要顺手改无关模块。

前端和后端又有各自的说明。前端需要遵守组件组织方式，后端需要使用指定的接口错误格式。

这种信息比“请认真工作、保证代码质量”更有用。因为助手知道该看什么、执行什么，也更方便用结果检查它有没有遵守。

下面是用于讲解的目录示例，不代表所有工具都会自动读取这里的每个文件：

```text
repo/
├── AGENTS.md
├── frontend/
│   └── AGENTS.md
└── backend/
    └── AGENTS.md
```

根目录写公共规则，子目录写局部差异。不要在三个文件里各复制一份完整说明，否则改一次要求就要同步三处，很容易留下互相矛盾的版本。

### 加载范围由工具决定，不由文件名凭空保证

以当前 Claude Code 文档为例，工作目录及上级目录的 CLAUDE.md 会在启动时加载，子目录的文件按访问情况加载。

它现在也支持 AGENTS.md，但受版本、插件与 Project instructions 设置影响。默认模式在工作目录及上级没有 CLAUDE.md 或 CLAUDE.local.md 时使用 AGENTS.md；也可以设置同时加载两类文件。[Claude Code 当前记忆与规则文档](https://code.claude.com/docs/en/memory)。

这些是 2026-10-09 核对的产品行为，不是 AGENTS.md 格式对所有工具强制规定的行为。

因此，接入项目以后先检查实际加载列表。以 Claude Code 为例，可以用 /context 查看 Memory files。文件内容写得再完整，工具没有加载，模型这一轮仍然看不到。

![可视化规则作用范围，明确具体加载行为仍需核对](https://note.lgdsunday.club/img/Q500/02-directory-scope.webp)

### 项目规则和自动记忆为什么要分开维护？

假设助手在一次临时排错中学到：“当前测试环境需要一个特殊代理。”

这条笔记可能方便下次继续任务，但不应该直接写成整个团队都必须遵守的项目规则。

项目要求通常需要团队确认、代码审查和版本记录。自动记忆更多是工作中积累的背景，两者都可能过时，但责任人和使用范围不一样。

对于重要要求，更稳妥的是放到明确维护的项目规则里；临时环境经验留在相应范围，标明条件，避免影响其他机器和任务。

### 写着禁止删除，为什么仍要做权限限制？

因为“模型知道不该删除”和“执行器不能删除”并不是同一件事。

助手可能理解错、漏看规则，也可能被其他低可信内容干扰。因此，敏感目录访问、删除操作或线上变更，还需要执行层限制。

例如一个只读排查助手，可以不提供写工具，或者在工具执行前拒绝写操作。即使模型发出了删除请求，后端仍能拦住。

规则帮助模型选择正确行为；权限负责不让错误行为真正执行。规则文件不能代替这个边界。

![解释文本规则不是强制控制，独立执行门禁为何必要](https://note.lgdsunday.club/img/Q500/03-rule-tool-gate.webp)

## 面试官继续追问

### 所有要求都放在根文件里，是不是最稳？

不一定。

无关要求会进入不需要它的任务，还会使文件越来越难维护。公共约束留在根目录，局部命令和差异放在对应范围，通常更好理解。具体加载方式仍须按工具核对。

### 根规则和子目录规则冲突怎么办？

先查当前工具的优先级，再修掉冲突。

不能长期依赖模型替团队猜测。子目录如果需要例外，就明确写出适用路径和原因；与安全权限冲突时，文本规则也不能扩大执行权限。

### 怎样验证规则真的在工作？

开一个新会话，查看加载文件，再分别安排前端与后端的小任务。检查助手使用的命令、修改范围和最终结果。

涉及安全边界时，还要单独测试执行器会不会拒绝不允许的操作。助手回答“我会遵守”不算验证完成。

## 面试速记卡

> - 规则内容：写具体命令、路径和要求，少写空泛口号。
> - 加载机制：按工具与版本检查，不只看文件有没有创建。
> - 目录范围：公共规则与局部规则分开维护。
> - 自动记忆：交互笔记不自动成为团队确认的项目规范。
> - 强制边界：规则引导模型，执行权限阻止不允许的动作。
