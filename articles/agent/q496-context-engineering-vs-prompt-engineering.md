# Context Engineering 是什么？和 Prompt Engineering 有什么区别？

*下面是一段模拟面试对话。*

🧑‍💻 面试官：Context Engineering 和 Prompt Engineering 有什么区别？

🙋‍♂️ 我：上下文工程就是把提示词写得更完整，多补一些背景。

🧑‍💻 面试官：假设提示词已经写了“修改前先阅读测试”，但模型拿到的输入里没有测试文件，你再加一句“认真阅读”，能解决吗？

🙋‍♂️ 我：不能。得让它找到测试，再把需要的内容读进来。

🧑‍💻 面试官：如果读进来的是旧分支的测试，或者中间漏掉了“不改接口”的要求呢？问题还是提示词不够好吗？

> 这道题的关键是「本轮输入」：指令写得好，还得保证模型在做决定时拿到了对的信息。

## 面试速答（60 秒版）

Prompt Engineering 主要解决“怎样把要求写清楚”。例如让模型修改代码之前先找测试、不要改变公开接口，这些属于指令设计。

Context Engineering，也就是上下文工程，考虑的范围会更大。它需要根据当前任务，决定这一轮给模型哪些指令、工具、代码、历史记录和记忆，并检查这些内容是否仍然有效。[Anthropic 对两者的说明](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

因此，两者并不是二选一。提示词是上下文的一部分，但上下文工程还要处理信息从哪里来、什么时候加载，以及任务执行以后下一轮应该补什么。

例如 AI 编程助手已经找到报错函数，下一轮就应该带上相关代码、调用方和测试，而不是继续塞整个仓库介绍。出现问题时，也需要检查模型实际看到了什么，不能只盯着系统提示词改。

## 知识点详解：一次模型调用之前，要准备哪些信息？

### 先把“写好了”和“看到了”分开

假设咱们在做一个编程助手。用户要求修复登录失败的问题，同时明确说：不要修改登录接口的返回格式。

开发者在系统提示词里写了“先找原因，再修改代码，最后运行测试”。这句话已经说明了做事顺序，但它并没有告诉模型登录代码在哪里、报错是什么，也没有自动把用户的限制保存到后面的每一轮。

所以，指令设计完成以后，应用还要准备这次调用的输入。

这份输入可以包括用户目标、不能改动的地方、刚拿到的报错、相关代码，以及当前允许使用的工具。这里说的是一种应用设计，不是某个框架规定的固定字段。

如果返回格式限制根本没进输入，那么模型下一轮即使很认真，也可能朝错误方向继续做。

### 上下文组装会随着执行结果变化

第一轮，应用只知道“登录失败”。可以先给模型报错和代码目录，让它决定去哪里查。

工具找到了登录函数以后，下一轮就有了新的信息。此时需要读取这个函数，再根据调用关系补上参数从哪里来、返回值被哪里使用，以及相关测试。

| 执行阶段   | 这一轮需要补充什么       | 不必重复搬进来的内容   |
| ------ | --------------- | ------------ |
| 刚接到任务  | 目标、限制、报错、目录线索   | 与登录无关的全部业务说明 |
| 找到可疑函数 | 真实代码、调用方、相关测试   | 大量已确认无关的搜索结果 |
| 准备交付   | 修改内容、测试结果、未解决事项 | 所有探索过程的原始输出  |

注意，用户的目标和限制不是“上一轮出现过就够了”。它们仍然影响后面的决定，需要以可靠的方式继续提供；真正执行写操作时，应用还要独立校验权限。

这就是上下文工程需要跟着任务循环处理的原因。工具返回新结果以后，应用不能只是把结果追加到一份越来越长的聊天记录里。

*图示为假设排错过程；输入内容会变化，仍有效的任务限制应持续保留。*

### 信息多，不代表信息准备得好

继续看这个例子。假设仓库索引返回了三个登录函数，其中一个已经删除，另一个属于测试工具。

如果应用把三个结果都当作当前代码交给模型，问题不是“背景太少”，而是背景的适用条件没说清。

可以在候选结果里保留文件路径和版本，再读取当前工作区文件核对。用户指定不能改变的接口，也应该和普通历史讨论分开标识，避免被旧方案淹没。

对于这里的编程助手，完整仓库不必一次进入输入。先给定位线索，再按需读取文件，是一种可行做法。每次读取会多花时间，所以已有明确入口时，可以直接提供相关文件，不必让模型从零找起。

上下文工程做的是这些选择，不是追求“输入越短越好”，也不是“输入越全越好”。

## 面试官继续追问

### 怎样证明是上下文的问题，而不是模型太弱？

先保留一次失败调用的实际输入，检查正确代码和用户限制有没有出现。

如果缺了必要信息，可以只补齐这些信息，保持模型、任务和其他配置不变，再看结果。若证据已经完整，还需要检查指令是否矛盾、模型是否错误理解，以及工具返回是否可信。

这种对照能缩小问题范围，但一次成功不能证明某种组装策略普遍有效。还要用多种任务做回归。

### 上下文窗口变大以后，这些工作能不能省掉？

不能完全省掉。

大窗口可能让应用少裁剪一些内容，但不会替应用判断哪个分支有效，也不会知道哪份资料已经过期。输入容量和信息适用性是两件事。

### 应该记录什么，才能方便排查？

这类应用可以记录任务版本、实际注入的文件与内容版本、缺失信息、模型输出和工具结果。涉及用户信息时应脱敏，并限制查看范围。

评测时除了任务能否完成，还要看必要证据有没有进入输入、无关内容占了多少，以及增加读取步骤后耗时和成本是否值得。

## 面试速记卡

> - Prompt Engineering：把任务要求和行为指令写清楚。
> - Context Engineering：准备和维护每一轮模型实际看到的信息。
> - 关系：提示词是上下文的一部分，两者不是替代关系。
> - 排错：先检查实际输入，再判断要改指令、检索还是模型。
> - 边界：上下文中的限制不能替代应用执行层的权限校验。
