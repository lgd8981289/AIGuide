# Microsoft Agent Framework 是什么？它与 Semantic Kernel、AutoGen 是什么关系？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/agent/q697-microsoft-agent-framework-semantic-kernel-autogen/) · [题库目录](../../README.md)

*下面是一段模拟面试对话。*

🧑‍💻 面试官：项目用了 AutoGen，现在又有人推荐 Microsoft Agent Framework，它们只是名字不一样吗？

🙋‍♂️ 我：不是同一个包。Agent Framework 承接了 AutoGen 的 Agent 抽象和 Semantic Kernel 的一些企业集成能力，还提供工作流等运行组件。

🧑‍💻 面试官：那把 import 改一下，原来的多 Agent 系统就迁移好了？

🙋‍♂️ 我：还要检查会话、工具、消息和编排方式是否兼容。

🧑‍💻 面试官：迁完以后，旧会话还能继续、工具不会多执行一次，这两件事你怎么确认？

> 框架的继承关系，不能当成代码与运行状态的兼容保证；迁移要沿着实际执行链逐项核对。

## 面试速答（60 秒版）

Microsoft Agent Framework 是微软提供的 Agent 应用开发框架。它包含单个 Agent、工具接入、会话状态、中间件以及显式工作流等组件，可以把模型调用接进应用的运行过程。

按当前官方定位，它是 Semantic Kernel 和 AutoGen 的后继方向，结合了两者积累的一些能力。但这不代表旧代码、工具定义和会话数据可以原样搬过去。

在实际项目里，Agent 负责需要模型判断的部分，Workflow 可以规定多个函数或 Agent 怎样协作。会话负责组织一次持续交互的数据，业务权限和外部操作的可靠性仍然由应用保证。

因此，评估迁移时，需要先确认所用语言与功能的支持状态，再挑一条完整任务验证消息、工具、状态与错误处理。能回答一轮问题，只能证明模型接通了，不能证明迁移完成。

## 知识点详解：先分清框架定位，再检查要迁移的对象

### 三个名字之间是什么关系？

Semantic Kernel 和 AutoGen 是此前形成的两套项目。它们的抽象、包结构和使用方式并不相同。Microsoft Agent Framework 的[官方概览](https://learn.microsoft.com/en-us/agent-framework/overview/)将它定位为这两个方向的后继，而不是一个统一的旧包别名。

这个事实可以帮助理解产品路线，却不能直接推出所有旧功能都已覆盖，或者所有语言版本具有相同能力。本文核验日为 2026-10-18；具体项目应查看当时所用语言、包版本和功能状态，不能拿另一门语言的示例承诺兼容。

### 单个 Agent、会话和工作流，负责的事情不同

假设有一个报销审核助手。它先检查资料，再查询制度，最后给出审核建议。

模型需要判断该查询哪条制度时，可以由 Agent 调用工具。资料检查必须先完成、最终付款必须经过人工批准，这些顺序则可以由工作流明确安排。

会话保存对话和运行所需的数据，但“保存过用户说的话”与“财务系统已经付款”不是同一条记录。即使框架提供了会话能力，付款结果仍要在业务系统里确认。

因此，框架提供了组织这些组件的方式，不表示开发者可以把所有状态放进一个聊天历史对象。订单状态、审批版本、任务进度与消息历史，需要按各自的生命周期管理。

![Agent、会话和工作流，各管一段](https://note.lgdsunday.club/img/Q697/02-framework-responsibilities.webp)

### 迁移不只是替换类名

可以先列出原项目真正使用的对象。比如 Semantic Kernel 中使用了哪些插件和函数、会话由谁保存、哪些消息包含工具调用，哪些过滤器会阻止操作。

然后逐项找新框架中的对应位置。官方的 [Semantic Kernel 迁移说明](https://learn.microsoft.com/en-us/agent-framework/migration-guide/from-semantic-kernel/)专门对照了 Agent 创建、会话、工具注册和调用方式。这些对照意味着需要调整程序，而不是复制一个安装命令就结束。

AutoGen 项目也应沿着自己的消息、参与者和编排方式检查，不能套用 Semantic Kernel 的迁移表。[AutoGen 迁移入口](https://learn.microsoft.com/en-us/agent-framework/migration-guide/from-autogen/)应作为对应项目的核验依据。

### 用一条完整任务检验，比比较功能清单更有用

假设从“查询报销规则”开始迁移，可以固定同一批输入，比较迁移前后实际调用的工具、字段、消息顺序和最终结果。再增加一次工具失败、一次人工暂停和一次会话恢复。

有写操作时，还要模拟“工具已经完成，结果却没送回来”。如果新程序恢复时重复提交，就算对话内容完全一样，也不能认为业务兼容。

这里的建议是一套迁移验收办法，并不是本文已经完成的迁移实验。本文没有运行真实模型、云服务或跨框架历史会话恢复，也不据此给两个框架排性能名次。

## 面试官继续追问

### 使用这个框架，就必须绑定某一个云平台吗？

不能只从厂商名字判断。要查看具体模型客户端和服务集成的支持范围，再确认你要的会话、工具和部署能力。支持多个供应商，也不意味着它们的能力与行为完全一致。

### 原项目运行稳定，有必要马上迁移吗？

先看维护需求、支持周期和新能力是否解决真实问题。迁移有回归成本，应该保留旧版本与回退路径。没有明确收益时，不需要为了名字更新而一次性改掉整个系统。

### Agent Session 能替代业务数据库吗？

不能这样替代。会话是交互与执行上下文，业务数据库负责业务事实及其约束。恢复会话时，还需要重新检查当前权限和业务结果，不能相信历史消息里的一句“已经批准”。

## 面试速记卡

> - 定位：Microsoft Agent Framework 承接 Semantic Kernel 与 AutoGen 的发展方向。
> - 区别：后继关系不保证包、消息、工具与旧状态直接兼容。
> - 组合：Agent 做局部模型判断，Workflow 明确协作路径。
> - 会话：保存交互状态，不自动代表外部业务事实。
> - 迁移：验证完整链路、失败恢复与回退，不能只测一轮回答。
