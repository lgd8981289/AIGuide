# Spring AI 的 Advisor 是什么？顾问链顺序如何影响模型调用？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/agent/q700-spring-ai-advisor-chain-order/) · [题库目录](../../README.md)

*下面是一段用于讲题的模拟面试对话。*

🧑‍💻 面试官：Spring AI 的 Advisor 和 Tool，有什么区别？

🙋‍♂️ 我：Tool 提供可以执行的能力，Advisor 可以在请求、响应经过调用链时做处理。

🧑‍💻 面试官：一个 Advisor 的 order 是 10，另一个是 20，谁先处理请求？谁先处理返回结果？

🙋‍♂️ 我：较小的值先进入，请求向下传，响应再沿调用链返回。

🧑‍💻 面试官：如果第一个 Advisor 没调用下一环，模型还会执行吗？流式调用也能照搬普通调用的实现吗？

> 理解 Advisor，关键是跟着一次请求进去，再跟着响应出来；顺序和是否继续调用，会直接改变模型看见的内容。

## 面试速答（60 秒版）

Spring AI 的 Advisor 用于拦截和处理 AI 调用。它可以修改请求、补充检索资料或对话历史，也可以观察响应，或者直接返回结果，不再继续调用模型。

多个 Advisor 按 `getOrder()` 排序。较小的值先处理请求；在正常继续调用并返回的链路中，先进入的 Advisor 后处理响应，有点像一层层包住模型调用。

Tool 则是模型可以请求执行的具体能力，和 Advisor 的职责不同。Advisor 可以参与工具循环周围的处理，但不能把它简单理解成另一种工具。

实际使用时，需要检查顺序、传递的数据和普通调用与流式调用的差异。尤其是历史消息和工具结果，不能因为用了默认顾问，就假定每一轮都按自己想要的方式保存和注入。

![Advisor 在调用链，Tool 在执行端](https://note.lgdsunday.club/img/Q700/01-spring-ai-advisor-overview.webp)

## 知识点详解：请求往里走，响应再沿调用栈回来

### 一条链怎样包住模型调用？

假设有两个 Advisor，A 的 order 为 10，B 为 20。A 先处理请求，再把请求交给下一环 B；B 继续交给模型调用。

模型结果回来以后，B 可以先处理响应，再返回给 A，最后才回到业务代码。因此，不能拿“谁先处理请求”去判断“谁先看到模型结果”。

这里的 10、20 是为了说明顺序的假设值，不是内置组件的默认配置。相同 order 的顺序也不应作为业务依赖。本文按核验时 Spring AI 2.0.1 的[Advisor 文档](https://docs.spring.io/spring-ai/reference/api/advisors.html)解释，升级后需要重新核对具体组件。

![请求 A 再 B，响应 B 再 A](https://note.lgdsunday.club/img/Q700/02-advisor-order.webp)

### 一次增强，会改变后面的输入

假设 A 负责补充当前用户的历史消息，B 负责检索资料。它们处理过以后，模型读到的是增强后的请求，不再只是页面最初提交的那一句话。

所以，调试时应分别检查进入 A 以前、进入 B 以前和真正送给模型的数据。否则，最终回答不对时，很容易只改提示词，却没发现历史被重复加入，或者检索资料在中间被覆盖。

Advisor 之间可以传递上下文信息，但哪些值进入提示词、哪些只是应用内部数据，要看实现。不能把“放在上下文里”理解成模型自然就能看到，也不能理解成自动保密。

### 不调用下一环，可以直接把结果送回去

Advisor 可以在满足条件时提前返回。例如一个缓存顾问命中了有效结果，就可以不继续访问模型。

这时它需要提供符合调用约定的响应。不能既不继续调用，又假定最后的模型组件会替它补结果。

提前返回也会改变哪些后续组件得到执行。假设审计、权限检查或结果过滤只放在被跳过的一环，就可能丢掉必要检查。因此，链中的优化不能随意绕过安全要求；缓存键也必须覆盖当前用户允许看到的数据范围。

![提前返回，会跳过后面的环节](https://note.lgdsunday.club/img/Q700/03-advisor-short-circuit.webp)

### 对话记忆和工具循环，要确认放在内层还是外层

模型可能先请求工具，再根据工具结果继续回答。记忆顾问处于循环的不同位置时，可能接触到不同阶段的消息。

应该先确定产品需要保存完整工具轨迹，还是只保存最终问答，再查看所用工具调用顾问、记忆顾问和仓库的实际行为。尤其不要同时打开几套历史管理，让同一条工具结果被反复加入。工具与历史的细节需要结合[工具调用说明](https://docs.spring.io/spring-ai/reference/api/tools.html)及[对话记忆说明](https://docs.spring.io/spring-ai/reference/api/chat-memory.html)核对，而不是背一个固定 order 数字。

![先看循环范围，再决定记录哪些消息](https://note.lgdsunday.club/img/Q700/04-advisor-loop-scope.webp)

### 普通调用和流式调用，要分别验收

普通调用使用一次返回的响应；流式调用面对的是一段持续输出。两者的 Advisor 接口和继续调用方式并不相同。

可以用假的模型与事件记录，确认 A 进入、B 进入、B 返回、A 返回的顺序，再增加缓存命中、工具失败和流式中断。日志中不要直接打印密钥或完整敏感资料。

这是一套验证建议。本文没有运行 Spring 容器、真实模型或性能对比；代码位置属于 Java 的 Spring AI，不会把 LangChain 的同类 Middleware 当成它的 TS/Python 官方实现。

## 面试官继续追问

### Advisor 和 Spring AOP 是一回事吗？

它们都能表达前后处理，但作用入口和数据模型不同。Advisor 面向 Spring AI 的请求响应链，AOP 面向代理对象的方法调用。不能把两者的执行顺序和异常行为直接套用。

### 过滤回答中的敏感内容，只放在最后一个 Advisor 就够了吗？

先确认“最后”指请求顺序还是响应顺序，还要检查提前返回、异常和流式分片是否都经过它。涉及敏感输入时，输出过滤也不能替代把敏感数据挡在模型输入之外。

### 流式中途失败，能让重试把整段重新发送吗？

需要处理客户端已经收到的内容。直接重播可能让文字重复，工具还可能已产生副作用。应先明确任务与事件状态，再决定恢复、重试或提示失败。

## 面试速记卡

> - Advisor 处理调用链中的请求与响应，Tool 提供具体执行能力。
> - order 小的先处理请求，正常返回时后处理响应。
> - 相同 order 不应成为业务顺序保证。
> - 不继续调用可以提前返回，也可能跳过后续组件。
> - 普通调用、流式调用、记忆与工具循环要分别检查实际行为。
