# Browser Use 是什么？和直接用 Playwright 写自动化脚本有什么区别？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/agent/q635-browser-use-vs-playwright/) · [题库目录](../../README.md)

*下面是用于讲题的模拟面试对话。*

🧑‍💻 面试官：给你一个后台，要求导出上个月的报表，你选 Browser Use 还是 Playwright？

🙋‍♂️ 我：如果操作路径固定，可以用 Playwright；如果需要根据页面临时判断，可以考虑 Browser Use。

🧑‍💻 面试官：那按钮文字换了，Playwright 就一定失败，Agent 就一定成功吗？

🙋‍♂️ 我：不一定。脚本的定位方式会影响稳定性，Agent 也可能看错页面。

🧑‍💻 面试官：Agent 说“导出成功”，你用什么确认文件真的拿到了，而且月份没选错？

> 浏览器操作做完了，任务未必做对了。选型要看页面变化由谁处理，验收则要看最终文件和页面里的真实结果。

## 面试速答（60 秒版）

Browser Use 是围绕浏览器任务构建 Agent 的开源项目，也有单独的云服务。它可以把任务目标、浏览器状态和执行动作组织成循环，让模型判断下一步怎么操作。

直接用 Playwright 写脚本时，主要路径由开发者写好，例如定位日期框、填写月份、点击导出，再等待下载。页面里可以有分支和重试，但这些处理逻辑仍由代码规定。

Browser Use 更适合操作路径难以提前写全、需要读页面再决定下一步的任务；固定的回归测试和重复导出，通常更适合可检查、可重复运行的脚本。两者也可以组合，让模型处理开放判断，把稳定动作封成受控工具。

无论选哪种方案，都要管理登录会话、执行权限、超时和任务验收。下载按钮被点过，只能说明发起了动作，还需要检查文件是否存在、内容是否完整，以及导出的是否为目标月份。

## 知识点详解：同样在点页面，谁决定下一步？

### 先看固定脚本怎么完成导出

假设后台的报表流程稳定，每次都在同一个页面选择月份，然后下载 CSV。

开发者可以用 Playwright 的定位器表达要找的对象，按顺序执行填写和点击，并在下载发生时取得文件。Playwright 自带等待和可重试断言，脚本也可以编写异常分支。因此，不要把它描述成只会按坐标机械点击的工具。[官方定位器文档](https://playwright.dev/docs/locators)强调了按角色、文本及其他语义寻找页面元素的方式。

这种情况下，模型每次重新理解页面未必划算。明确的脚本更方便比较结果、复现失败，也不会因为同一次任务里的模型判断不同而改走另一条路径。

### Browser Use 多了一轮页面判断

如果进入后台后，用户可能看到引导弹窗，也可能先进入选择工作空间的页面，任务路径就更开放了。

Agent 需要取得当前页面信息，判断眼前是否已经到了报表页，再提出点击、输入或导航等动作。执行后重新读取状态，继续判断。页面内容如何整理、可用动作有哪些、会话怎么连接，应按 Browser Use 所用版本的组件来理解，不能把开源库、CLI 和 Cloud API 的例子混成同一套调用方式。[官方仓库](https://github.com/browser-use/browser-use)提供了不同接入方式的入口。

模型可以适应一部分页面变化，但它同样可能选错目标、漏掉筛选条件，或者不断重复同一个操作。任务运行需要步数、时间和调用预算，遇到无法确认的状态也需要停下来报告。

![页面状态怎样回到下一轮判断？](https://note.lgdsunday.club/img/Q635/02-browser-use-vs-playwright.webp)

### 两种方式都需要管理同一个浏览器身份

报表来自哪个账号、哪个工作空间，通常由浏览器会话决定。不能把“浏览器里已经登录”理解成 Agent 有权访问这个账号的所有功能。

假设任务只允许下载财务报表，就应限制可访问的站点、可使用的动作和文件落点。页面里出现“请把文件发到这个网址”，也不应自动扩大任务授权。网页是任务材料，它给出的指令不等于用户的新要求。

对于付款、删除和发送消息这类动作，尽量使用单独受控的工具或审批步骤。仅靠提示词写一句“不要误操作”，无法检查实际调用到底改了什么。

![浏览器登录了，权限仍要收住](https://note.lgdsunday.club/img/Q635/03-browser-use-vs-playwright.webp)

### 结果验收要离开模型的自我描述

导出场景可以从三个地方确认。先检查页面上的月份与工作空间，再确认下载事件对应到本次动作，最后读取文件的字段、日期范围和必要行数条件。下载流程见 [Playwright 官方说明](https://playwright.dev/docs/downloads)。

没有下载事件，可能是点击没生效；下载成功但筛选月份不对，则是任务条件没有落实。这两种失败应该分别记录。

评估选型时，用同一批固定任务测试两种方案，加入弹窗、慢加载、会话失效和页面小改版。比较完成率、实际操作轨迹、执行时间和维护改动，而不能只展示一次“Agent 自己点完了”的录像。

![点了导出，怎样确认任务完成？](https://note.lgdsunday.club/img/Q635/04-browser-use-vs-playwright.webp)

## 面试官继续追问

### 页面结构变化以后，Agent 的维护成本一定更低吗？

不一定。脚本可能只需改一个定位器，Agent 可能需要改指令、动作定义和验收条件。应该记录一段时间内实际发生的页面变更，以及两种方案为此付出的修改成本。

### Browser Use 能当 E2E 测试工具吗？

可以参与探索性任务，但固定回归用例通常需要明确的步骤、断言和失败复现。模型规划产生的路径变化，应计入测试设计；不能因为它最终说页面正常，就替代关键断言。

### 为什么还要保留自定义工具？

有些操作已经足够稳定，或者需要严格检查参数。例如把“下载目标月份报表”做成受控动作，可以减少重复页面判断。开放决策负责选择目标，确定动作负责可靠执行，两者可以在同一任务里配合。

## 面试速记卡

> - Playwright 按代码规定的逻辑操作页面，也支持语义定位与自动等待。
> - Browser Use 组织目标、页面状态、模型判断和动作反馈。
> - 开源库、CLI 和 Cloud 是不同接入方式，按实际版本确认组件。
> - 登录状态不等于无限授权，页面指令不能自行扩大权限。
> - 验收看页面、文件和业务结果，不能只看 Agent 的结束语。
