# Agent 的语义记忆、情景记忆和程序性记忆有什么区别？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/agent/q498-agent-semantic-episodic-procedural-memory/) · [题库目录](../../README.md)

*先看一段模拟面试对话。*

🧑‍💻 面试官：Agent 常说的语义记忆、情景记忆和程序性记忆，分别是什么？

🙋‍♂️ 我：语义记忆存事实，情景记忆存经历，程序性记忆存做事方法。

🧑‍💻 面试官：假设助手昨天修好了一个登录错误，今天把那次记录再读一遍，这属于哪一种？

🙋‍♂️ 我：情景记忆，因为它记住了一次排错经历。

🧑‍💻 面试官：那从这次经历总结出“修登录错误先改超时时间”，能直接变成以后都执行的规则吗？

> 分类只是起点。这道题真正要讲清的是：一条事实、一次经历和一种方法，分别能支持多大范围的判断。

## 面试速答（60 秒版）

这三类记忆主要按内容来分，不是按保存时间来分。

语义记忆保存事实或知识，例如某个项目使用 Python，用户希望示例讲得详细一些。情景记忆保存一次具体经历，包括当时的条件、做过什么和得到什么结果。

程序性记忆则保存做事方法或行为规则，例如修改接口前先检查调用方，再运行对应测试。这里的“程序性”不等于一段程序代码。[LangMem 对三类记忆的划分](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)。

同一次任务可以留下三类内容，但不能把一次成功经历直接升级成通用规则。方法适不适合新任务，还要看原来的条件是否相同，并用新的任务验证。

同时，短期与长期说的是信息要在哪些会话中保留；语义、情景和程序性说的是保留什么，两种分类可以交叉使用。

## 知识点详解：从一次排错记录里，能留下什么？

### 语义记忆留下“已经知道的内容”

假设咱们有一个编程助手，正在帮助维护 Python 项目。用户说明项目要求使用 Python 3.12，不能依赖更新版本才有的语法。

这可以成为一个项目范围内的事实。下次助手修改代码时，它可以读取这个约束，而不需要完整重放上次聊天。

注意，保存的内容应该带着适用对象。这个项目使用 Python 3.12，不代表用户所有项目都使用这个版本。

语义记忆也不是“真实事实”的保证。模型从对话里抽取错了，保存下来仍然是错误信息。分类描述用途，不能替代事实核对。

### 情景记忆留下“这件事当时怎样发生”

继续假设这个项目出现了登录请求超时。助手检查后发现，测试环境的代理配置有误，修正配置以后，相关测试通过。

如果保存的是这次任务的条件、排查步骤、实际修复和测试证据，那么它更接近情景记忆。

下次出现类似问题，助手可以参考当时检查过哪些位置。但新任务只是也出现“超时”，并不能证明原因还是代理配置。

因此，一份有用的经历不应该只写“登录故障已解决”。它至少要说明：在哪个环境发生、观察到了什么、做了什么，以及凭什么认为修复有效。这是本文对案例记录的设计建议，不是某个框架要求的固定 Schema。

### 程序性记忆留下“下次准备怎样做”

从这次排错里，可能提炼出一个比较稳妥的方法：遇到测试环境的网络错误，先核对环境和配置差异，再判断是否需要修改业务代码。

这条内容不再只是回顾过去，而是在影响下一次任务的处理方式，所以更接近程序性记忆。

但是，“以后登录超时都修改代理配置”就过头了。它把一次任务的具体修复，当成所有任务的通用办法。

如果准备让助手根据历史形成新方法，可以先把它作为候选规则。注明适用条件，在不同故障任务里验证，必要时由维护者确认，再加入长期使用的规则。没有验证的经验，不应该自动覆盖已经确认的项目要求。

| 同一任务留下的内容          | 更接近哪一类 | 下次使用时要注意什么       |
| ------------------ | ------ | ---------------- |
| 这个项目要求 Python 3.12 | 语义记忆   | 项目范围与版本是否仍有效     |
| 某次代理配置错误导致测试超时     | 情景记忆   | 新任务的环境和症状是否相符    |
| 网络错误先核对环境差异再改业务代码  | 程序性记忆  | 适用条件是否满足，规则是否已验证 |

### 短期、长期，为什么不能放在同一排比较？

因为它们回答的是另一个问题。

一次排错经历可以只保留到任务结束，也可以保存半年，以便未来参考。保存半年，不会让它从情景记忆自动变成语义记忆。

同样，某个事实可能只在今天有效，也可能跨会话长期使用。保存时间和内容性质要分开看，才能决定怎样管理与读取。

并不是每个助手都必须建立三套存储。小项目可以从必要事实和原始经历开始，先把来源与使用范围维护好。

## 面试官继续追问

### 情景记忆一定要保存模型的完整推理吗？

不需要。

保存可观察的情况、行动与结果，往往更方便复查。模型写下的解释可能只是事后描述，不能代替工具结果、测试记录和真实环境证据。

### 程序性记忆会不会改变模型参数？

不一定。

本篇讨论的是应用保存和加载做事规则。规则可以进入提示词或作为方法文档被取回，不代表进行了训练或微调。

### 怎样检查分类有没有实际帮助？

分别准备三种任务：直接查询项目事实、寻找类似历史经历、把一种方法用到不同条件的新任务。

看助手是否拿到了正确内容，也看它是否把旧案例当成新任务事实。分类标签都填对了，但新任务仍然盲目照搬旧修复，设计就还没有解决问题。

## 面试速记卡

> - 语义记忆：知道什么，保存事实与知识。
> - 情景记忆：发生过什么，保留条件、行动和结果。
> - 程序性记忆：准备怎样做，保存方法与行为规则。
> - 分类维度：内容类型与短期、长期不是同一维度。
> - 风险：一次经历不自动成为通用规则，方法迁移需要验证。
