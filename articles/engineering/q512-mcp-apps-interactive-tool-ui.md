# MCP Apps 是什么？MCP 工具如何返回可交互的界面？

> 作者：程序员Sunday · [Sunday面试指南](https://note.lgdsunday.club/)
>
> [在线阅读与配图](https://note.lgdsunday.club/engineering/q512-mcp-apps-interactive-tool-ui/) · [题库目录](../../README.md)

下面是一段模拟面试对话。

🧑‍💻 面试官：MCP 工具已经能查库存，为什么还需要 MCP Apps？

🙋‍♂️ 我：它可以让工具返回网页，把结果显示得更好看。

🧑‍💻 面试官：显示出来以后，用户点击“切换仓库”，界面怎么继续调用工具？

🙋‍♂️ 我：需要让页面和宿主应用通信，再由宿主去调用工具。

🧑‍💻 面试官：页面能发请求，就能调用所有工具吗？当前聊天客户端不支持这个扩展，又会发生什么？

> 这道题的核心是「谁加载界面，谁转发动作，谁判断权限」。MCP Apps 把工具与交互界面接起来，宿主仍然掌握边界。

## 面试速答（60 秒版）

MCP Apps 是 MCP 的扩展，用来把工具提供的能力显示为可交互界面。例如查询库存以后，在聊天应用里显示图表，用户可以切换仓库或查看某个商品。

它不只是让工具返回一段 HTML。服务器要提供相关 UI 资源，支持扩展的宿主要加载界面，并处理工具结果、界面消息和后续调用。[官方概览](https://modelcontextprotocol.io/extensions/apps/overview)。

界面通常在宿主的沙箱 iframe 中运行，通过规定的消息与宿主通信。用户点击按钮以后，也要经过宿主允许的能力和服务器授权，不能直接获得全部工具权限。

因此，接入时要同时检查 Server、UI 和宿主支持。宿主不支持扩展时，应保留能够独立理解的工具数据或文字结果，不能让核心功能完全依赖图形界面。

## 知识点详解：一次库存查询怎样变成可操作页面

### 工具结果和 UI 资源是两份不同的东西

假设 `query_inventory` 返回仓库编号、商品名称和库存数量。普通 MCP 客户端可以读取这些结构化数据，再生成文字解释。

现在咱们希望显示库存图表。服务器还要提供用于呈现数据的界面资源，并在相关元数据中建立工具和界面的联系。宿主根据扩展约定找到资源。

数据告诉应用“库存是多少”，界面资源告诉宿主“怎样呈现和交互”。不能只在普通工具结果中塞一段网页源码，就假定所有客户端都会执行。

这也解释了为什么扩展需要宿主支持。仅支持核心 MCP 工具调用的客户端，未必知道怎样加载 Apps 界面。

### 宿主负责加载界面，再把数据交给它

支持 MCP Apps 的宿主会在受控环境里加载界面。界面初始化并完成通信准备以后，才能处理宿主送来的工具输入、结果或更新。

例如库存图表先显示加载状态，拿到数据以后才展示柱形图。工具请求失败时，也应显示失败，而不是把旧数据继续当作最新库存。

界面与宿主之间使用基于消息的协议，不是任意访问父页面对象。[官方对通信和沙箱的说明](https://modelcontextprotocol.io/extensions/apps/overview)。服务器侧 MCP 连接与界面侧通信处在不同位置，不要画成 iframe 直接接管整套 MCP Client。

![工具结果与 UI 资源怎样汇合](https://note.lgdsunday.club/img/Q512/02-resource-loading.webp)

图中是两路内容的关系示意。关联资源通常由工具定义中的元数据说明；宿主再读取资源，不是每次工具调用都把整份界面代码随结果返回。

### 点击按钮以后，调用仍要经过宿主

用户把仓库从 A 改成 B，界面可以按扩展协议提出工具调用。宿主接到请求后，检查当前允许的能力，再通过自己的 MCP 连接处理调用。

服务器执行工具时，还需要根据可信身份检查：这个用户能否查看 B 仓库。界面传来的 `warehouse_id` 是输入参数，不是授权证明。

如果涉及调整库存，情况又不同。查询按钮和写入按钮不能共享一个模糊的“已授权”状态。高风险动作还可能需要明确确认，并验证参数没有在确认以后被替换。

![点击确认以后，谁调用工具？](https://note.lgdsunday.club/img/Q512/03-button-call.webp)

### 沙箱减少界面影响范围，但不会替代业务校验

MCP Apps 的界面运行在沙箱 iframe 中，宿主控制可访问能力，并通过消息进行通信。[扩展介绍](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)。

这能限制界面对宿主页面和数据的影响。不过，业务接口接受错误参数、服务器没有验证用户权限，仍然会导致问题。

可以沿一次操作逐段检查：界面提出了什么请求，宿主允许了什么，服务器最终执行了什么。三处日志按任务关联起来，失败时才能知道是界面未加载、消息未到达，还是工具拒绝了执行。

本文讲扩展机制，不提供会随 SDK 主版本变化的复制即用代码。真正接入时应锁定 SDK 与宿主版本，再核对资源元数据和通信方法。

## 面试官继续追问

### 它和 A2UI 是同一个东西吗？

不是同一套约定。MCP Apps 关注 MCP 能力怎样带上可交互界面；A2UI 关注如何用受控的声明描述界面。

可以存在组合，但不能因为都涉及 UI，就假定消息格式、资源加载和宿主支持相同。

### 界面发起的调用需要再次让模型批准吗？

不应把“模型批准”当成授权机制。具体调用是否需要确认，由宿主与业务规则决定。

例如切换可读仓库可以直接进行，写入库存可能需要用户确认。无论模型有没有参与，都要在可信执行层检查权限。

### 怎么验证集成完成了？

检查首次加载、工具失败、重复点击、不同宿主，以及不支持扩展时的文字回退。还要构造一个越权仓库请求，确认服务器拒绝后，界面能够正确显示结果。

## 面试速记卡

> - MCP Apps：把 MCP 能力与可交互界面连接起来的扩展。
> - 服务器：提供工具、数据和关联的 UI 资源。
> - 宿主：加载界面、转发消息并限制可用能力。
> - 界面：展示结果、接收用户操作，不能自行扩大权限。
> - 集成检查：宿主支持、业务授权和无界面回退都要验证。
